# 模块 05：技能加载

> 把专业领域知识做成一本本"说明书"：启动时只在系统提示词里放一张目录卡，模型干到哪块缺知识，就自己翻哪本——全文按需进上下文，目录常驻不膨胀。

## 这个模块要解决什么问题

到模块 04 为止，这个智能体已经有了手（文件工具、命令工具）、有帮手（子智能体）、有计划（待办清单），但它仍然"没读过书"：

- **模型的知识停在训练那天**。某个前端框架的最新脚手架参数、团队内部的提交规范、本项目约定的测试写法——这些都不在模型参数里，靠猜就会用错参数、走错流程。
- **把知识全塞进系统提示词太贵**。假设有 10 个领域各写一份 2000 token 的说明书，全量注入就是 2 万 token。而其中 9 份跟当前任务毫无关系，却要在**每一轮**请求里重复付费，还稀释了模型对真正重要内容的注意力。
- **更无法预知要用哪份知识**。用户下一句话是部署还是写测试，启动时根本不知道；预加载所有技能就是花 2 万 token 买一份"可能用不上"的保险。

模块 05 要回答的问题是：**怎么让智能体"知道有哪些知识可学"，又只为自己真正用到的那份知识付费。**

## 核心思想

一句话：**知识的惰性加载**。像图书馆——书架上摆的是索引卡片（便宜、常驻），藏书在库房里（昂贵、按需取用）。

落到机制上就是**两层注入**：

```
启动时（第一层，便宜）：
  系统提示词 ← "可用技能：git（版本管理规范）、test（测试实践）……"
                每条约 100 token，一共几百 token，每轮都带着

运行中（第二层，按需）：
  模型发现缺知识
      ↓ 调用"加载技能的工具"，指名要 git
  执行体从启动时建好的内存库里取出全文（约 2000 token）
      ↓
  全文作为这一次工具调用的结果回灌进消息列表
      ↓
  模型下一轮就"读过这本书"了
```

关键在于：**全文只进消息列表，永远不进系统提示词**。这一条决定了整个模块的成本结构（后文详述）。

也可以把两层各自的角色这样记：第一层回答"**有什么可学**"（让模型知道知识的存在），第二层回答"**具体怎么学**"（把知识真正送进上下文）。缺了第一层，模型不知道去加载；缺了第二层，加载无从谈起；两层都全量常驻，则退回到最初那个贵得离谱的方案。

## 工作原理

### 1. 技能是一份带元数据的说明书

每个技能就是一个子文件夹里的一份说明文件，格式刻意简单：

- 文件开头是一小段元数据：技能名称 + 一句话描述（"什么时候该用我"）；
- 分隔线之后是正文——用自然语言写给模型看的操作指南，可以有步骤、清单、注意事项、示例参数。

启动时，加载器递归扫描技能目录，把每份文件解析成"名称 → 全文"存进一张内存映射表，同时抽出元数据备用。扫描同时兼容两种运行形态：开发时直接读磁盘上的文件夹；整体打包之后也能从包体内部把同样结构的文件读出来——技能随包分发，不依赖外部环境。

这份"说明书"的定位要和工具区分开：**工具是能力（做什么），技能是知识（怎么做才对）**。加载一个技能不会增加任何可执行的东西，只会改变模型接下来"怎么用已有工具"。

### 2. 第一层：系统提示词里只放目录和使用策略

装配阶段，加载器把映射表压缩成一份极简清单——每行"名称：一句话描述"——作为一段提示片段拼进系统提示词。同一段落里还写明了使用策略，大意是：

- 处理不熟悉的主题之前，先加载相关技能；
- 遇到需要遵循特定规范或标准流程的场合，主动加载；
- 加载之后先读懂，再动手。

另外还有一处容易被忽略的"双保险"：**加载工具自身的描述文案里也拼上了全部可用技能名**。模型在决定调用什么工具时，看的是工具清单；目录在系统提示词里、技能名也在工具描述里，两条路都通向同一个事实，模型想"找个技能"时不会扑空。

这一层的成本被精确控制：每个技能约 100 token，10 个技能也只有千把 token，而且是**静态的**——启动后每一轮都一模一样。

把两种做法的账本摆在一起看，差别一目了然：

| | 全部塞进系统提示词 | 两层注入（本模块） |
|---|---|---|
| 启动时常驻成本 | 约 20000 token（10 份全文） | 约 1000 token（10 条目录） |
| 与当前任务无关的开销 | 每轮都在付 | 几乎为零 |
| 加载新知识后 | 系统提示词变样，缓存全部失效 | 只多一条消息，缓存照旧 |
| 新增一份技能 | 常驻成本再涨一截 | 目录涨 100 token，仅此而已 |

### 3. 第二层：模型主动调用加载工具取全文

当模型判断需要某份知识，它会发出一次普通的工具调用，指名要哪个技能。执行路径极短：

1. 执行体拿技能名去查启动时建好的那张内存映射表——**不发生任何磁盘读取**，因为全文早在启动时就已经载入内存了；
2. 查到了，就把全文用一对成对的标记包裹起来（技能名称和描述作为标记的属性），返回作为本次工具调用的结果；
3. 查不到（模型拼错了名字），不抛异常，而是返回一句错误提示并附上全部可用技能名——模型下一轮就能自己纠正，对话不会中断。

于是这份约 2000 token 的全文出现在消息列表中间，模型从下一轮开始就能引用它。如果同一会话里不再提到，这份内容的"性价比"只在被用到的那几轮里支付。

### 4. 为什么全文走工具结果，而不是塞进系统提示词

这是本模块最重要的一条设计决策，理由有两个：

**其一，保住提示词缓存。** 系统提示词的特点是跨轮完全不变，服务提供商可以对其做缓存，重复轮次只收极低的缓存命中价。如果技能全文注入系统提示词，每加载一个新技能，系统提示词就变一个新样子，缓存立刻全部失效，之前攒的便宜全部作废。而工具结果属于消息列表的动态部分，注入多少内容都不碰那块"可缓存的不动产"。

**其二，控制膨胀。** 系统提示词是只增不减的常驻成本；技能会越攒越多，全部塞进去等于把"按需"退化回"全量"。走工具结果，上下文里只留模型真正要用的那一两份。

代价也要说清楚：消息列表中段的内容，模型对它的注意力优先级略低于系统提示词。本模块刻意接受了这点损失——对"照着说明书操作"这类任务，这点损失远小于缓存失效和膨胀的代价。

### 5. 与既有能力的拼装：提示片段 + 工具

本模块没有重写智能体循环，待办催办、子智能体这些上一模块的功能原样保留。新增的技能功能同样以"一个工具 + 一段提示片段"的形式挂载进主程序：

```
基础工具（读/写/改/查/命令/搜索）
    + 待办能力（工具 + 催办钩子 + 提示片段）
    + 子智能体能力（工具 + 提示片段）
    + 技能能力（加载工具 + 技能目录片段）   ← 本模块新增
    = 拼装完成的智能体
```

技能加载器由技能能力自己持有，装配处只负责把"目录清单"交给系统提示词、把"加载器"交给内置的查看技能命令。想摘掉这个能力，删掉装配的那几行即可，其余一切照常。

### 6. 技能是数据，不是代码：扩充零成本

本模块还有一个容易被低估的性质：**给智能体添加新知识，不需要动任何程序**。想教它一套新的部署规范，步骤是——在技能目录下建一个新文件夹，放一份说明文件，开头写上名称和一句话描述，正文用自然语言写清楚步骤与注意事项，重启即生效。

技能因此是纯粹的**数据**：可以由不懂编程的人来写、可以版本化管理、可以在不同项目间拷贝复用。对比一下另一种思路——把领域知识"编译"进程序逻辑或者写死在提示词模板里，每加一条知识都要改代码、重新构建。技能机制把"知识更新"从工程行为降级成了编辑行为，这也是它在现实中被广泛照搬的根本原因。

启动时还能随时用内置命令打印当前可用技能清单，人和模型看到的是同一份目录——排查"模型为什么没用某技能"时，第一步就是确认目录里到底有没有它。

## 一次完整运行的流转

以剧本 s05 为例，用户说："搭建一个新的 Next.js 项目，使用 TypeScript。"

1. **会话开始前**，加载器已扫描技能目录、建好映射表；系统提示词里带着技能目录。目录里恰好有一条框架技能，描述写明"前端框架项目脚手架与配置规范"。
2. **第一轮**，模型读到任务，意识到这是特定框架的工程，参数自己拿不准。它没有直接动手，而是先调用加载工具，指名要那份框架技能。
3. **注入**，工具结果位置出现了那份说明书全文：脚手架命令的正确参数组合、目录结构约定、各类配置项的推荐值。此刻系统提示词一个字都没变。
4. **第二轮**，模型"读过书"了，回复说了解这个框架的搭建方式，接着发起命令调用——参数与说明书里给的一一对应：启用类型检查、启用指定目录结构、装上样式与代码检查、选用新版路由风格。没有技能时这些参数很容易漏一两个，事后补配置要折腾很久。
5. **结果**，项目一次创建成功，模型汇报：项目已建好，包含哪些配置。整个过程目录层只花了百来 token，全文层只在被用到的那两三轮里存在。

补一个不顺利的分支，看看容错是怎么工作的：假如模型第二轮拼错了技能名，执行体不会抛错中断，而是回一句"未知技能，可用技能如下"并附上全部名字。模型下一轮照着清单重新调用一次，全文照样到手——**错误信息被设计成下一轮的导航**，多花一轮，对话不崩。

再补一个日常分支：用户接着说"帮我按团队规范审一下刚才生成的代码"。模型在目录里看到有一条代码审查技能，加载全文后照着里面的检查清单逐项过——同一份目录，这一轮服务的是另一个领域。目录常驻的价值正在于此：模型随时知道自己"还写过哪些书"。

对照着看，如果没有这个机制，模型大概率靠训练记忆拼一个"大概对"的命令，或者先花好几轮试错探路——知识按需注入把这两类浪费都省掉了。

## 设计取舍

- **按需加载 vs 预加载全部**。按需省下绝大多数 token，代价是多数任务要多付一次工具调用往返；预加载省一次往返，却为"用不上的知识"持续付费，还要预判模型需要什么。本项目选按需，并写明使用策略让模型主动去取。
- **目录常驻 vs 全文常驻**。每技能约 100 token 的目录是"索引成本"，换来的是模型**知道**有这份知识存在——这是按需加载成立的前提。如果连目录都不放，模型根本不知道可以去加载什么。
- **元数据 + 正文的混合格式**。纯正文文件省事，但抽取"名称/描述"得靠脆弱的猜规则；纯结构化数据文件好解析，但正文得塞进字符串里，人没法舒服地写和改。开头一小段元数据 + 分隔线 + 自然语言正文，两头兼顾。
- **注意力优先级 vs 缓存友好**。全文若放系统提示词，模型会更"重视"它，但缓存失效加无限膨胀的代价更高。本模块明确选了后者，这是在"模型表现"与"工程成本"之间做的一次显式交易。
- **加载失败不抛异常**。拼错技能名返回错误清单而不是让整轮崩溃——对模型这类"会犯糊涂的调用方"，把错误信息设计成可自我纠正的提示，比设计成异常更实用。
- **技能内容包一层标记再注入**。全文不是裸贴进对话，而是用一对带名称与描述属性的成对标记裹好——模型一眼能看出"这是一份完整说明书、讲到哪里为止"，不会把说明书正文误认作用户在说话。

## 在整个项目中的位置

- **相对模块 04 新增了什么**：04 解决的是"人手不够"（把活儿分给子智能体），05 解决的是"知识不够"（把书按需借来读）。至此智能体四个基本要素凑齐了三样：工具（02）、计划（03/04）、知识（05），唯独还欠一样——**记忆装不下**。
- **为后续铺了什么路**：
  - "提示片段 + 工具"这种能力拼装方式，是后续所有功能模块的标准形态：模块 06 的压缩、07 的任务图、08 的后台执行，全都以同样方式挂载；
  - "全文只进消息列表、系统提示词保持静态"的原则，在模块 15（系统提示词工程）里会被进一步展开；
  - 技能目录从本模块起成为每个后续模块的标配，"按需加载说明书"也正是现实里各类"技能包"机制（给智能体发教材，而不是给它换大脑）的雏形；
  - 剩下的那个洞——上下文越干越满怎么办——正是模块 06 的主题。

读下一章之前可以先带走的判断标准：**凡是"知道它存在就够"的信息，放目录；凡是"要用时才需要细节"的信息，放说明书；凡是"每轮都必须在场"的信息，才配进系统提示词。** 这个三分类，几乎能套答此后所有关于提示词该放什么的争论。
