# 模块 19：自主运行

> 从被动应答到主动奔跑：给队友一块"任务板"，它们空闲时自己看板、自己认领、自己收工，负责人只负责把活放上去。

## 这个模块要解决什么问题

到上一模块为止，团队有了通信与协议，但分工依然是**推**式的：每一个任务都要负责人亲手拉起一个队友、亲手把任务说明塞给它。两个明显的不划算：

- **派发成本线性增长**。任务板上有十件活，负责人就得发起十次"拉起 + 派活"。任务越多，负责人越像个手工调度员。
- **队友的产能被浪费**。一个队友五分钟干完了派给它的活，接下来就是空转到轮数上限；而隔壁可能正有一堆积压任务没人做。负责人要么手工二次派发，要么眼睁睁看着一边闲一边忙。

真正缺的是**拉**式的机制：把活放到一块大家都看得见的地方，让干完活的队友自己去看"还有没有我能做的"，有就认领，没有就体面退出。这就是自主运行。

## 核心思想

**任务管"干什么"，自主钩子管"什么时候干"，邮箱管"发生了什么"。**

```
   负责人                          任务板（每条任务一个存盘条目）
     │  拆解工作，创建任务 A/B/C        A  [ ] 待办  无人认领
     │  拉起若干队友（只拉一次）        B  [ ] 待办  无人认领（依赖 A）
     │                               C  [ ] 待办  无人认领
     ▼
   队友甲后台循环                     队友乙后台循环
     │ 第一轮：干负责人派来的活          │ 第一轮：干负责人派来的活
     │ 干完 → 收尾？不，先看板            │
     │   └─ 空闲钩子：每 5 秒扫一次      │
     │       扫到 A → 抢占认领（写上认领人，状态改为进行中）
     │       继续干活 → 完成后把 A 标记完成
     │       再看板 → B 的依赖已解除 → 认领 B ……
     │       连续 60 秒无活 → 退出并向负责人汇报
```

三个支撑点：

- **任务板是共享事实**：任务状态、依赖关系、认领人都落在磁盘上，负责人和所有队友看到的是同一份，谁也不用互相转告。
- **认领是抢占动作**：认领 = 把任务的状态改成"进行中"并写上自己的名字。名字一旦被别人占住，后来的认领会直接被拒绝——这是多队友并发下不重复干活的关键。
- **空闲钩子是自主循环的发动机**：上一模块的队友循环里预留了一个"本轮没有新消息时问一句还有没有活"的口子，本模块往这个口子里接上了任务板。

## 工作原理

### 1. 任务板：把"派活"变成"放活"

任务板是一个独立于对话的持久化结构：每条任务单独存成工作区隐藏目录下的一个小文件，字段包括编号、标题、描述、状态、认领人和两组依赖关系（"被哪些任务阻塞"与"阻塞哪些任务"）。任务板能力向负责人提供五个动作：创建、列出、查看、认领、完成。

几条让任务板"像回事"的规则：

- **状态只有三档**：待办、进行中、已完成。其它取值直接被拒绝。
- **依赖是双向同步的**：给任务甲声明"它阻塞任务乙"，乙的"被阻塞"清单里会自动补上甲；反过来不用你维护两遍。
- **加依赖前先查环**：如果想给甲加一个"被乙阻塞"，而乙已经（直接或传递地）依赖甲，这条操作会被拒绝——否则两个任务会互相等待到天荒地老。
- **完成即解绑**：任务标记完成时，所有把它当前置的任务会被自动解除阻塞。这一步是自主认领能"接力"的前提：前一道工序完成，下一道工序才会浮出水面。
- **编号自增且重启可续**：任务板在启动时会扫描现有文件，从最大编号继续发号，重启不会撞号。

### 2. 认领：一次抢票的原子语义

认领动作有严格的门槛，按顺序检查三件事：

1. **状态允许吗**：只有待办或进行中的任务能被认领，已完成的直接拒绝；
2. **有人了吗**：如果任务已经有认领人、且不是当前来认领的这个队友，直接拒绝——"这个任务已经是别人的了"；
3. **都通过**：把状态改成进行中，写上认领人，落盘。

另一个隐藏约束：**认领这个动作只有队友能做**。认领人身份取自当前执行流的私有标记——负责人主线程里没有这个标记，所以负责人调认领会被明确拒绝（"只能由队友调用"）。这不是缺陷而是设计：负责人是派活的，不是抢活的；如果负责人可以随意认领，自主机制就退化回了手工调度。

配套的**扫描**动作则回答"现在有什么可干的"：遍历任务板，挑出同时满足"待办、没有未完成的前置依赖、没有认领人"的任务，按编号排序。三个条件分别排除了"做过的""还不能做的""已经有人做的"。

### 3. 空闲钩子：自主循环的发动机

团队能力在上一模块预留了一个可插拔的**空闲回调**位：队友每一轮开始时先消费自己的邮箱，如果本轮**没有任何新输入**，就去问这个回调"还有没有活"。本模块的自主能力实现了这个回调，逻辑是一个带截止时间的轮询：

```
空闲回调被触发（说明队友手头没活了，邮箱里也没新指示）
   │
   │  在 60 秒期限之内循环：
   │     ├─ 扫描任务板上的可认领任务
   │     │     └─ 有 → 认领编号最小的那个，
   │     │         返回一段话："已认领任务 #N：标题……描述……
   │     │                       完成后请把它标记完成"
   │     │
   │     └─ 没有 → 睡 5 秒再扫
   │
   └─ 60 秒到了还是没活 → 返回空
         队友收到空 → 走正常收尾（向负责人汇报），退出
```

返回的那段话会被当成一条**用户消息**注入队友自己的对话——也就是说，队友并不是被代码牵着去干活，而是"收到一条派工通知"，然后由它自己的智能体循环决定怎么干。这是整个设计里最优雅的一点：**自主性是靠往上下文里注入信息实现的，而不是靠硬编码流程**。

装配方把自主能力挂到团队能力上的方式只有一行"注入空闲钩子"。团队完全不知道任务板的存在，自主能力也可以被拔掉换成别的调度策略——比如换成"从消息队列取活"或"按时间表取活"。

### 4. 队友的三段式生命周期

加入空闲钩子后，队友的生命周期从"干完就走"变成三段：

| 阶段 | 触发 | 行为 | 离开方式 |
|---|---|---|---|
| 干活 | 被拉起 / 收到新消息 / 认领到任务 | 跑智能体循环，调工具，最多 10 轮 | 本轮无工具调用，或轮数用完 |
| 空闲 | 干完活但没被叫走 | 每 5 秒看一次邮箱和任务板 | 60 秒内找到新活 → 回到干活；找不到 → 进入收尾 |
| 收尾 | 空闲超时 / 收到关停请求 / 异常 | 向负责人汇报结果或错误，退出 | 执行流结束 |

注意**干活的轮数上限是"每一段"的，而不是一生的**：队友认领到新任务后，又是一个崭新的最多 10 轮。于是一个队友可以连续做很多件任务，只要每件任务都在轮数预算内完成。

### 5. 防护栏

自主等于"没人盯着也在跑"，所以防护栏比前两个模块更密：

- **空闲超时**（60 秒）：防止队友永久空转占着资源。这是自主循环唯一的退出定时器。
- **单段轮数上限**（10 轮）：防止单个任务把执行流跑飞。花销上限以轮数近似，教学版没有做真正的预算计量。
- **认领冲突保护**：两个队友同时扫到同一件任务时，只有一个能认领成功，另一个的认领会失败——失败方收到的是明确的错误，而不是默默重复劳动。
- **依赖顺序**：被阻塞的任务根本不会出现在可认领清单里，队友想抢也抢不到，避免"前置没做完就开工"。
- **异常即汇报即退**：任何异常转成消息投回负责人邮箱，执行流安静结束；负责人进程结束时，所有还在跑的队友被统一打断。

### 6. 负责人依然是对话式的

一个容易误解的点：本模块的"自主"只发生在**队友**一侧。负责人依然是一个阻塞式的对话循环——你不说话，它就不动。自主与交互两种模式在同一个进程里并存：

- **交互模式**（负责人）：你输入 → 它思考 → 它调工具 → 它回复。随时可以插手：查任务板、追加任务、发起关停。
- **自主模式**（队友）：无人指挥，靠邮箱和任务板驱动，靠超时与轮数上限自我约束。

两者唯一的交汇点是那张任务板和那套邮箱：负责人往任务板上放活，队友从任务板上取活；队友的完成回执与认领进展通过邮箱回到负责人的下一轮对话。定时调度能力也仍然挂着——时间触发产生的提示同样走邮箱，等于给了负责人一种"不需要你说话也能动"的补充途径。

## 一次完整运行的流转

以"整理项目文档"为例：

```
你：把文档工作拆成任务分给队友，不用一个个派

负责人：创建三件任务并拉起两个队友
        #1  [ ] 整理接口文档        （无人认领）
        #2  [ ] 整理部署文档        （无人认领）
        #3  [ ] 汇总索引           （依赖 #1、#2）
        小艾、小博已上线

        └─ 小艾第一段：干负责人初始说明里的活，4 轮做完
        └─ 小博第一段：3 轮做完自己的活
             （两人先后进入空闲，各自开始每 5 秒看一次板）

        小艾扫到 #1 → 认领成功（状态变为进行中，认领人=小艾）
        小博几乎同时扫到 #1 → 认领被拒绝"已被小艾认领"
             → 小博下一轮扫描认领了 #2

        小艾完成 #1 → 任务板自动把 #3 的阻塞解除一项
        小博完成 #2 → #3 的阻塞全部解除
        小艾空闲钩子再扫描 → #3 出现在可认领清单 → 认领并完成

        小博空闲钩子连续 60 秒没扫到活 → 返回空
             → 向负责人汇报"我这边没有更多任务了"，退出
        小艾完成 #3 → 同样超时退出

你：做得怎么样了？

负责人：（钩子收信，回执全部注入本轮）……三件任务全部完成，
        接口文档 12 页、部署文档 5 页、索引已生成。
```

关键观察点：

- 负责人只做了一次"拆解 + 拉人"，之后的六次派工全部由任务板与空闲钩子自发完成；
- #3 的接力依赖"完成即解绑"——如果没这条规则，它永远躺在板上没人能动；
- 小博那次失败的认领是并发的真实痕迹，抢票语义保证了没有重复劳动。

## 设计取舍

- **共享任务板而不是互相派消息**。让队友互相指派会形成网状通信，复杂度爆炸；收敛到一块板子上，通信量从"两两"降到"人人对板"。代价是任务板成为单点：它坏了，整个团队的自主性就停摆（好在它只是目录里的一批小文件）。
- **先扫描后认领，两步分开**。扫描是只读的、可以很宽松；认领是写状态的、必须严格。分开之后，"发现工作"和"占有工作"可以各自演进，也天然处理了并发竞争——扫描到不等于拿到，拿到才算数。
- **空闲轮询而不是事件推送**。实现只要一个带截止时间的循环，无需任何订阅机制。代价是最多 5 秒的响应延迟和空转的扫描开销——对后台队友来说这两个代价都可以忽略。
- **空闲超时一刀切**。60 秒没有活就退出，简单且必然收敛。代价是"活可能在 61 秒后到来"——但负责人随时可以再拉一个队友，退出不是不可逆的损失。
- **认领权限只给队友**。把负责人排除在抢活之外，保住了"派活方不与干活方竞争"的角色边界，也让"认领人"字段永远指向真正干活的人。
- **教学版的已知简化**：任务板与依赖都为教学做了裁剪，没有优先级、没有截止时间、没有重试计数；队友认领靠"编号最小优先"，没有更聪明的匹配（比如按角色匹配擅长任务）。

## 在整个项目中的位置

- **相对模块 18（团队协议）**：协议解决了"怎么有纪律地对话"，自主运行解决了"谁来发起对话"。队友第一次不需要等指令就能产生工作量，负责人的角色从调度员退到拆解者与验收者。
- **相对模块 16（定时调度）**：定时是"时间驱动的自主"，只对负责人生效；本模块是"任务驱动的自主"，对队友生效。两者叠加后，这个系统既能在没人说话的时间点醒来，也能在醒来后自己找活干。
- **上一模块的空闲回调位被填上了**：团队模块预留的扩展点第一次真正接上了实现，也验证了"能力插拔"设计——调度策略可以整包替换。
- **为模块 20（工作区隔离）铺垫**：一旦队友开始自发认领、并行推进多件任务，"所有人都在同一个目录里改文件"立刻成为最大的事故源——下一个模块给每个任务划一块互不干扰的地盘。
- **为后续综合模块铺垫**：任务板 + 自主认领 + 协议握手 + 邮箱通信，这套组合正是后续综合模块里"多智能体协作系统"的骨架。
