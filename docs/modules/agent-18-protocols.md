# 模块 18：团队协作协议

> 一套循环适配多种"协议"：把上一模块松散的邮箱闲聊，升级成带唯一编号、有状态机的请求—回执握手，让负责人能体面地关停队友、审批队友的方案。

## 这个模块要解决什么问题

上一模块的队友能干活了，但协调是**松散**的：负责人发一段话，队友回一段话，中间没有任何约定。两个场景会立刻暴露问题：

- **关停**。负责人想让某个队友停下来。直接掐断它的执行流，它写到一半的文件就留在磁盘上，任务状态悬在半空。正确做法是握手：负责人发"请你收尾退出"，队友把手上最后一件事做完、回一句"收到"，然后自己退出。
- **高风险操作先审后做**。队友要重构核心模块，直接动手太冒险。应该先让它交一份方案，负责人看过、批了，它再动手；不批，它就改方案或者放弃。

这两个场景结构完全一样：**一方发请求，另一方给回复，请求和回复靠同一个编号关联，中间状态要有人记账**。把这套"请求—回执"机制抽出来，就是本模块的全部内容。

顺带分清一个容易混淆的词。本项目里"协议"有两个含义：

1. **模型接口协议**——智能体与不同大模型服务之间的请求格式差异。这件事从第一个模块起就被一层协议中立的消息抽象挡住了：同一条对话消息、同一批工具定义，既能被某家风格的适配层翻译，也能被兼容另一家风格的适配层翻译，智能体循环本身一行业务逻辑都不用改。那种"协议兼容"不属于本模块。
2. **团队协作协议**——多个智能体**彼此之间**怎么有礼貌、有纪律地通信。这才是本模块要做的：在文件邮箱之上，加一层结构化的请求—回执状态机。

## 核心思想

把"闲聊"升级成"公文"。一条公文有三个要素：

```
 发起方 ─── 请求(类型 + 唯一编号 + 内容) ───> 接收方
    ▲                                          │
    │                处理并落账                  │
    └────── 回执(同一编号 + 结果) <──────────────┘

 台账：编号 ─> { 类型, 发起方, 接收方, 状态: 待回应 → 已回应/已通过/已驳回 }
```

- **编号贯穿全程**：请求带着编号出去，回执带着编号回来。没有编号，负责人收到三条回执就分不清哪条对应哪个请求。
- **状态机记账**：每条请求在发起方一侧登记一条状态记录，从"待回应"走到"已回应 / 已通过 / 已驳回"。记账的意义是可查询、防重复、防错配。
- **按类型路由**：收件箱里的消息不再一律当闲聊注入对话，而是先按类型分流——普通消息照旧，协议消息走各自的处理器。

## 工作原理

### 1. 台账：一次握手的完整档案

负责人一侧维护一张**协议台账**：一个并发安全的名册，键是请求编号，值是一条完整的状态记录——类型、发起方、接收方、当前状态、负载内容、创建时间。

- 发请求时**建档**：生成一个短随机编号，写一条"待回应"的记录；
- 收到回执时**销账**：按编号找到记录，把状态改成"已回应"；
- 审批动作会显式地把状态改成"已通过"或"已驳回"。

台账是纯内存的，生命周期能力启动到进程结束。它不追求持久化——协议握手是短命的，丢一条台账的代价远小于维护一套落盘机制的复杂度。

### 2. 路由器：收件箱里的分拣员

负责人每轮调用模型前，团队能力会把收件箱整箱取走；本模块在这条链路后追加了一个**路由器**，按消息类型分拣：

```
收件箱消息
   │
   ├─ 类型 = 关停回执      → 台账销账（状态改为已回应），
   │                        注入提示："某某已确认关闭"
   │
   ├─ 类型 = 方案审批请求  → 台账建档（状态为待回应），
   │                        注入提示："某某请求审批方案（编号 xx），
   │                        请用审批工具决定通过/驳回"
   │
   └─ 类型 = 普通消息/其他 → 原样包装注入："收到来自某人的消息：……"
```

路由器对每条消息返回一个**处理结论**：要不要终止谁、要给模型注入什么提示文本。这个"结论"是刻意设计的小接口——本模块只用到"注入提示"，但"终止某人"这个开关位已经留好，后续模块（比如自主运行里的超时退场）可以直接用。

注入的提示文本是这条链路的点睛之笔：路由器不只是默默记账，它把"下一步该干什么"写进提示里（"请用审批工具决定"），等于把操作指引递到了模型手上。模型下一轮自然会去调审批工具。

### 3. 握手一：优雅关停

方向：负责人 → 队友。

```
负责人                          队友
   │ 发起关停                      │
   │  生成编号、台账建档（待回应）    │
   │  类型=关停请求 的消息入队友邮箱  │
   │ ────────────────────────────> │
   │                               │ 队友每轮循环开始先读邮箱
   │                               │ 认出关停请求 →
   │   类型=普通消息："收到，退出"     │ 回一条确认
   │ <──────────────────────────── │ 立即结束自己的循环
   │                               │
   │ 收到确认 → 台账销账             │
   │ 注入提示："某某已确认关闭"        │
```

对队友来说，关停只是它循环里多判断的一个消息类型，不需要任何新工具。收到就回执、就退出，写了一半的活由它自己在收尾逻辑里交代——这就是"体面"的含义：**退出是队友自己走的，不是被外力掐断的**。

### 4. 握手二：方案审批

方向：队友 → 负责人（发起权反过来）。

流程分四步：

1. **索取方案**：负责人用"索取方案"动作给某个队友发一条普通消息，说明希望对方按什么方向出方案。这一步不走台账——它只是个普通的提醒。
2. **提交方案**：队友把自己的方案用一条**带类型**的消息（方案审批请求，附上编号与方案正文）发进负责人邮箱。
3. **分拣与提示**：负责人邮箱被路由器分拣：认出是审批请求，就台账建档（记录发起方是哪个队友），并提示负责人"某某请求审批方案，请用审批工具决定"。
4. **审批回送**：负责人调用**审批**动作（给编号 + 通过或驳回 + 可选意见）。台账先改状态，然后按台账里记录的发起方，把审批结果（编号、是否通过、意见）作为带类型的回执投回**那个队友**的邮箱。

第 4 步里"回给谁"是查台账查出来的，不是审批时再填的——这正是台账存在的价值：**发起方信息在请求建档时就被记住了，审批人只需要记住一个编号**。

### 5. 与团队模块的拼装关系

协议能力没有去改动团队能力的任何代码，它的接入方式是叠加：

- **共享同一套邮箱**。邮箱是无状态的纯文件，协议能力自己拿一个总线实例去读写，看到的就是和团队能力同一批收件箱。两个能力甚至可以只注册其中一个——只装协议能力也能发起关停，只是没有队友会回执而已。
- **同一种注入机制**。团队能力的钩子把普通回执包成"［来自某人］……"，协议能力的钩子把路由结论包成"［协议］……"。两个钩子按注册顺序依次执行，互不知晓但互不冲突。
- **工具面**。负责人在此前基础上多了三件协议工具：发起关停、索取方案、审批方案。队友一侧不变——它只是多认识了两种消息类型。

## 一次完整运行的流转

以"让队友小博重构认证模块，但方案要先过审"为例：

```
你：让小博重构认证模块，方案先给我看

负责人：拉起小博（角色：后端工程师），并让它先交方案
        └─ 小博后台启动，读代码，第 3 轮提交方案：
           "方案：抽出鉴权过滤器，统一令牌校验，预计改 6 个文件（编号 a1b2c3d4）"
              └─ 带类型的消息进负责人邮箱

你：现在什么情况？

负责人：（钩子收信 → 路由器分拣 → 台账建档为"待回应"）
        ［协议］小博请求审批方案……（编号 a1b2c3d4），请用审批工具决定
        我看方案可行，批准。

        （调用审批工具：编号 a1b2c3d4，通过，意见"注意兼容旧接口"）
              └─ 台账状态改为"已通过"
              └─ 审批回执投进小博邮箱

        └─ 小博下一轮读邮箱，拿到"已通过 + 意见"，开始动手重构
           干完之后兜底汇报："小博 已完成：重构完成，共改 7 个文件"

另一条线上，你顺口说："让小艾别跑了"
        负责人：对小艾发起关停 → 小博之外的那条后台流收到关停请求，
        回一句"收到"，安静退出；台账销账，负责人向你确认。
```

关键观察点：

- 编号贯穿了"提交方案 → 建档 → 审批 → 回执"四步，负责人从头到尾只引用了那一个编号；
- 审批结果能准确回到小博手里，靠的是台账里记下的发起方，而不是审批时手工填写；
- 队友的退出是它自己走完的，负责人只是发起了一个握手。

## 设计取舍

- **内存台账，而不是落盘**。握手是秒级到分钟级的短命事务，为它建一套持久化得不偿失。代价是进程重启后所有"待回应"记录消失，对方可能永远等不到回执——教学场景里可接受。
- **类型用字符串而不是严格的枚举校验**。路由器按字符串分发，未知类型一律当普通消息处理。好处是加一种新协议类型不用改任何旧代码；代价是拼错类型名不会报错，只会被当成闲聊——调试时要靠控制台的分拣日志。
- **索取方案不走台账，提交方案才走**。发起方向的"提醒"本质是一条普通消息，没有等待回执的语义；真正需要记账的是队友发起的审批请求。按"谁在等结果谁记账"的原则分配，避免台账里塞满无意义的记录。
- **协议消息对队友是"多认识两种类型"，而不是多一套机制**。队友侧没有路由器、没有台账，只在循环开头多判断一个类型。这让协议的不对称性（负责人重、队友轻）与实际权责一致：协调是负责人的职责。
- **回执可能对不上号**。如果队友发方案时没带编号，路由器会替它补一个；如果负责人审批了一个不存在的编号，工具会报错而不是静默成功。教学版选择"能补救就补救，不能补救就报错"，不追求严格的校验链。

## 在整个项目中的位置

- **相对模块 17（智能体团队）**：17 给了团队"嘴巴"（能说话），18 给了团队"礼节"（说什么、怎么说、说完怎么确认）。松散消息升级为请求—回执，是团队从"能并行"到"可治理"的分水岭。
- **与模块 01（基础循环）的呼应**：模型接口协议的兼容在第一个模块就由协议中立的适配层解决了——本模块的"协议"是另一种协议：智能体之间的协作契约。两者共同构成"对外兼容、对内有礼"的完整图景。
- **为模块 19（自主运行）铺垫**：关停握手就是自主队友的安全阀——当队友开始自己找活干，就必须有一种不让它停不下来的方式。审批握手则是"自主但不越权"的雏形。
- **为模块 20（工作区隔离）铺垫**：审批通过的方案往往意味着要动文件；当多个被批准的方案并行落地时，"在哪改"成为新问题——工作区隔离顺势登场。
