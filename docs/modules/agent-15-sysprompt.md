# 模块 15：系统提示词工程

> 系统提示词从"写死的一长串"变成"每轮按当前环境现场装配的拼装件"——身份、工具、环境、记忆四段各管一段、按条件挂载，谁在场谁出现，谁不在场谁消失。

## 这个模块要解决什么问题

此前的模块里，系统提示词有三种活法，各有毛病：

- **一整段硬编码**。改一个字都要动代码；想按环境换个说法，只能再写一份然后自己判断用哪份。
- **基础提示 + 能力片段一次性拼好**。模块 13、16 用的就是这种：装配时把各能力贡献的片段接上，拼完就定型。问题在于拼好的那一刻**环境是那个环境**，之后环境变了提示词不会跟着变——工具被拔了，清单还在；记忆文件删了，"你有持久记忆"的谎话还在骗模型。
- **提示词与真实状态漂移**。这是最隐蔽的一类问题：模型被告知"你有九个工具"，实际只剩六个；它被告知"工作目录是某某"，而目录早就换了。模型不质疑提示词，它只会照着过时的地图走路。

根因是把系统提示词当成了**常量**。本模块把它改造成**函数**：输入是"当前环境的快照"，输出是提示词文本；环境变，快照变，文本就变。顺带把"提示词该写什么"这件事本身结构化——不再是一篇散文，而是各司其职的几个段落。

## 核心思想

四句话：

1. **分段注册，按序渲染**。系统提示词由若干"段"组成，每段有名字、有启用条件、有渲染逻辑；装配时逐段检查——启用就渲染，拼上去；不启用就整段消失。单段出错只跳过该段，不连累整体。
2. **条件挂载，内容即状态**。某段在不在场，本身就是信息：工具段有内容说明装了工具，记忆段出现说明记忆文件存在。提示词从"声明"变成了"仪表盘"。
3. **每轮重算，指纹缓存**。每次调用模型之前都重新装配一次，保证与真实状态零漂移；同时给上下文快照算一个指纹，指纹没变就直接复用上次的结果——重算的频率是每轮，重算的成本近乎为零。
4. **挂在既有钩子上，内核零扩展**。内核本来就有"每次调用模型前"这个挂载点，而且顺序恰好是"先跑能力的钩子、再读取系统提示词构造请求"——钩子里改写提示词，对**本轮**请求立即生效。动态装配不需要给内核加任何新接口。

```
   每轮模型调用之前：

   环境快照（工作目录 / 操作系统 / 当前工具名集合 / 记忆文件是否存在）
                     │
                     ▼
             计算上下文指纹 ──与上次相同？──是──► 直接复用上次装配结果
                     │否
                     ▼
   ┌─────────────────────────────────────────────┐
   │ 身份段（永远挂）  我是谁、由谁造、行为基调      │
   │ 工具段（有工具才挂）从实际注册的工具表现场生成   │
   │ 环境段（永远挂）  操作系统 + 工作目录          │
   │ 记忆段（记忆文件存在才挂）索引摘要，超长截断    │
   └─────────────────────────────────────────────┘
                     │ 按注册顺序拼接
                     ▼
            写回宿主智能体的系统提示词 ──► 构造本轮请求
```

## 工作原理

### 1. 系统提示词在循环中的位置与作用域

智能体循环里每一条消息都有自己的身份：用户消息来自人，助手消息来自模型，工具结果来自执行。系统提示词不属于任何一条——它附着在**每一次请求的最前面**，是模型开口之前就已设定的语境。

这决定了它的四个特性：**作用域是全会话**（每一轮都生效，不是某一轮的指令）；**不进消息历史**（改它不会污染对话记录，也不会被裁剪、压缩波及）；**改了立即生效**（下一轮请求就带上新版）；**优先级天然高**（用户消息说"忽略你之前的设定"时，模型会在系统提示词与用户消息之间摇摆——设定在系统层，权重远高于对话层）。

因此它适合承载的是**跨轮次的稳定事实**：人格、身份、环境约束、工具规范、安全边界。而"当前用户想让干什么"这类一次性信息属于消息，不属于这里——装配上下文里特意留了一个用户输入字段，但指纹计算明确**不**把它算进去，就是为了防止"用户每说一句话，系统提示词就重装一遍"这种既无意义又毁缓存的行为。

### 2. 四个段落各自装了什么

**身份段**。回答"你是谁"：角色定位（什么样的助手）、归属（由谁创建）、行为基调（主动、简洁、遇错怎么办）。它永远挂载——无论环境怎么变，人格不变。这也是安全边界的第一道闸：把"哪些事不该做"写成身份的一部分，比散落在对话里叮嘱有效得多。

**工具段**。把"你现在有哪些工具"从**当前工具表**现场生成——注意是表里有什么就写什么，而不是把一份写死的清单背出来。这个差别在能力插拔的体系里是本质性的：注册一个新能力，下一段提示词自动多出它的工具；拔掉一个能力，清单自动缩短。模型的世界观永远与实际能力对齐，"拿着过期清单调工具"这一类错误从根上消失。

**环境段**。两条硬事实：操作系统、工作目录。别小看操作系统这一行——在 Windows 上不说明运行环境，模型会高频输出 Unix 风格的命令，然后命令执行工具逐条失败。这是项目里真实踩过的坑，最终以一行环境提示的形式固化下来。工作目录同理：相对路径是相对于谁，必须先说清。

**记忆段**。这是整个模块的"活体演示"：装配时实时探测工作目录下是否存在一个记忆索引文件——存在就把它的内容读进来（只取开头若干字符，超长截断并标注，避免一大篇记忆把系统提示词撑爆），以"持久记忆索引"的名义挂上；不存在就整段缺席。文件被创建，下一段提示词就有记忆；被删除，下一段就没有。**提示词跟着文件系统的现实起落**，动态装配的所有要素在这一段里都能看到。

四段放在一起：

| 段 | 挂载条件 | 装的是哪类事实 | 变化频率 |
|---|---|---|---|
| 身份 | 永远挂 | 人格、归属、基调、边界 | 几乎不变 |
| 工具 | 工具表非空 | 当前实际有哪些能力 | 随能力插拔 |
| 环境 | 永远挂 | 操作系统、工作目录 | 极少变 |
| 记忆 | 记忆索引文件存在 | 长期约定与背景摘要 | 随文件增删 |

这个划分本身就是一套提示词方法论：**按"变化的频率"分段**。不变的东西放一段（可以长期稳定，甚至有利于服务端的提示缓存），易变的东西单独一段（变了只重算一小块，语义边界也清晰）。反过来，如果身份、工具、环境、记忆揉成一整段，任何一处变动都会让整篇提示词作废重来，模型也要在每轮重新分辨"哪句是设定、哪句是现状"。

### 3. 装配上下文：指纹里有什么，没有什么

装配的输入是一份环境快照，字段不多：工作目录、操作系统名、当前工具名集合、记忆文件是否存在，外加一个故意不参与指纹的用户输入字段。指纹就是这几个字段串起来——任何一个变了，说明"该重新装配了"；一模一样，直接取缓存。

这个取舍背后是成本模型：重算一次装配要遍历工具表、探测一次文件系统、拼接若干段文本，单次不贵但每轮都发生；而绝大多数会话里，这些字段整场不变。指纹缓存把"每轮重算"的正确性和"几乎零成本"的实惠同时拿到。另外还有一层短路的记忆：连续两轮指纹相同就直接用上一次的结果，连查缓存的字典都省了。

工具名这块还有一个细心的处理：收集时用的是**不排序的集合**，指纹也按集合语义拼接。也就是说，两个能力先后注册顺序的调换、或者同一批工具以不同次序进入工具表，都不会触发一次毫无意义的重装——指纹衡量的是"世界里有什么"，而不是"东西是按什么顺序放进去的"。

### 4. 怎么加一段：扩展的最小路径

装配器开放了"注册"这个动作：给一个段名、一个启用条件、一个渲染逻辑，新段就挂进了装配序列——顺序即注册顺序，注册新段会顺手清空缓存（因为装配结果变了）。想加一个"安全边界段"，就是一个永远启用、渲染出一串禁令的段；想加一个"团队规范段"，条件可以是某个配置文件存在，渲染就是读它。

配合模块 13、14 已经出现过的"提示片段贡献"机制，项目里实际有两条给系统提示词添内容的路：**能力声明一段固定片段**（适合静态说明，比如某个能力的用法规范），以及**注册一个条件渲染的段**（适合依赖环境的内容）。前者的内容在装配时拼接、之后不归装配器管；后者每次装配都会重新评估。选哪条，判断标准就一条——这段话需不需要跟着状态变。

### 5. 与用户消息的区别：一张对照表

| 维度 | 系统提示词 | 用户消息 |
|---|---|---|
| 来源 | 程序按环境装配 | 人（或外部调用方）输入 |
| 生命周期 | 每轮重算，不落历史 | 追加进历史，随会话保存 |
| 受压缩影响 | 不受影响 | 会被裁剪、占位、摘要 |
| 适合承载 | 稳定事实与规则 | 一次性意图与临时指令 |
| 被对抗的难度 | 高（模型默认它是最终权威） | 低（可以和系统设定冲突） |

最后一行值得展开：用户可以在对话里说"从现在起你是另一个助手"，模型多半会配合——但那是在**扮演**；而系统提示词里定义的身份是**设定**。把安全边界放在哪一层，效果完全不同。这也是为什么身份段永远挂载、且不开放给运行时改写。

### 6. 提示词的长度账：每一段都是每次请求的固定开销

系统提示词有一个容易被忽视的成本属性：它**每轮都全额计费**。消息历史可以压缩、裁剪、摘要，系统提示词不行——它永远整篇在场。所以每加一段、每多一句，都要按"乘以整个会话的轮数"来估。

本模块的三道闸门都对着这笔账：记忆段截断（长记忆只进索引摘要，不进全文）；工具段只列名字与一句话（参数细节走工具定义通道，不重复计费）；条件挂载（没有内容就整段缺席，绝不渲染"暂无"）。再往上，指纹缓存还带来一个间接红利：装配结果稳定不变，对支持提示缓存的服务端来说，重复的前缀可以被服务端记住，实际费用进一步下降——**稳定不仅在语义上正确，在计费上也便宜**。

### 7. 每轮生效的实现细节

整个机制能成立，依赖内核里一个已经存在的执行顺序：每次调用模型前，内核先把消息列表交给所有能力的钩子过一遍，**然后**才读取系统提示词去构造请求。所以提示词能力只需在钩子里做一件事——按当前快照重新装配，把结果写回宿主的系统提示词字段——本轮请求用的就已经是新版了。上下文消息列表原样返回，一个字节不动。

这也是能力体系灵活性的一次展示：有的能力注册工具（模块 13、16），有的能力只贡献提示片段（模块 14），有的能力在每次调用前对消息列表动手术（模块 06 的压缩）——而本模块证明，能力甚至可以**改写宿主自身的状态**，只要改动发生在正确的挂载点。

落地时有一条要盯紧的时序约定：钩子里必须**先装配、后返回**，而且绝不能在返回值里做文章——消息列表原样交回，改的只是系统提示词。若在这里顺手裁剪消息，就会和模块 06 的压缩能力在同一挂载点上抢方向盘；各能力守各能力的地盘，是多个能力共存时唯一的和平协议。

## 一次完整运行的流转

以"记忆段的一生"为主线：

1. **启动**。工作目录下没有记忆索引文件。装配出的系统提示词只有三段：身份、工具（五个内置工具）、环境。控制台打出一行提示：手动创建或删除那个记忆文件，下一轮提示词会自动切换。
2. **第一轮**。用户请助手整理一份项目约定。助手调写文件工具，产出一个记忆索引文件，写入了主题与条目概要。
3. **第二轮**。用户接着问："根据我们的约定，注释风格是什么？"这一轮调用前，装配钩子探测到记忆文件**出现了**——快照指纹变了，触发重装，记忆段带着索引摘要挂进系统提示词。模型据此准确回答了约定内容，尽管本轮对话里没人复述过那份文件。
4. **第三轮**。用户用命令执行工具删掉了记忆文件。再下一轮，探测落空，记忆段整段消失，指纹再次变化。模型的世界观回到"没有持久记忆"的状态。
5. **旁证**。中途若注册一个新的能力包（比如模块 16 的定时任务），工具段会在下一次装配时自动多出它的三个工具——不需要任何人去改提示词。

验证这套机制不需要任何工具：看模型第二轮的回答内容就知道记忆段在不在场——它引用了索引里的条目，说明段挂上了；它说"我没有这方面的记录"，说明段撤下了。提示词的装配结果，模型的言行就是最直接的观测口。

这场戏的要点：没有人调用过任何"更新提示词"的动作，提示词却始终与磁盘上的现实、工具表里的现实保持一致。**漂移被消灭在每轮装配里。**

## 设计取舍

- **每轮重算 vs 启动时一次装配**。一次装配省事且省心，但提示词的生命周期从此与启动时刻绑定；每轮重算换来零漂移，再用指纹缓存把成本压到可忽略。正确性优先，成本用缓存消化。
- **条件挂载 vs 全量挂载**。把记忆段永远渲染、内容写"暂无记忆"看似统一，实则是往每次请求里塞噪音——空段不仅浪费 token，还会诱导模型围绕"我没有记忆"产生多余联想。不满足条件就整段缺席，让"缺席"本身成为信息。
- **记忆进系统提示词 vs 进消息历史**。塞进历史只花一次 token、但会被压缩管线当垃圾裁掉；放进系统提示词则每轮都在、代价是每轮都占额度。本模块选后者并加了截断上限——记忆索引要的是"恒定在场"，截断保证它不会反客为主。完整的记忆管理是模块 11 的正戏，这里只搭最小示范。
- **单段失败静默跳过 vs 整体失败**。某一段渲染抛了异常，正确反应是打一条红色警告然后跳过它——提示词少一段是降级，整个装配失败才是事故。装配器是优化路径，不是关键路径。
- **工具段用名字清单 vs 带上完整参数说明**。名字加一句话描述足够模型建立世界观；参数细节本就通过工具定义的通道传给端点，提示词里再抄一遍纯属重复计费。提示词与工具定义各说各的话，不重叠。
- **用户输入不进指纹**。进指纹意味着用户每发一条消息就重装一次提示词——缓存形同虚设，而且用户输入根本不该影响系统层设定。字段可以存在于快照里，但必须明确排除在指纹外。
- **每轮都探测一次文件系统 vs 用事件通知**。记忆段的存在性检查是"傻"的：每次装配都真去磁盘看一眼，不订阅任何文件变动事件。事件驱动更精致，但要引入监听器、处理丢失事件、管理生命周期；而一次存在性检查的成本微乎其微。**状态问一遍比维护一份状态副本便宜**——这类"轮询真相"的取向与模块 16 的秒级扫描一脉相承。
- **身份段谁有权改**。工具段派生自工具表，记忆段派生自文件系统，唯独身份段是"作者的手笔"——它不提供运行时改写入口。理由在安全：一个能被模型或对话内容改写的人格设定，等于没有设定。想换人格，换装配器或换身份段的渲染内容（改代码或改配置），走人来把关。
- **装配挂在能力钩子里 vs 内核内置提示词管理器**。把装配器做进内核当然更"正统"——但系统提示词的形态太因项目而异，内核内置就意味着每次换人格都要动公共代码。放进能力包后，内核继续只认"每次调用前读一下系统提示词"这一条老规矩，动态与否、几段、怎么条件，全是能力包自己的事。**内核定节奏，能力定内容**，这条边界在本模块被划得非常清楚。

## 在整个项目中的位置

- **相对模块 14 新增了什么**：14 证明了一段提示词能重塑智能体的行为方式，15 回答的是"提示词本身该怎么管理"——从字符串升级为装配线，从写死升级为派生。它还是第一个**改写宿主状态**而非仅仅贡献内容的能力包，把能力体系的表达边界又推了一步；而它能存在，靠的是模块 10 建立的钩子挂载点。
- **为后续铺了什么路**：
  - 模块 11 的记忆系统在这里预演了最小形态——"记忆文件在不在，决定提示词长什么样"，后续的读写、整理、遗忘都建立在这个入口上；
  - 模块 17 的多智能体协作里，每个成员的性格差异、职责边界，本质上是给每个实例装配不同的身份段——本模块的装配器就是那套差异化提示词的生产线；
  - 模块 19 的自治运行与模块 24 的综合外壳，都要在长时运行中反复回答"智能体现在是谁、有哪些工具、处在什么环境"，每轮装配、指纹缓存这套机制是它们直接复用的底座；
  - 更普适的一条：本模块与模块 14、模块 13 的提示片段贡献合起来，确立了项目的提示词纪律——**提示词要么派生自状态，要么由能力声明，不手写第三份**。
  - 验收它也只需一个动作：盯着同一会话里模型前后两轮的自我介绍是否随环境而变——变了，装配在工作；没变，八成是指纹缓存把变化吃掉了，去查快照字段。
