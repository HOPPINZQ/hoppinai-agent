# 模块 13：MCP 工具集成

> 智能体第一次通过一个开放标准协议接入"外部工具生态"——在配置清单里写几行声明，远端服务器提供的工具就会被自动发现、翻译成本地工具，并出现在同一次模型调用的工具表里。

## 这个模块要解决什么问题

模块 01 到 12 里，智能体的所有工具都是**写死在代码里**的：执行命令、读写文件、编辑、列目录、搜索内容。这套家底有两处硬伤：

- **接一个新系统 = 一次开发周期**。想让智能体查论坛、查数据库、调搜索服务，就得照着内部工具的样子再写一套定义、一套实现，然后重新编译。每接一个系统都重来一遍，而且每家系统的地址、认证方式、返回格式都不一样。
- **能力边界锁死在发布时**。工具集在程序打包那一刻就固定了，用户和运维都无能为力。

模块 05 曾用"技能"扩展过知识面，但技能给的是**文字说明**，不是**可执行的能力**。真正缺的是一个标准：让任何人在任何语言、任何机器上实现一个"能力供应方"，智能体不改动一行代码就能把它接进来。

MCP（Model Context Protocol，模型上下文协议）就是为这件事定制的开放标准。本模块把智能体变成这个标准的一个客户端：从此工具数量从固定的六个变成"六个内置 + N 个远端动态"，而 N 由一份配置文件决定。

## 核心思想

四句话：

1. **客户端-服务器分离**。智能体只当客户端；每种外部能力由一个独立进程或独立服务提供。谁实现的不重要，跑在什么语言上不重要，只要按协议说话就能接。
2. **协议只管三件事：握手、发现、调用**。连上后互相报版本与能力；客户端问"你有什么工具"；客户端说"帮我执行某个工具，参数是这些"。消息格式定死，与怎么传输无关。
3. **配置驱动 + 运行时发现**。服务器清单写在配置里（沿用主流桌面 AI 助手的同一套格式，方便直接抄别人的配置）；每个服务器到底提供哪些工具，不在配置里写死，而是启动时现场去问。
4. **翻译而非改造**。远端工具被逐个"翻译"成和内置工具一模一样的形态塞进统一工具表。内核不知道哪些是外来的，模型也不知道——它只看到一张工具清单。

```
  配置清单              启动期                                运行期
 ──────────           ──────────                            ──────────
 服务器甲(本地子进程) ─┐
 服务器乙(远程服务)  ──┼─► 解析配置、判定传输方式
 服务器丙(已禁用)    ─┘        │
                          逐个握手（单个失败只跳过）
                               │
                          向每个服务器索取工具清单
                               │
                          翻译：改名、保参、生成执行体
                               │
  六个内置工具 ──────────► 统一工具表 ◄──────────────────────┘
                               │
                     模型挑中某个远端工具并调用
                               │
                     智能体按名字路由 ─► 经客户端转发回原服务器 ─► 结果回灌上下文
```

## 工作原理

### 1. MCP 到底约定了什么

把 MCP 想象成"给 AI 用的插座标准"。协议分三层：

- **消息语义层**：定义了一组标准请求——互相介绍（握手）、列出工具/资源/提示词模板、执行工具、读取资源。所有消息一来一回都带编号，可以配对。
- **传输层**：规定这些消息**怎么**跑起来——本地进程的管道、还是网络请求。协议语义与传输细节完全解耦，同一套消息可以换三种通道跑。
- **能力层**：把外部能力分成三类——**工具**（模型主动调用的一次动作）、**资源**（可按地址读取的数据）、**提示词模板**（服务器预置的提示语）。本模块重点接工具，资源和提示词模板也有对应的枚举与读取入口。

对智能体来说，接入一个服务器分三步：握手确认彼此版本与能力，拿到一份工具清单（名字、用途、参数结构声明），之后随时可以点名执行其中一个。

### 2. 三种传输方式分别怎么工作

传输方式在配置里可以显式声明；没写时按特征推断——**有启动命令就是本地子进程，有网络地址就看地址里是否带事件流路径标记**。

**标准输入输出（STDIO）——本地子进程。** 智能体按配置里的启动命令把服务器**拉起为一个子进程**，之后所有协议消息都从子进程的标准输入写进去、从它的标准输出读出来。优点是零网络部署：一个本地程序、一份启动命令就能当服务器用；子进程随智能体退出而关闭。代价是纪律严格——**这条管道被协议独占，服务器侧绝不能往标准输出打印任何日志**，一个多余字符都会把消息流搅乱。这是子进程方式最容易踩的坑。

**服务器推送事件（SSE）——早期的远程方式（现已逐步被替代）。** 客户端先向服务器发起一条长连接，服务器通过这条连接持续往下推消息（下行通道）；客户端要发请求时另开普通网络请求走上行。于是有个别扭的细节：连接建立在"基础地址 + 固定的事件流路径"上，而调用请求发到另一个端点，所以**配置里给的地址要先剥掉尾部的事件流路径标记**，否则拼出来就是"标记叠标记"的错误地址。加载器专门处理了这个裁剪。

**流式 HTTP（Streamable HTTP）——现行推荐方式。** 只有一个端点，请求和响应都走它：客户端把每条消息发往同一地址，并声明"我既能收普通数据也能收事件流"；服务端可以回一段普通数据，也可以回一条持续推送的流。握手成功后服务端发放一个**会话标识**，客户端此后每次请求都要带上，服务器靠它认人。服务器主动发的通知类消息只回一个"已受理"的空响应。配置里的地址**原样使用**，不需要任何拼接。自定义请求头（鉴权令牌、密钥等）在三种方式下都会被统一注入到每个请求里，且有多级写法可叠用。

三种方式放在一起看，选择逻辑一目了然：

| | 标准输入输出（STDIO） | 服务器推送事件（SSE） | 流式 HTTP（Streamable HTTP） |
|---|---|---|---|
| 服务器在哪 | 本机，按命令拉起子进程 | 远程 | 远程 |
| 通道形态 | 一条独占的进程管道 | 下行长连接 + 上行短请求 | 单一端点，收发同路 |
| 地址用法 | 无地址，只有启动命令 | 要裁掉尾部事件流路径标记 | 原样使用 |
| 会话归属 | 子进程即会话 | 长连接即会话 | 每次请求携带会话标识 |
| 典型场景 | 本地程序包、脚本工具 | 旧式远程服务（逐步退役） | 现行远程服务 |
| 最易踩的坑 | 往管道里打印日志 | 地址拼接出"标记叠标记" | 忘带会话标识被拒 |

### 3. 启动期：从一份配置到一列可用工具

启动过程是一条流水线，每一环都为"隔离故障"做了设计：

1. **读配置**。逐条解析服务器清单；每条支持一个启用开关，关掉的就地跳过。解析失败只记日志，不拖垮启动。
2. **建连**。为每台服务器按传输方式创建通道并握手。**每台服务器单独兜底：某台连不上只打一条"已跳过"，其余照常**。一个细节：异步客户端的握手动作是"惰性"的——不主动等待它，连接其实根本没建立。这是个隐蔽的坑，代码里显式等待才真正建连。
3. **索取清单**。对每台连接成功的服务器问一遍"你有哪些工具"，拿到名字、描述、参数结构声明。
4. **翻译**。这是最核心的一步，把"远端工具"变成"本地工具"，三件事：
   - **名字清洗**。模型侧对工具名有严格格式要求（只允许字母数字下划线连字符、长度有上限），而远端工具名可能带点、带冒号。做法是把非法字符统一替换成下划线、超长截断；**真实原名记在执行体里**，执行时直接用原名回查远端——不需要维护一张"改名对照表"。
   - **参数结构原样保留**。只挑"类型、属性、必填项"几样是常见错误——远端声明里的其他字段（引用定义、附加规则等）一旦被丢掉，部分模型端点会直接拒绝请求。所以翻译时**整体保留、只剔除空值**，并补上最基础的兜底（缺类型补对象、缺属性补空集）；描述缺失时用工具名顶上。
   - **生成执行体**。为每个远端工具造一个闭包，把"服务器是谁、工具原名是什么"封在里面。此后内核调用它和调用内置工具没有任何区别。

### 4. 运行期：一次远端调用的路由与回程

模型发起工具调用后，内核按名字在统一工具表里命中目标，把参数交给执行体，接下来发生的事完全在翻译层内部：

- **入参双形态兼容**。内核对无类型工具有一层包装（"工具名 + 参数"套在一层外壳里），而模型直连时传的是裸参数。执行体两种都认：有外壳就拆外壳，没外壳就把整包当参数并剔除外壳残留的键。少了这层兼容，换个协议端点工具就"调不动"，而且症状诡异。
- **转发**。执行体通过对应的客户端把"执行某工具 + 参数"发给原服务器（同步方式直接等结果；异步方式等待其完成再继续）。
- **回程拼装**。服务器返回的结果可能由**多段文本**组成，拼接时全部保留、换行相连——早期版本"后一段覆盖前一段"会静默丢数据。
- **错误即结果**。远端异常不抛出到顶层，而是转成一句错误文本回灌给模型——模型看到错误描述后可以换参数重试或改走别的路，而不是整个回合崩掉。

此外，客户端在握手时也交换了彼此支持的能力（例如客户端可以声明"我有哪些工作区根目录"），为资源、提示词模板、采样等高级特性留了口子；本模块实现了资源与模板的枚举与读取。

### 5. 配置即接口：清单怎么写，鉴权怎么给

配置清单的格式刻意与主流桌面 AI 助手保持一致，所以网上现成的服务器配置大多可以直接抄。结构上是一张"名字 → 配置"的表：名字随取（会显示在连接状态里），配置体按传输方式二选一——本地子进程方式给"启动命令、命令参数、环境变量"三样（鉴权令牌常走环境变量，避免明文散落在参数里）；远程方式给"服务地址、请求头"。每条都可以带一个启用开关和一个以秒计的超时时间（慢服务器单独放宽，默认值对大多数服务够用）。

鉴权请求头有三种写法，优先级从高到低：任意多个自定义头（键值对集合，密钥头、会话凭证都能配）；单个请求头的便捷写法（头名 + 头值一行搞定）；以及一个只针对鉴权头的旧字段。三种写法最终在发送前合并成一张头表，空值全部过滤——网络层不接受空值头，漏了这层过滤就是莫名其妙的连接失败。

这份清单的深层意义在于：**接入一个外部能力的全部知识，被压缩成了几行声明**。不需要懂协议、不需要懂传输，甚至不需要懂编程——运维改配置就能给智能体加一只新"手"。

### 6. 让模型"知道"远端世界，并体面地收场

光注册工具还不够——模型对远端工具一无所知就容易乱传参数。所以系统提示词里动态拼入一节"外部工具说明"：逐台服务器列出工具名、用途、每个参数是否必填，再附两条调用纪律（**必填参数要传全、名字与大小写要精确**）。这份清单在客户端就绪后才生成，因此装配顺序上有讲究：先取工具、再拼提示。

配套还有两条以斜杠开头的诊断命令：一条打印各服务器的连接状态与传输方式，一条实时枚举所有远端工具及其描述，排障时不用翻日志。

生命周期上，能力包提供了启动与关闭两个钩子。客户端初始化采用**懒触发**：谁先用（取工具或启动横幅）谁负责建立，且只建立一次；进程退出前统一关闭所有连接——标准输入输出方式拉起的子进程不会自己消失，**不显式关闭就会留下孤儿进程**。

## 一次完整运行的流转

配置清单里有三台服务器：一台本地论坛服务（标准输入输出方式，启动一个本地程序包，鉴权令牌走环境变量传入）、一台远程演示服务（流式 HTTP，鉴权密钥写在自定义请求头里）、一台已禁用的服务器推送事件示例。

1. **启动**。控制台先打出连接横幅：本地论坛"已连接（标准输入输出）"，远程演示"已连接（流式 HTTP）"，禁用的那条压根没出现。随后打印"成功加载 N 个远端工具"。系统提示词里已经拼进了两台服务器的工具清单和必填参数说明。
2. **用户**："在论坛上搜一下关于发动机故障的帖子，把要点整理到本地笔记里。"
3. **第一轮**。模型选了**远端**的论坛搜索工具，按提示词里的参数说明传全了必填项。内核按名字命中工具表里那个"名字被清洗过的"远端工具，执行体拆开参数、经客户端转发到本地论坛子进程；子进程把搜索结果按多段文本返回，拼接后作为工具结果回灌。
4. **第二轮**。模型分析搜索结果，切到**内置**的写文件工具，把要点写进本地笔记。这一步没有任何特殊处理——在工具表里，远端和内置本来就无法区分。
5. **收尾**。模型用自然语言总结发了什么、写了什么。用户敲诊断命令核对：两台服务器、各自的传输方式、工具总数一目了然。
6. **退出**。关闭钩子逐台优雅断开，本地子进程随之终止，控制台打出"客户端已关闭"。

这场戏的要点：跨系统任务（外部取数 + 本地落盘）在同一个回合里自然完成，模型全程只做"选工具、传参数"两件事，协议细节被翻译层完全吸收。

## 设计取舍

- **标准协议 vs 自研接口**。自研可以为单一场景做到最简，但每接一个系统都要重写连接、认证、错误处理；MCP 把这些一次性标准化，代价是要实现一整套客户端——一次投入，之后"接新能力"退化成"加几行配置"。
- **独立进程 vs 进程内插件**。技能是进程内的，扩展了知识却有安全与稳定性顾虑；MCP 服务器是独立进程，崩了只影响自己，还能由不同的人用不同的语言独立升级。代价是进程管理与通信复杂度。
- **动态发现 vs 静态配置**。把工具清单也写进配置会更"可控"，但服务器每次加功能都得改配置重启；启动时现场问一遍，配置里就只需要"在哪、怎么连"。
- **名字清洗 + 闭包回查 vs 建反向映射表**。改名后执行时要用回原名，最直觉的做法是维护一张对照表——但那是一份要同步维护的状态；把原名直接封进执行闭包，分发用清洗名、执行用原名，零额外状态。
- **参数结构全量保留 vs 精简透传**。精简看似干净，实则会在严格的端点上直接失败；全量保留加"剔空 + 兜底"才是兼容多协议端点的稳妥解。
- **单个失败跳过 vs 快速失败**。一台远端服务挂了不该让整个智能体起不来。跳过策略让"部分可用"始终优于"全部不可用"，同时把跳过的原因明明白白打出来。
- **默认同步客户端 vs 异步客户端**。同步写法直白、好排障，教学项目首选；异步吞吐更高，但初始化是惰性的、忘了等待就等于没连接——这个坑被显式等待堵死，并在注释里点名。
- **清单进系统提示词 vs 只靠工具定义**。把远端工具的用途与必填参数写进提示词要花 token，却显著降低模型乱传参数的概率；对"参数结构复杂、名字被清洗过"的远端工具，这点开销值得。
- **超时从配置读 vs 全局一刀切**。远端服务的响应速度天差地别——本地子进程几十毫秒，远程服务可能要几秒。统一的短超时会让慢服务器"永远不可用"，统一的长超时会让快服务器的故障拖慢启动。把超时下放到每条配置，是把判断权交给最了解那台服务的人。
- **只接工具 vs 三类能力全接**。协议里还有"资源"（按地址读取的数据）和"提示词模板"（服务器预置的提示语）两类能力，本模块实现了它们的枚举与读取入口，但只把**工具**接进了模型的世界。资源类能力的正统用法（按需读取、缓存、差异同步）值得单独一个模块，与其浅尝辄止，不如把工具这一条主干打穿。
- **懒初始化 vs 启动即全量建连**。握手是重操作——子进程方式要拉起进程，远程方式要走网络。启动时就把所有连接建好，横幅信息完整，但"启不启动得起"被最慢的那台服务器绑架；改成"谁先用谁触发、只触发一次"，装配路径轻快，代价是首次使用的延迟和一点初始化守卫的复杂度（并发路径下要保证只建一次）。
- **多段结果拼接 vs 后段覆盖前段**。远端返回的结果常常分成好几段文本，图省事的写法是循环里不断赋值——最后只剩一段。拼接只多一个换行符的代价，保住的却是被静默吞掉的那部分数据。这类错误不报错、不崩溃，只在某天有人发现"结果怎么少了半截"时才暴露，所以值得在实现层一次做对。

## 在整个项目中的位置

- **相对模块 12 新增了什么**：12 解决"出错后怎么恢复"，13 解决"能力从哪来"。这是项目第一次引入**外部协议**：工具不再全部自产，而是可以来自任何遵守标准的外部供应方；工具数量的自由度从"编译期"移交给了"配置期"。同时本模块把能力包的插拔范式用到了极致——整包复制 + 一行注册，内核零改动。
- **为后续铺了什么路**：
  - 模块 18 的协议兼容改造（让同一套智能体同时说得来多家模型端点）直接受益于此处打的地基：参数结构全量保留、工具名清洗、入参双形态兼容、多文本段拼接——这四件事全是"为了换协议不翻车"做的；
  - 模块 17 的多智能体协作与模块 19 的自治运行，都可以把远端工具当作"现成的手"，不必事事内置；
  - 本模块确立的"配置驱动 + 动态发现 + 翻译桥接"三段式，是后续一切"接外部世界"类需求（远程服务、外部数据源、第三方命令）的模板。
