# 模块 11：持久记忆

> 跨会话的长期记忆：值得记住的事实以文件形式留在磁盘上，下次会话开始时自动回灌进模型的脑子。

## 这个模块要解决什么问题

到此为止的智能体记性再好，也只记得住"这一次运行"里的事。会话一结束，上下文就没了：

- 用户上周明明说过"我只用这个编辑器，别给我生成别的"，这周还得再教一遍；
- 用户纠正过的坏习惯（别用表情符号、别写没用的前言），下次照犯；
- 项目的目录约定、技术栈选择、部署方式，每次会话都要重新交代一遍。

会话管理器解决的是"把这次对话原样存下来、下次接着聊"——那是**逐字复述**，属于会话恢复。而这里要的是另一种东西：从对话里**提炼出值得长期保留的事实**，它们比对话本身小几个数量级，却能跨会话、跨任务地影响行为。对话是流水，记忆是沉淀。

难点有三个：什么值得记（记少了没用，记多了全是噪音）；怎么记（要让人能直接打开看、改、删）；以及怎么用（不能把全部记忆一股脑塞进上下文——那很快就比对话本身还长了）。

## 核心思想

**记忆是"磁盘上的一堆小文件 + 一个索引"，写入靠模型抽取，读取靠模型挑选。**

三句话概括整个机制：

1. **一条记忆 = 一个文件。** 每条记忆单独落盘，开头是一小段元数据（类型、名称、标签、创建时间），后面是正文。人可以直接打开看、改、删——记忆系统没有黑盒。
2. **索引只存摘要。** 另有一个索引文件，每条记忆一行。挑选相关记忆时只把索引喂给模型，而不是全部正文——这是记忆库大了之后还能便宜地检索的前提。
3. **写与读都由模型做判断。** "这轮对话里有没有值得记的事"和"这条旧记忆跟当前问题相不相关"，都是语义判断，规则写不出来，交给一次轻量的模型调用最合适。

## 工作原理

### 一、记忆以什么形式存在

记忆全部落盘在工作目录下一个以点开头的隐藏目录里，一条记忆一个文件；另在工作目录根部放一个索引文件：

```
  工作目录/
  ├── 记忆目录（以点开头，默认隐藏）   ← 一条记忆一个文件
  │     ├── 用户偏好_偏好编辑器
  │     ├── 反馈_不要用表情
  │     └── 项目_部署约定
  │
  └── 索引文件                        ← 每条记忆一行摘要
        · 用户偏好｜偏好编辑器｜标签：编辑器 —— 用户偏好使用某个编辑器
        · 反馈｜不要用表情｜标签：风格 —— 回复中不要使用表情符号
```

单个记忆文件分两段：前面是元数据块（类型、名称、标签，以及写入时自动补上的创建时间戳），后面是正文，一句话说清这条事实。名称会被清洗——只保留字母数字和下划线，其余一律替换——保证它能安全地当文件名用。

记忆分四类，分类本身就是一种质量控制：

| 类型 | 记什么 | 例子 |
|---|---|---|
| 用户偏好 | 用户的习惯与身份 | 偏好某个编辑器、习惯某种回复风格 |
| 反馈 | 用户纠正过的错误做法 | "不要用表情""结论放前面" |
| 项目 | 项目级约定 | 目录结构、技术栈、构建与部署方式 |
| 参考 | 外部资料线索 | 文档链接、关键路径 |

其中"反馈"是最有价值的一类：偏好影响风格，反馈修正行为，一条被记下的纠正等于永久免学费。写入时同名同类型的记忆会被覆盖而不是追加，索引行同步替换，不会越积越乱。

### 二、索引文件的作用

索引是整个机制的效率支点。它每条记忆只占一行：类型、名称、标签、截到 80 字符以内的一句话摘要。

为什么要单独维护索引？因为"挑相关记忆"这一步每次模型调用都要做一遍，如果把全部正文都喂给模型，记忆库一胖，每次挑选的代价就超过记忆带来的收益。只喂索引——几十行短摘要——挑选就始终是一次廉价调用；选中之后再按名称去读对应文件的正文。索引相当于书脊，正文是书页，翻书脊永远比翻书快。

写入记忆时索引同步更新：先扫一遍现有行，发现同名条目就原位替换，否则插到所有条目之后。索引与明细文件总是成对更新，不依赖启动时重建。

### 三、什么时候写：抽取的时机与分寸

写入的时机卡得很准——**只在整轮对话结束之后**。实现上挂在"模型调用前"这个钩子上：每次要请求模型之前看一眼上下文最后一条消息，只有当它是模型带正文的收尾回复（而不是某个工具的执行结果）时，才认为上一轮已经完整落幕，值得从中提炼。工具循环的中间态绝不触发抽取——否则一次任务会写出十几条半成品记忆。

两个防重复的设计：

- **水位线**：记下"已经抽取到第几条消息"，同一轮绝不抽第二次；
- **同输入跳过**：注入侧也有对称设计（见下一节），同一句用户输入不会触发两次挑选。

抽取本身也是一次模型调用：把"最近一条用户输入 + 模型最终回复"（各自截断，防止超长）交给模型，要求按固定行格式输出——类型、短名、标签、一句话正文，每行一条；**没有值得记的就输出空**。这一句约定很重要：它把"该不该记"的判断权交给模型，同时用"宁缺毋滥"压住了噪音。返回的每一行都要过格式校验，不符合的直接丢弃——解析不出的记忆宁可不要，也不能写坏文件。落盘前还带一道开关：抽取可以整体关掉，让系统退化为"只读不写"的记忆库。

两侧都有兜底：抽取失败只在控制台打一行提示，绝不阻断主对话。记忆是锦上添花，不能因为它把任务搞挂了。

### 四、下次会话如何回灌：逐轮注入

读取发生在每次模型调用之前，同样挂在"模型调用前"钩子上：

```
  新一轮用户输入
        │
        ▼
  读索引文件（全文，几十行摘要）
        │
        ▼
  一次轻量模型调用：给索引 + 当前问题，
  只要求返回相关的记忆名（最多 5 条，可为空）
        │
        ▼
  按名称读出正文（单条截断到 400 字符）
        │
        ▼
  拼成"相关记忆"段，追加在基础系统提示词之后
```

几个关键细节：

- **注入是逐轮刷新的，不是开场拼一次。** 相关性依赖"这一轮的最新用户输入"，所以每次模型调用前都重新挑选。查询和上一轮相同时直接跳过，省掉一次模型调用。
- **挑不出相关的就把系统提示词还原成基础版本**，而不是留着上一轮的旧记忆段——记忆必须跟当前问题对得上号，才配占上下文。
- **数量与长度双上限。** 每轮最多注入 5 条，单条正文最多 400 字符。这两个数字是防膨胀的闸门：记忆系统的失败模式从来不是"记不住"，而是"什么都往上下文里塞"，把上下文预算吃光、把真正相关的信息淹没。
- **为什么动态部分不能走装配期拼接？** 系统提示词的静态片段在装配时拼一次就定死了；"相关记忆"逐轮变化，只能走钩子在调用前刷新。而内核恰好是先分发钩子、再读取系统提示词的，所以钩子里的修改对本次调用立刻生效——这个顺序是注入能够成立的前提。
- 供挑选与抽取用的模型调用都是固定采样、限短输出的轻量调用，成本可控。

### 五、一个挂载点，两个方向：先写后读

注入和抽取共用同一个挂载点，执行顺序是固定的三步：先记住基础系统提示词（首次调用时捕获一次），再做抽取，最后做注入。这个"先抽取、后注入"的次序有个附带好处：本轮刚沉淀下来的新记忆，磁盘和索引里已经有了，紧接着的注入读到的就是最新索引——刚学到的事，当轮就有机会被用上。

配套的还有一条查看命令，随时能看记忆条数和索引全文；加上记忆本身就是可读可改的纯文本，人工修剪一条错误记忆只需要打开文件改两行。记忆库条数涨到阈值（10 条）时，控制台会提示"建议合并"——当前版本只提示不动作，真正的合并（把近义条目归并、过时条目归档）留给生产实现。记忆系统被刻意做成一个**人可以随时接管**的系统，而不是只有机器能读的黑箱。

### 六、记忆、会话、技能：三种"记住"的分工

| | 存什么 | 粒度 | 跨会话 |
|---|---|---|---|
| 会话持久化 | 对话原文 | 逐字 | 恢复后原样续聊 |
| 技能 | 怎么做某类事 | 说明书 | 显式加载才生效 |
| 持久记忆 | 关于用户与项目的事实 | 一句话一条 | 自动挑选、自动注入 |

三者互补而不重叠：会话管"这次聊过什么"，技能管"这类事怎么做"，记忆管"你是谁、这个项目是什么规矩"。记忆的独特之处在于**自动性**——用户不需要说"记住这个"，也不需要在下次会话里"加载记忆"，挑选与注入全程无声。

## 一次完整运行的流转

**第一次会话。** 用户说："以后都用这个编辑器给我改代码，另外回复里别用表情符号。"

1. 模型正常回答"好的"。这一轮以模型收尾文本结束，但此刻还没抽取——抽取发生在下一次模型调用前。
2. 用户接着问了一个代码问题。内核准备请求模型，记忆钩子先被触发：上下文最后一条是模型的收尾回复，上一轮落幕，水位线推进，开始抽取。
3. 一次轻量模型调用读入"上一轮的用户输入 + 模型回复"，返回两行格式化输出：一条用户偏好（编辑器），一条反馈（不要表情符号）。逐行校验通过，写成两个记忆文件，索引追加两行，控制台各打一行"已保存"。
4. 抽取完接着注入：读索引，拿当前问题挑相关记忆——此刻刚写的两条与代码问题不太相关，挑不出来，系统提示词保持基础版本。模型正常回答代码问题。
5. 会话结束。磁盘上留下两个记忆文件和两行索引，程序退出，上下文随之消失——但事实已经沉淀。

**第二次会话（重启程序）。** 用户问："我之前说过喜欢用什么编辑器来着？"

1. 启动横幅显示"已存在 2 条记忆"。
2. 内核准备请求模型，钩子触发：最后一条不是模型收尾回复（是刚进来的用户输入），不抽取；接着注入——读索引，把索引全文和这个问题一起交给轻量模型，返回一条相关记忆名。
3. 按名称读出正文，截断拼接，系统提示词在基础版本之后多出一段"相关记忆"，里面写着用户偏好哪个编辑器。
4. 主模型读到系统提示词里的这段记忆，直接答出正确答案，仿佛它从来没忘过。
5. 用户中途输入查看命令，索引全文与条数被打印出来，可以人工核对、随手改掉不准确的措辞。

## 设计取舍

**为什么用一堆文件而不是数据库？** 因为这个教学项目里，可读性、可改性、零依赖比检索性能重要得多。文件形式让人能直接打开检查模型"记了什么、记得对不对"，这对建立对记忆系统的信任至关重要；换数据库则立刻引入连接、迁移、备份一整套负担。代价是检索只能靠"模型读索引"这种语义方式，记忆库大到几千条时索引本身都会变长，届时需要向量检索或分片索引——但那是规模问题，不是现在的问题。

**为什么写入靠模型抽取，而不是用户显式说"记住这个"？** 显式指令最精确，但要求用户时刻记得"教"智能体，而绝大多数有价值的信息（随口提到的偏好、纠正时的语气）都是在自然对话里流失的。自动抽取的代价是可能记错、记偏——所以格式校验、宁缺毋滥、抽取开关、以及"人工随时可改"的文件形式，都是为这个代价准备的补偿。

**为什么每轮注入而不是会话开始一次性注入？** 一次性注入要么把全部记忆塞进去（上下文爆炸），要么凭开场第一句话猜相关度（话题一切换就失效）。逐轮注入让记忆跟随话题走，代价是每轮多一次轻量模型调用——用"同一输入跳过"的短路，把这份代价压到"每个新问题一次"。

**为什么抽取用固定格式行，而不让模型自由发挥？** 自由发挥的输出里会混着解释、标题、多余标点，解析极脆弱。固定行格式把"模型输出"约束成可逐行校验的记录，不符合格式的行直接扔掉，坏数据进不了磁盘。这是"让模型干活，但用格式卡住它的产出"的典型手法，模块 12 的错误分类会再次用到同样的思路。

**与上下文压缩（模块 06）的分工。** 压缩是会话内的应急：历史太长时把旧对话折叠成摘要，保的是"这次任务的连续性"；记忆是会话间的沉淀：把事实提炼成小文件，保的是"跨次任务的连续性"。两者操作的层次不同，因此互不冲突——一个管上下文里的，一个管上下文外的。

## 在整个项目中的位置

相对模块 10，11 是钩子契约的第一个深度用户：它同时用"模型调用前"这一个挂载点完成了两件方向相反的事（读——注入；写——抽取），并示范了有状态能力如何跨多轮调用维持水位线等内部状态。

往前看，它补上了智能体"经验"维度上缺失的一环：06 让上下文装得下长任务，09/10 让行为可控，而 11 让智能体在一次次会话之间"越用越懂你"。它也为后续模块埋了伏笔——模块 15 的系统提示词工程把"提示词的动态组装"变成一门显式学问，逐轮注入相关记忆正是最典型的动态组装；模块 19 的自主智能体要在无人干预下长时间运行，没有持久记忆就无法积累经验；而"什么时候该记、记多少"的克制原则，本质上与模块 06 的压缩共享同一套上下文经济学。
