# 模块 10：钩子系统

> 把控制权开放给使用者：智能体生命周期的关键节点上预留挂载点，任何人都能把自己的逻辑挂进去。

## 这个模块要解决什么问题

模块 09 的权限闸门很好用，但它暴露了一个更深的问题：那次改造是把"执行前检查"这种逻辑**焊死在权限这一个场景里**。用起来很快就会发现，想在工具执行前后做的事远不止权限一种——

- 想知道智能体每一步到底调了什么工具、传了什么参数（排查问题时无从下手）；
- 想在某个工具返回超长结果时收到告警（上下文要被撑爆了）；
- 想统计每轮对话用了多少次工具（评估与调优的基本数据）；
- 想在工具执行后做清理、埋点、限流……

如果每一种都照 09 的方式做一遍，就得一次次修改循环本体，改到最后内核变成一堆互不相干的分支判断。这个模块要做的，是把 09 里"执行前检查"这个偶然事件**上升为一种机制**：内核在生命周期的固定节点上预留挂载点，自己不再实现任何具体检查；谁想在什么时机做什么事，注册一个钩子就行。权限从此只是钩子的众多用途之一。

## 核心思想

**内核提供时机，使用者提供逻辑；内核不知道钩子里写了什么，钩子也不需要读懂内核。**

这个模块的价值不在那四个示例钩子本身，而在挂载点这套契约：

1. **挂载点固定，逻辑可插拔。** 循环在哪些时刻"停下来问一圈"是写死的、可预期的；每个时刻上挂了什么、做多少事，完全由使用者决定。
2. **返回值就是控制权。** 绝大多数挂载点上，钩子的返回值有明确语义——"工具执行前"返回非空即拦截，"模型调用前"返回一份新上下文即替换。于是钩子不只是旁观者，它能真正干预主流程，但干预方式被契约约束在一个极小的、可推理的面上。
3. **多个钩子互不感知。** 审计钩子不知道有护栏钩子，护栏钩子也不知道自己会被谁覆盖。它们只在挂载点上按注册顺序依次被问到，顺序就是全部的协作协议。

## 工作原理

### 一、生命周期上的四个挂载点

内核在智能体循环的四个固定时刻，向所有已注册能力依次分发事件。钩子默认什么都不做，能力只覆盖自己关心的点：

```
 用户输入 ──► ┌────────────────────────────────────────────┐
             │ ① 模型调用前（含工具循环里的每一轮）            │
             │    可返回新上下文整体替换（压缩/注入类能力的入口）│
             │            ▼                                │
             │      请求模型 ──► ② 模型响应后                 │
             │                   只读：结束原因、用量统计       │
             │            ▼                                │
             │  有工具调用？                                 │
             │   ├─ 是 ─► ③ 工具执行前（一票否决：非空即拦截）  │
             │   │            ▼                            │
             │   │        真实执行 ──► ④ 工具执行后（只旁观）   │
             │   │            ▼                            │
             │   │        结果回灌，回到 ① 进入下一轮          │
             │   └─ 否 ─► 本轮结束                           │
             └────────────────────────────────────────────┘
```

四个点的"权力"刻意不同：

| 挂载点 | 时机 | 权力 | 典型使用者 |
|---|---|---|---|
| 模型调用前 | 每次请求模型之前（含工具循环的每一轮） | 可整体替换上下文，内核同步保留 | 上下文压缩（06）、记忆注入（11） |
| 模型响应后 | 回复到达、消息入库之前 | 只读：结束原因、用量 | 轮次统计、旁路记录 |
| 工具执行前 | 每个工具调用真正执行之前 | 一票否决：返回非空即拦截 | 权限闸门（09）、危险命令护栏 |
| 工具执行后 | 工具执行完成之后 | 只读：工具名与最终回灌的结果 | 审计日志、长输出告警、计数 |

其中两点值得展开：

- **模型调用前是权力最大的点。** 钩子拿到完整上下文，原样返回表示不改；返回一份新列表，内核就用自己的消息列表整体替换——后续每一轮都基于改过的版本，而不是只影响当次调用。上下文手术类能力全靠它。
- **工具执行后连被拦截的调用也会触发。** 此刻钩子拿到的是拦截文本——审计钩子因此能完整记录"模型想做什么、实际发生了什么"，包括被拦下的那一次。如果被拦截的调用不留痕，事后排查"模型为什么反复尝试危险命令"时就缺了关键一环。

### 二、四个示例钩子：四种典型姿势

模块自带的四个钩子，恰好示范了挂载点的四种典型用法：

| 钩子 | 挂载点 | 权力 | 作用 |
|---|---|---|---|
| 危险命令护栏 | 工具执行前 | 拦截 | 命中危险命令模式（递归强删、提权、格式化盘符）即拦截，拦截说明回灌给模型 |
| 审计日志 | 工具执行前 + 后 | 只读 | 打印每次调用的工具名与参数、结果；内容过长只截取前 80 字符 |
| 长输出告警 | 工具执行后 | 只读 | 结果超过 4000 字符时告警，提示上下文面临膨胀 |
| 轮次统计 | 工具执行后 + 模型响应后 | 只读 | 每次工具调用后计数；回复以非工具调用收尾即视为本轮结束，打印总数并清零 |

四个钩子展示了同一契约下的四种姿态：**拦截**（改变主流程走向）、**记录**（完整旁路，永不干预）、**告警**（只提示不处理，真正的截断交给压缩类能力）、**统计**（跨事件维持一个计数器，在合适的时机输出并复位）。

轮次统计的实现细节值得一看：它怎么知道"一轮"结束了？答案是挂在模型响应后这个点上看结束原因——只要回复不是以"还有工具调用要执行"收尾，工具循环就到头了，此刻把累积的计数打印出来并清零。一个跨多个事件点的有状态钩子，就这样用两个只读挂载点拼了出来。

还有一个反直觉的细节：护栏钩子审查的是**整段参数文本**，而不是从中抽出命令字段再匹配。这比模块 09 的做法粗糙——参数里任何位置出现危险写法都会命中，可能误伤——但它换来的是零解析成本。同一类需求，粗糙而便宜的实现和精细而昂贵的实现可以共存，取决于你愿意为准确性付多少复杂度。

### 三、钩子只是能力的五条通道之一

把钩子放回能力契约的全景里看会更清楚。一个能力包可以向内核表达自己的途径有五条：注册新工具、注册钩子、注册斜杠命令、贡献系统提示词片段、以及感知生命周期（装配完成的启动回调、关闭时的清理回调）。

本模块的能力刻意只用其中一条——注册钩子，外加一段提示词片段。它不新增任何工具、不注册任何命令，却切实改变了智能体每一次工具调用的命运。这种"纯粹性"正是本模块的示范意义：工具扩展的是智能体**能做什么**，钩子约束的是智能体**做的时候会发生什么**，两条通道互相独立。

### 四、钩子之间如何共存

同一个挂载点上可能有多个钩子，规则只有两条：

1. **执行顺序 = 能力注册顺序**，能力内部再按其声明的钩子顺序。先注册的先被问到。
2. **工具执行前挂载点上，第一个非空返回值短路**——后面的钩子不再被询问，这次调用已经注定被拦截。

于是共存的语义可以预测：护栏钩子先注册，它就能在审计钩子之前拦下危险命令（审计在"前"挂载点上根本不会被问到）；而审计钩子无论排在第几，都能在工具执行后看到真实回灌的结果。钩子之间不需要知道彼此存在，也不需要互相调用——想要"先拦后记"的搭配，靠注册顺序就能拼出来。

### 五、超时与失败：契约信任钩子，内核不做隔离

这是必须如实交代的一面：当前实现里，钩子调用**没有超时保护，也没有异常隔离**。一个钩子若陷入死循环，主循环就停在那里；一个钩子抛出异常，会一路穿透循环本体，直接终止本次会话。

这不是疏忽，而是一种取舍：钩子是使用者自己写的代码，与智能体同进程、同信任级别，内核若为每个钩子包一层超时与捕获，调用路径会变得复杂，而钩子里最常见的错误（打印格式、空引用）本来就该在钩子自己的测试里暴露。代价也很清楚——第三方提供的钩子不可信时，这层契约是裸奔的。若要加固，大致是三件事：

- 给单个钩子设超时上限，超时按"未表态"处理（放行）并记录在案；
- 异常捕获后降级为一条告警，不让钩子的错误中断主循环；
- 提供一个开关，让使用者决定"钩子失败时放行还是拦截"——安全类钩子应当默认拦截。

这三件事都属于后续工程化改造的明确缺口，本模块只负责把缺口标出来。

### 六、给后续模块写钩子的三步

这个模块实际是一份给后面所有模块的"接入手册"：

1. **选时机**：想改上下文 → 模型调用前；想拦动作 → 工具执行前；只想看看 → 模型响应后或工具执行后。
2. **定权力**：能改主流程的只有两个点，其余一律只读。克制是钩子的美德——能用只读解决的，不要抢否决权。
3. **守顺序**：需要"先拦后记"之类的搭配时，靠注册顺序保证，而不是让钩子互相调用。
4. **留退路**：契约没有隔离层——写钩子的人要自己保证它不抛异常、不死循环，因为它和主循环活在同一个进程里。

### 七、如何验证这套钩子

| 对它说 | 期望 |
|---|---|
| 执行递归强删命令 | 护栏钩子拦截，审计钩子留下被拦记录 |
| 列出当前目录所有文件 | 审计钩子打前后两条记录，末尾统计本轮工具调用次数 |
| 读取一个很大的文件 | 长输出告警钩子提示结果超限 |

## 一次完整运行的流转

用户输入："列出当前目录所有文件，再读一下其中最大的那个。"

1. 内核发起模型调用前，先向所有能力的钩子问了一圈模型调用前挂载点——本模块四个钩子都没挂这个点，上下文原样通过。
2. 模型回复一次工具调用：列目录。内核先走工具执行前挂载点：危险命令护栏一看不是命令执行工具，放行；审计钩子打印一行灰色审计记录（工具名 + 截断后的参数），同样放行。
3. 工具真正执行，结果是一份很长的文件清单。工具执行后挂载点依次触发：审计钩子打印后置记录（工具名 + 结果前 80 字符）；长输出告警钩子发现结果超过 4000 字符，打印一条黄色告警；轮次统计钩子把计数加到 1。
4. 结果回灌，模型读到清单，挑出最大的文件，第二次发起调用：读文件。审计钩子再次记录前后两条，计数加到 2。
5. 模型读完内容，给出纯文本总结，结束原因不再是"有工具调用"。响应后挂载点上，轮次统计钩子看到本轮结束，打印"本轮结束，共执行 2 次工具调用"并清零。
6. 换一个用户输入："执行一下强制清理脚本。" 模型发起命令执行调用，参数命中危险命令模式。这次工具执行前挂载点上，护栏钩子返回非空拦截文本，短路——审计钩子在这一轮的前置记录上根本没被问到。真实执行被跳过，拦截说明作为结果回灌；工具执行后挂载点依然触发，审计钩子如实在案：这条命令被拦了，模型收到了什么。模型随即改用安全的等价操作。

## 设计取舍

**为什么删掉自建的事件框架？** 这个模块的早期版本自建了一整套事件机制：四类事件枚举、回调接口、注册表，语义与内核的钩子契约几乎完全重叠。能力化改造时把它整个删了，示例钩子直接实现内核契约。教训很实在：当内核已经提供了挂载点，能力包里再造一套平行机制，只会让同一个拦截动作有两套注册方式、两套顺序规则。扩展点应该只有一个。

**为什么工具执行后连被拦截的调用也触发？** 因为"执行后"的语义被定义为"拿到实际回灌给模型的文本"。审计最重要的价值恰恰在异常路径上：被拦截的调用若不留痕，"模型为什么反复尝试危险命令"就永远查不清。代价是钩子作者必须自己判断结果文本是不是拦截说明——契约没有额外标记。

**为什么长输出只告警、不截断？** 因为截断是破坏性操作，该不该截、截多少、要不要先落盘，取决于场景；而告警是无损的。把"发现问题的钩子"和"解决问题的能力"分开，钩子保持简单，决策留给专门的压缩能力。这也是模块 06 与钩子系统的分工边界。

**为什么护栏钩子不问用户、直接拦？** 模块 09 的第三关会停下来问人，这里的护栏却是一拦到底。因为钩子的职责是"表达一条硬规则"——命中即拦截，干脆利落；要不要引入交互式确认，是权限能力的事。同一个挂载点上，"硬规则"和"软确认"是两种可以各自成包的策略，不必揉在一个钩子里。

**为什么不给钩子加超时与异常隔离？** 参见工作原理第五节：同进程、同信任级别的前提下，隔离层收益有限、复杂度不低。这个决定在"钩子都由自己人写"时是对的；一旦钩子来自第三方（外部插件、用户脚本），就必须补上——这也是模块 13 引入外部工具协议前必须想清楚的问题。

## 在整个项目中的位置

相对模块 09，10 完成了一次关键抽象：09 证明"执行前检查"有价值，10 把它从权限专属推广为通用扩展点。内核循环从此定型——它只在四个固定时刻分发事件，不再为任何具体特性改代码。

往前看，这个契约就是后面所有"行为类"能力的地基：模块 11 的持久记忆靠"模型调用前"挂载点完成逐轮注入与抽取；模块 06 的上下文压缩走的也是同一个点；模块 24 的可观测与统计，本质上是一组更精致的审计与轮次统计钩子。而钩子"无隔离"的缺口，则与模块 13（外部工具接入）和模块 23（沙箱）形成呼应——当挂进来的不再是自己写的代码，信任模型就必须重新设计。
