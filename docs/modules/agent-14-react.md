# 模块 14：ReAct 推理模式

> 让模型的推理过程从黑盒搬到台面上——用一条严格的格式约束，把"先想清楚、再动手、看结果、再想"的循环变成肉眼可见的文本，而不是只留下一次来路不明的工具调用。

## 这个模块要解决什么问题

前十二个模块里，模型的"思考"是**不可见**的。观察一次正常的工具调用：上一条消息还是用户的提问，下一条消息就是一条工具调用——为什么挑这个工具、为什么传这些参数、为什么此刻不动手，全发生在模型内部，开发者只能看结果倒推原因。会话出问题时（调错工具、传错参数、过早收工），没有推理现场可查。

更深一层：**结构化工具调用是模型端点的增值能力，不是天生权利**。有的模型端点不支持它，有的支持得不稳定。如果智能体的整套执行机制都押在"端点必须能返回结构化调用"上，可用面就被卡死了。

还有一层属于"使用体验"：调试会话时，开发者最想问的问题不是"它调了什么工具"（日志里有），而是"**它当时为什么这么调**"。这个问题在旧体系里没有答案——推理没有留下任何痕迹，事后只能靠猜。要回答它，要么在模型服务端内部想办法，要么就让模型把理由说出来。前者不可控，后者就是本模块。

ReAct（Reasoning + Acting，推理-行动）是针对这两个问题的经典答案：要求模型在每次行动**之前**，先用规定格式的文字写出"我打算怎么做"，然后才行动；行动结果（观察）回灌后，再进入下一轮思考。本模块把它引入项目，并回答一个关键设计问题：**推理显式化应该怎么落地，才不牺牲现有执行通道的可靠性。**

## 核心思想

四句话：

1. **推理-行动-观察是一个循环，不是一个功能**。思考决定行动，行动产生观察，观察喂养下一轮思考；直到某一轮模型判断"不用工具了"，用自然语言作答收尾。
2. **在本项目里，ReAct 不是另一套主循环，而是一条提示词约束**。内核的工具循环一行没改：思考写在模型回复的文本部分（人看得见），行动仍走原生的结构化工具调用通道（机器解析可靠）。推理的"显式"与执行的"结构化"各取其长。
3. **格式即契约**。既然要把思考文本当作可读、可依赖的输出，格式就必须钉死：三行固定写法、一串明令禁止的错误写法、一个工具名白名单、一条"观察永远由系统给出"的铁律。
4. **一行开关，两种人格**。一个布尔开关决定系统提示词走 ReAct 版还是普通版；关掉后智能体退回"直接调用工具、少说话多干活"的默认形态。

```
             ┌──────────────────────────────────────────┐
             │ 用户问题                                   │
             └───────────────┬──────────────────────────┘
                             ▼
        ┌───► 模型回复 = 文本部分 + （若需要）工具调用
        │         │                    │
        │    文本部分：             工具调用：走结构化通道
        │    "思考 + 行动声明"           │
        │    （逐字打印给用户看）          ▼
        │                          执行工具
        │                              │
        │                              ▼
        │        观察（工具结果）作为工具结果消息回灌上下文
        │                              │
        └──────────────────────────────┘
                        │  直到模型不再发起工具调用
                        ▼
              纯文本作答（回复中不允许再出现格式关键字）
```

## 工作原理

### 1. 显式推理循环：每轮发生了什么

开启 ReAct 后，模型被要求：**需要用工具的那一轮，回复的文本部分只能是一组固定三行**——第一行是思考（当前处境分析、为什么选这个工具），第二行是行动（工具名），第三行是行动参数（结构化数据）。输出完这三行，模型**必须停**，等系统执行工具、把观察回灌，才能继续。观察到手后，模型基于它写下一轮思考：继续行动，或者宣布"信息够了"转入纯文本作答。

关键在于**思考与工具调用如何交织**：在同一次模型响应里，文本块（思考与行动声明）和工具调用块是并存的两个部分。内核照常把文本打印出来、照常执行工具调用、照常把结果回灌、照常判断要不要继续循环——主循环对"文本里写了思考"这件事完全无感。于是推理链有了两个去处：屏幕上实时展示给用户；消息历史里持久化保存，会话恢复后整条推理链依然在。

也就是说，模型实际"想"的内部过程我们依然看不见（那是权重里的事），ReAct 强制的是**一份对外的、成文的自我陈述**。它的价值不在"还原真相"，而在逼模型在行动前把计划落成文字——落成文字这个动作本身，就能筛掉大量冲动调用。

### 2. 格式契约的工程化：为什么提示词这么长

这个模块的系统提示词里有一大段"反例清单"，逐条列出会破坏格式的写法：用尖括号把行动包起来、用加粗或反引号或代码块包裹、用了中文冒号、冒号后少了空格、一次回复里塞了多组三行、**自己编造观察结果**。这不是啰嗦，是必要的工程措施：

- **格式漂移的下游是解析风险**。哪怕执行走结构化通道，思考文本若格式散乱，一切"想基于思考文本做事"的后续（展示、审计、甚至未来切回纯文本解析模式）都会变脆。
- **模型有强烈的"礼貌性补全"倾向**：它会自作主张替系统把"观察：结果如下……"也写出来。自己编的观察等于**用想象代替现实**，是这类循环里最危险的失败模式，所以提示词把它单列为头号禁令。
- **工具名白名单**。提示词末尾把当前注册的工具名列成一串，并声明"行动一栏只能从这个集合里选"。没有白名单，模型会臆造一个听起来合理的工具名，然后在执行期吃到"工具不存在"。还有一个容易忽视的联动：思考文本里**禁止出现这些格式关键字**的前提是"不需要工具的时候"——纯作答的轮次若还蹦出"思考：……"，用户会误以为后面还有行动。
- **缺参数就问，不硬调**。提示词要求模型在缺少必要参数时直接向用户提问，而不是拿想象中的值填进去。这把"问用户"变成循环里的一种合法出路。

### 3. 与"直接调用工具"的区别与代价

把同一道题分别用两种模式跑一遍，差异立刻可见：

| 维度 | 直接调用（普通模式） | ReAct 模式 |
|---|---|---|
| 决策过程 | 不可见，只有调用结果 | 成文展示，可审计可复盘 |
| 调用前置检查 | 依赖模型自觉 | 被迫先写"为什么调它" |
| 输出长度 | 短 | 每轮多出一段思考文本 |
| 复杂任务表现 | 容易一步错步步错 | 边走边校准，纠错更早 |
| 简单任务表现 | 干净利落 | 略显啰嗦 |
| 对端点的依赖 | 需要结构化工具调用能力 | 执行同样依赖，但推理部分只需要文本能力 |

代价是真实的：**每轮多产出的思考文本都要计入输出开销**，任务越长、轮次越多，这笔账越大；格式纪律偶尔会让模型"为了格式而格式"，在明明可以直接回答的地方也挤出三行。所以开关才重要——它不是缺陷开关，是场景开关。

还有一处有趣的张力：内核默认会在系统提示词末尾追加一句环境提示，鼓励模型"**优先直接行动，少解释**"；而 ReAct 提示词要求"**行动前必须先解释**"。两条指令字面冲突。本模块选择让 ReAct 提示词占据主体、环境提示作为补充共存——教学场景里推理可见性优先；真要追求效率时，关掉开关即可。

### 4. 提示词由能力包自持，工具清单动态注入

ReAct 相关的一切都收在一个能力包里：模式开关、两版系统提示词的构建、启动横幅的描述。装配时把当前工具表交给它，提示词里的"可用工具"一节和工具名白名单都是**现场生成**的——将来往智能体里注册新能力（哪怕是从模块 13 接来的远端工具），清单和白名单自动跟上，不需要改任何提示词文本。

关闭开关时，能力包贡献的是另一版朴素提示词：工具清单加工作目录，外加"需要就用，直接调用"的一句话。两版切换的成本为零，因为它们只是两段不同的文本。

### 5. 错误也是观察：失败如何回到循环里

真实运行中工具会失败：文件不存在、命令打错、远端超时。本模块沿用项目的一贯纪律——**错误不抛出、不中断，转成一句错误文本作为观察回灌**。这在推理-行动-观察的框架里格外顺理成章：失败本身就是一条观察，模型在下一轮思考里读到它，可以纠正参数重试、换一个工具、或者承认此路不通并向用户求助。

对比一下没有这套机制的世界：一次工具失败直接把回合炸掉，用户看到的是堆栈而不是解释。而在这里，失败被消化成推理链上的一个节点——回看会话记录时，"哪一步失败了、模型当时怎么想的、之后怎么绕开的"完整可见。提示词里"工具执行出错时向用户说明情况并寻求帮助"这条工作流约定，给模型的兜底动作也划了界：不许在失败后死循环重试。

### 6. 终止条件：循环怎么停、停错了怎么办

循环的退出判据只有一条：**本轮模型没有发起任何工具调用**。所以"宣布完成"的动作权完全在模型手里——它判断信息够了，就用纯文本作答，循环自然收尾。为了让这个判据可靠，提示词从正反两面夹击：需要工具时必须输出三行（不许只说不做），不需要时必须干净作答（不许再出现格式关键字）。两头都钉死，"停"这个动作就没有歧义。

另外有一类**非正常停止**会被单独盯防：回复因长度上限被截断时，思考文本可能写了一半、工具调用可能残缺。内核对这种情况有专门的告警——截断的回复会被明确提示，而不是静默吞掉后让循环空转。在推理显式化的模式下这件事更常见（思考文本本身就占输出额度），一条显眼的警告能省掉大量"为什么它停了"的困惑。

### 7. 主循环为什么一行不用改

这是本模块在架构上最值得记的一笔。老式做法是把 ReAct 做成执行层分支：模型只输出纯文本，智能体用正则表达式从文本里抠出工具名和参数，执行后把观察伪装成一条用户消息塞回历史。这条路线要处理解析失败、要放弃原生的并行工具调用、要伪装消息角色，且工具定义根本不发给端点（模型只能靠提示词里的描述猜参数格式）。

本模块的路线是：**约束交给提示词，执行交给原生通道**。格式约束保证推理可见，结构化通道保证调用可靠，内核的循环条件（是否还有待执行的工具调用）、工具结果的回灌方式、会话的持久化全部沿用。ReAct 从"另一种执行引擎"降维成"一段提示词"，复杂度消失，兼容性拉满。

### 8. 与模型内建"思考"能力的区别

还有一个容易混淆的概念要撇清：不少模型端点自带"思考"机制（推理阶段在内部进行，正文之外产出思考内容，由请求参数开关控制）。它和本模块的 ReAct 不是一回事，尽管产品形态相似：

| | 端点内建思考 | ReAct 显式推理 |
|---|---|---|
| 归属 | 模型服务的内部机制 | 提示词层面的输出纪律 |
| 开关 | 请求参数 | 系统提示词 |
| 内容归属 | 常被单独标记、回传受限 | 就是普通回复文本，谁来都一样 |
| 依赖 | 只有部分端点支持 | 任何能生成文本的端点都能跑 |
| 可控性 | 格式与深度由服务端定 | 三行格式、工具白名单都由提示词定 |

本模块选择后者，正是因为它**不挑端点**：思考写在回复文本里，是协议最基础的能力。两者并不互斥——端点开了内建思考，ReAct 的三行约束照样生效，一个管"想得多深"，一个管"说出来什么形状"。

## 一次完整运行的流转

用户："帮我分析这个项目的代码质量，给出改进建议。"

1. **第一轮**。回复文本："思考：这是一个需要摸底的任务，先看项目里有哪些源码文件，应使用列目录工具。行动：列目录。参数：当前目录。"同时一条结构化调用发往列目录工具。控制台逐行打出思考与行动声明，随后是执行与结果——观察回灌：文件清单。
2. **第二轮**。"思考：清单里有核心实现文件，先从入口文件看起，评估结构与命名。"行动指向读文件工具。观察：几百行源码。
3. **第三轮**。"思考：逐个读太慢，改用内容搜索统计各类问题的分布。"行动换成内容搜索工具，参数带上了模式与目录。观察：命中统计。
4. **第四轮**。模型判断信息已足够，输出的是一段**不带任何格式关键字**的纯文本报告：哪些文件缺注释、哪些复杂度偏高、建议怎么改。主循环看到本轮没有待执行的工具调用，回合结束。
5. **对照组**。把开关拨到普通模式再跑同一问题：第一轮直接是一条工具调用，没有那三行——同样的工具、同样的结果，少了整条可见的推理链，也少了三分之一的输出文本。

这场戏的要点：循环的骨架（调用-结果-继续）与模块 01 完全相同；改变的只是模型每一轮"开口说的第一句话"。推理显式化不是加了新机器，而是加了**纪律**。

顺带一个选用建议：**什么时候值得开**。任务需要三步以上、步骤之间有依赖、或者事后要向别人解释"它为什么这么做"——这三种场景开 ReAct 几乎稳赚；一次性问答、单步操作、对延迟和成本敏感的高频调用——关掉，让智能体回到"少说话多干活"。

## 设计取舍

- **提示词约束 vs 自建文本解析引擎**。纯文本加正则的路线证明了"不依赖端点能力也能跑工具"，但要自己写解析器、自己扛解析失败、还要放弃原生通道的参数校验与并行调用。本模块选了"约束归提示词、执行归通道"，把 ReAct 的收益（可见、有序、自检）留下，把它的成本（解析器）扔掉。代价是执行仍然依赖结构化能力——这个依赖被模块 18 的协议兼容层继续消化。
- **强制格式 vs 自然表达**。放开格式，思考会更自然，但也更难被程序与读者稳定地"读"。教学项目宁可让模型戴着镣铐跳舞，也要保证每一轮的思考结构一致——这是一笔用表达力换确定性的交易。
- **一轮一组 vs 一轮多组**。一次回复塞多组"思考-行动-参数"看似高效，实则破坏了"行动之间必须经过观察"的因果链——后面的行动是在**没有看到前面行动结果**的情况下做出的。强制一轮一组，把"每一步都踩在现实上"变成硬规则。
- **观察必须由系统供给**。允许模型自己填观察，等于允许它跳过现实直接写小说。这条禁令没有技术上的折中，只有执行上的死守。
- **保留环境提示的"少解释" vs 删掉它**。字面冲突的指令可以共存，因为二者的作用域不同：环境提示约束整体姿态（别光说不练），ReAct 约束工具轮次的输出形状（练之前说清楚）。保留冲突本身也是一个教学点——提示词工程里，指令间的张力需要人来裁决优先级。
- **默认开 vs 默认关**。默认开，因为这是教学模块，推理可见性就是产品本身；生产场景的默认应该是关——那里要的是速度与成本。
- **思考文本留在历史里 vs 随压缩淘汰**。成文的思考会话话累积，长任务的上下文很快被它撑大。模块 06 的压缩管线会把旧轮次的思考替换成占位——理由在这里得到了双份支撑：旧思考的信息价值衰减极快（当时的盘算已被后续行动兑现或否定），而且它是输出额度的大户。"推理要显式"针对的是**当下这一轮**的可观测，不等于"推理要永久保存"。
- **能力包只给提示 vs 顺带接管执行**。这个能力包本可以更进一步：拦截工具调用、按自己的节奏调度。但它没有——它连一个钩子都没注册，只交了两段提示词。克制的原因是本模块的教学主旨：证明"仅凭提示词就能改变智能体的推理形态"，一旦伸手去碰执行层，这个证明就不成立了。
- **观察回灌走协议原生消息 vs 伪装成用户消息**。老路线里观察被包装成"用户说的话"塞回历史——模型视角下，"用户"忽然开始替系统汇报工具结果，角色边界被搅浑，长对话里还会出现"谁在说话"的错乱。本模块的观察走的是协议为工具结果专设的消息形态：谁产的、回给哪次调用，一一对应，历史记录干净且可审计。

## 在整个项目中的位置

- **相对模块 13 新增了什么**：13 拓宽的是能力的**广度**（能用的工具更多了），14 改造的是推理的**透明度**（用工具之前怎么想，看得见了）。它还顺手立了一个范式：一个只贡献提示词、不注册工具、不挂钩子的能力包长什么样——能力体系里最轻的一种形态。
- **为后续铺了什么路**：
  - 模块 15 是它的直系续作：14 证明了"一段提示词足以改变智能体的行为方式"，15 紧接着追问"那提示词本身该怎么工程化地组织"，两者合起来是项目的提示词工程上下篇；
  - "先成文再行动"的纪律在模块 19 的自治运行与模块 25 的目标循环里会被反复调用——无人监督的长时运行，比任何时候都更需要留下的推理痕迹可供事后审计；
