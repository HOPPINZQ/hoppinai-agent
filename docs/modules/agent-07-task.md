# 模块 07：任务系统（依赖图）

> 把"计划"从聊天记录里搬出来，落成磁盘上一张带方向的任务依赖图：谁在等谁写得明明白白，完成一个任务自动解锁下游——压缩删不掉，重启丢不了，多个智能体还能共看同一块板。

## 这个模块要解决什么问题

模块 03 给过智能体一张待办清单，但它有三个先天不足，任务一大就全部暴露：

- **它是平的**。清单里的条目彼此独立，只有"完成/未完成"两态。而真实的目标有结构：先建数据库表，才能写用户模型；写完用户模型，才能加认证接口。平面清单回答不了三个调度上的致命问题——**现在能干哪个？哪个被卡住了？哪几个能同时干？**
- **它活在内存里**。模块 06 的压缩会把上下文重写成一段摘要，清单随手就没了；进程一重启更是无影无踪。计划比对话更值钱，却比对话更短命。
- **它只属于一个智能体**。两个智能体各持一份内存清单，谁也不知道对方干到哪了，撞车和漏活都不可避免。

模块 07 要做的，是把"计划"升级成一种**独立于对话、独立于进程、可被多方读写的外部结构**。

## 核心思想

四句话：

1. **任务 = 磁盘上的一个小文件**。工作目录下开辟一个专门的任务文件夹，一个任务一个文件；整个文件夹就是一块任务板。文件系统就是零依赖的共享数据库。
2. **依赖 = 任务之间的有向边**。每个任务带两个方向的关联："我在等谁"（前置任务）和"谁在等我"（下游任务）。所有任务和边拼起来，就是一张有向无环的**依赖图**。
3. **状态 = 三态流转**。待处理 → 进行中 → 已完成。"已完成"不只是打个勾，它会触发图的一次自动松绑。
4. **调度 = 一个极简判定**。一个任务"现在能不能干"，只看两件事：状态是待处理，且"我在等谁"是空的。就绪任务列表就是调度答案。

```
依赖图一例（用户要建一个带认证的接口服务）：

   #1 建数据库表 ──► #2 写用户模型 ──► #3 加认证接口 ──► #4 部署配置
   （已完成）        （就绪，可开工）     （被 #2 卡住）     （被 #3 卡住）

  #1 完成的那一刻，#2 的"我在等谁"被自动清空 → 状态灯变绿
```

## 工作原理

### 1. 任务长什么样，存在哪

每个任务文件记录一组结构化信息：任务标题、详细描述（要求与验收标准）、状态、前置任务列表、下游任务列表、所有者、创建时间、所属会话。

每个任务有一个完整的长编号，同时对外暴露一个**8 位短编号**。模型在对话里只需要用短号——管理器支持"前缀匹配"：给个短号就能定位到唯一的长编号任务。这是给模型省力气的贴心设计，短标识既好记又不容易抄错。

启动时管理器扫描任务文件夹，统计已有任务数量——上一次会话留下的任务板，这一次直接接着用。

### 2. 建图：创建时声明"我在等谁"

把大目标拆成任务，靠的是一批任务管理工具（创建、更新、列表、查看详情、认领、完成，共六项）。创建工具除了标题和描述，还接受一个**前置任务列表**——"这个任务要等哪些任务完成才能开始"。

依赖关系有两个录入时机：创建时直接声明，或者事后用更新工具补挂。无论哪种，都有一条保证图不乱的规则——**双向同步**：

- 给任务 A 声明"我等 B"，A 的前置列表里写入 B；
- 给任务 A 声明"我阻塞 C"，除了 C 的下游列表里写入 A，还会**自动**把 A 写进 C 的前置列表。

也就是说，无论模型从哪个方向描述这条边，磁盘上的图永远两个方向都对得上。模型不必理解双向簿记，说一遍人话就够了。

### 3. 解图：完成一个任务 = 松开一条边

三个状态构成一条单向流转的主干，每一步都有门槛：

```
   待处理 ──认领（核查前置已全部完成、登记所有者）──► 进行中
     ▲                                                  │
     │  依赖被解除后重新就绪（图上仍是待处理，只是可以开工了）  │
     │                                                  │
   （等待前置任务）                              完成（只有进行中能完成）
                                                        │
                                                        ▼
                                                     已完成
                                                        │
                                        自动清除依赖：从所有任务的前置
                                        列表里移除自己，下游随之解锁
```

状态流转有防呆：

- **认领**（开始干活）：只能认领待处理状态的任务；认领前会先核查全部前置任务是否真的已完成——没完成就拒绝，并**列出卡住它的具体是哪几个任务**。认领成功即登记所有者、状态转为进行中。这一步把"能开工"从模型的自觉变成了系统的检查。
- **完成**：只有进行中的任务能标记完成。完成的一瞬间触发依赖清理——**遍历任务文件夹里所有任务文件，把刚完成的这个编号从每个人的前置列表里移除**。

清理之外还有一层体贴：完成工具的返回结果会顺带扫一遍全局，把"因此被解锁的任务"直接列在结果里（"以下任务现在可以开始了"）。模型不用再发一次列表调用去确认，下一轮就知道该接哪个活。

### 4. 调度：谁能跑、谁并行

判定规则简单到可以一句话说完：**待处理 且 无未完成前置 = 就绪**。

- 列表工具每次输出的不只是一份清单，还有统计头（总计多少、待处理/进行中/已完成各多少）和一行**"可立即执行"的短编号名单**——相当于每次都给模型一张带高亮的看板；
- 彼此没有依赖路径的就绪任务，天然构成可并行的批次。本模块里智能体还只是"知道"它们可以并行（逐个做也行）；到模块 08 有了后台执行，这种并行才真正落地；
- 每一个写操作（创建、更新、认领、完成）的返回结果都**回带完整的任务板**。模型永远是在"看得见全局"的前提下做下一个决定，不会盲操作。

模型实际看到的任务板大致长这样（文字示意）：

```
总计: 5 │ 待处理: 3 │ 进行中: 1 │ 已完成: 1
[x] #1  解析源码               （已完成）
[>] #2  转换语法树  所有者: 我   （进行中）
[ ] #3  生成目标代码            （就绪）
[ ] #4  生成文档               （就绪）
[ ] #5  全量回归测试  被阻塞: #2, #3
可立即执行: #3, #4
```

一屏之内，模型能同时读到进度、卡点和下一步——这就是"看板"二字的含义。

### 5. 让模型真的会用：写在系统提示词里的工作法

工具有了，还得教会模型用。本模块向系统提示词注入了一段任务使用指南，核心是一套循环工作流：

```
接到目标 ──► 拆解成任务、声明依赖（建图）
        ──► 查看板，找出就绪任务
        ──► 取任务详情，弄清要求
        ──► 认领（状态 → 进行中）
        ──► 用文件/命令工具真正干活
        ──► 标记完成（自动解锁下游）
        ──► 回到查看板，循环
```

配套的策略提示包括：前置列表为空的优先做；无依赖的任务可并行；每完成一个就回看一次全局进度。这些"使用说明"和工具一起注入，是"结构化能力"能被模型稳定用起来的关键——**光给工具不给工作法，模型往往用两次就忘了**。

### 6. 为什么磁盘存储是这三件事的共同答案

回到开头的三个问题，同一个选择全部化解：

- **压缩删不掉**：任务板根本不在上下文里，压缩只重写对话，动不了文件。摘要里只需一句"任务板在磁盘上，可随时查看"。
- **重启丢不了**：新进程启动扫一遍文件夹，任务板原样回来，编号也能接着排。
- **多方可协作**：文件系统天然是共享介质。另一个智能体（甚至另一个人）打开同一个文件夹，就能看到同样的板、认领同样的任务。所有者字段就是为此准备的——谁认领了、谁在做，板上有名。

## 一次完整运行的流转

以剧本 s07 为例，用户说："构建一个包含用户认证、数据库和部署配置的接口服务。"

1. **拆解建图**。模型识别出这是一个有先后次序的多段工程，连续调用创建工具建立四个任务，并声明依赖链：建表（无前置）→ 用户模型（等 #1）→ 认证接口（等 #2）→ 部署配置（等 #3）。每次创建的返回结果里都带着整块任务板：#1 标着"就绪"，其余依次标着"被谁阻塞"。
2. **开工 #1**。模型查看详情确认要求，然后直接动手——用写文件工具创建了建表脚本，表结构里带上主键、唯一邮箱和密码散列字段。这期间它并没有显式地"认领"，但接下来的完成操作会走同样的状态检查。
3. **完成 #1**。模型调用完成工具。管理器把 #1 标成已完成，扫全图把 #1 从 #2 的前置列表里移除，并在返回结果里附上那句关键的话——"任务 #2 现在就绪了"，外加刷新后的完整任务板。
4. **接力**。模型下一轮看着板上的高亮，宣布"数据库模式已完成，开始实现用户模型"，工作流自然滚动到下一个节点。

换一个更能体现"图"价值的剧本：用户要求做一个"解析 → 转换与生成（可并行）→ 测试"的重构流水线。模型建 4 个任务，#2 与 #3 同时只等 #1、彼此无依赖，#4 等它们俩。#1 完成的瞬间，返回结果里的"解锁名单"一次性列出 #2 和 #3——图在一处汇流、一处分叉的形状被原样表达了出来。此刻智能体只能按顺序逐个做，但它**知道** #2 和 #3 是同一批次；到下一个模块有了后台执行，这批任务就能真正同时开跑。

整个过程里，模型从未在对话里"复述计划"——计划在磁盘上，对话里只有当下这步。哪怕此刻触发一次模块 06 的压缩、哪怕进程当场重启，这块板都毫发无损，任何新会话都能从"#2 就绪"接着干。

## 设计取舍

- **文件 vs 内存 vs 数据库**。内存快但崩溃即失、无法共享；数据库有并发保证但平白引入依赖与运维。选文件：崩溃可恢复、多方可读、人还能直接打开手工修——教学项目里"随处可用的零依赖持久层"胜过一切。
- **声明式依赖 vs 优先级 vs 中央调度**。高中低优先级表达不了"B 在 A 完成之前根本没法开始"这种硬约束；中央调度器能排顺序，却成了单点瓶颈，也堵死了多方自治。让每个任务自带依赖声明，任何智能体读一眼文件就知道自己能不能动工——调度权分散到了每一个参与者手里。
- **双向边 vs 单向边**。只存"我在等谁"查询下游时得全表扫；双向都存，查询任意方向都是直读。代价是写入时要维护两边一致——这个复杂度被收在管理器内部，模型与工具层面完全无感。
- **任务与待办并存**。任务系统承接了待办的心智模型，但更重：有持久化、有依赖、有所有者。两者不互相取代——短、线性、一次性的小事用待办更顺手；跨会话、有结构、要协作的工程用任务板。课程主线自本模块起切换到任务系统。
- **持久化不等于并发安全**。文件能落地，却防不了两个智能体同时写同一个文件互相覆盖。所以纪律仍然要靠约定：改状态前先重读、确认状态与依赖符合预期再写回。这条纪律在此处只是提醒，到多智能体模块会变成真正的机制。

## 在整个项目中的位置

- **相对模块 06 新增了什么**：06 回答"记忆怎么活得久"，07 回答"计划怎么活得比记忆更久"。它把智能体从"按对话即兴推进"升级为"按外部结构调度推进"——对话可以被压缩成一段摘要，工作进度却始终有据可查。同时它也是第一次把**状态写到对话之外**，为一切"跨会话、跨智能体"的功能打了地基。
- **为后续铺了什么路**：
  - 模块 08 直接消费它的产出：任务板上的"就绪任务/可并行批次"，正是后台执行的最佳调度依据；
  - 模块 09 的权限控制、模块 17 的多智能体团队，都靠这块共享任务板协调"谁做什么、做到哪了"；
  - 模块 11 的记忆、模块 16 的定时任务、模块 19 的自治循环，同样建立在"状态可以独立于对话存活"这条本模块确立的原则之上；
  - 依赖图判定"就绪"的思路，还会在模块 17 的任务依赖编排里原样复用。

最后补一笔它与模块 03 待办清单的承袭关系——同一棵心智模型上的两次升级：

| | 待办清单（模块 03） | 任务板（本模块） |
|---|---|---|
| 存在位置 | 内存、消息之外的管理器 | 磁盘上的任务文件夹 |
| 条目关系 | 平铺，互不相干 | 依赖图，有方向 |
| 状态 | 两态（未完成/已完成） | 三态流转，带所有者 |
| 能否回答"现在能干啥" | 不能 | 就绪名单直接给出 |
| 压缩 / 重启之后 | 压缩后仍在，重启即失 | 两者都不丢 |
| 适合的活 | 短、线性、一次性 | 跨会话、有结构、可协作 |
