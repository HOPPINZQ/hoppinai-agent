# 模块 21：综合集成

> 把前面二十个模块练出的所有机制——多工具、任务板、定时调度、队友协作、关停与审批协议、工作区隔离、外部工具服务器、权限闸门、上下文压缩、错误恢复——全部编织进同一个智能体循环。

## 这个模块要解决什么问题

前面的每个模块都在回答一个单独的问题：模块二回答"怎么加工具"，模块六回答"上下文满了怎么办"，模块九回答"危险操作要不要问人"，模块十六回答"怎么定时触发"，模块十七、十八回答"多个智能体怎么配合"，模块二十回答"并行干活怎么不打架"。

但每个模块都只是一个"器官"。真实世界的智能体是一台整机：同一个循环里，工具要管、任务要派、定时器要响、队友要回消息、上下文要压缩、危险命令要拦。器官各自正常，拼在一起却可能互相打架：

- 压缩机制把历史裁短了，可能正好裁掉队友刚发来的一条关键消息；
- 定时器在工具执行到一半时插入一条新指令，会把对话状态搅乱；
- 两个队友同时写同一个文件，改动互相覆盖；
- 二十七个工具同时塞给模型，工具描述本身就占掉一大块上下文。

这个模块要做的，就是把所有器官装进同一具身体，并回答那个真正困难的问题：**机制之间在什么时机介入，才不会互相踩脚。**

## 核心思想

一句话：**机制很多，循环一个。**

无论装了多少机制，底层的形状不变——用户说一句话，模型看一眼上下文和工具清单，决定是回话还是调工具，工具结果回灌，循环往复，直到模型不再要工具。所有新机制都只有三种进入方式：

1. **变成工具**：模型主动调用。任务板、定时登记、派队友、发消息、建工作区、连接外部服务器，全都是工具。循环本身对它们一无所知。
2. **变成挂载点上的钩子**：循环在固定时机"探头"问一句"有人要说话吗"。权限检查、压缩、统计，都挂在钩子上。
3. **变成常驻后台**：定时器的扫描线程、队友的运行线程，在循环之外自己转，产出通过队列、信箱回流到上下文。

内核对任何具体机制零感知。入口类像一个总装车间：把各个子系统造好，以单例的形式注入工具层，再把工具、钩子、命令、提示词片段一次性注册给内核，然后启动循环。

## 工作原理

### 1. 内核只提供四个介入时机

内核循环里固定埋了四个"探头"，顺序如下：

```
用户输入
   │
   ▼
请求模型前 ──── 钩子可以改写上下文（压缩在这里动手）
   │
   ▼
模型返回（带若干工具调用）
   │
   ▼
执行每个工具前 ─ 钩子可以拦截（返回非空即拦截，拦截文案代替工具结果）
   │
   ▼
工具执行
   │
   ▼
工具执行后 ──── 钩子可以观察结果（记录、统计、触发旁路动作）
   │
   ▼
模型响应处理完 ─ 钩子可以拿到用量与结束原因
   │
   ▼
回到"请求模型前"，直到模型不再要工具
```

这套设计的妙处在于：压缩类机制永远在"请求模型前"介入，权限类机制永远在"执行工具前"介入，谁也不会越界。能力以插件形式注册，注册时合并工具清单（重名工具直接跳过，后来者不覆盖先到者）、收集用户命令、拼接系统提示词片段。拔掉一个能力目录、删掉一行注册代码，机器照常运转。

### 2. 二十七个工具：一张工具表，七个子系统

入口把工具按子系统分组登记：

| 分组 | 数量 | 能做什么 |
|---|---|---|
| 基础 | 6 | 执行命令、读文件、写文件、编辑文件、列文件、内容搜索 |
| 定时 | 3 | 登记定时任务、列出定时任务、取消定时任务 |
| 团队 | 3 | 派出一个队友、发消息、查收件箱 |
| 协议 | 3 | 请求队友关停、请队友提交方案、审批方案 |
| 任务 | 5 | 建任务、列任务、查任务、认领任务、完成任务 |
| 工作区 | 3 | 创建独立工作副本、移除、保留 |
| 外部服务器 | 1 + 4 | 连接服务器，以及连接后可调用的四个外部工具 |

每个子系统都是一个独立对象，以单例形式"塞进"工具层——工具函数本身只是薄薄一层遥控器，按键之后真正干活的是任务管理器、调度器、信箱总线、工作区管理器。这样带来的直接好处是：**工具的数量可以膨胀，循环的代码一行不用改。**

### 3. 队友如何住在同一个进程里

派队友这个工具被调用时，并不启动新进程，而是在当前进程里起一条后台线程。每条队友线程拥有完全独立的三样东西：自己的消息历史、自己的系统提示词（简短得多，只交代身份和可用工具）、自己的一份工具清单——只有七件，基础文件工具加认领、完成、发消息，刻意比主控少二十件，防止队友自行再派队友形成失控的递归。

队友线程跑着自己的小循环：

```
轮询自己的信箱
   │
   ├─ 收到关停请求 → 回执一条确认消息 → 退出线程
   ├─ 收到方案审批结果 / 普通消息 → 作为新一轮用户输入注入
   │
   ▼
跑一轮模型调用 + 工具往返（单轮内最多十次工具往返）
   │
   ▼
没有新消息 → 睡眠半秒 → 回到轮询（全程设五十轮安全上限防死循环）
```

信箱不是内存队列，而是磁盘上的一个个小文件——每个成员一个文件，发消息就是往对方的文件里追加一行记录，读信箱就是把文件内容读出来然后清空。"读后即清"保证同一条消息不会被反复处理。用文件而不是内存，是为了能随时打开文件观察团队之间的通信内容，调试起来一目了然。

一个巧妙的细节：发消息工具需要知道"我是谁"。主控调用时署名主控，队友调用时署名队友自己的名字——实现方式是给每条队友线程打上线程身份标记，工具执行时取当前线程的标记作为署名。同一个工具，在不同线程里自动带上不同的发件人。

### 4. 任务板与工作区隔离的联动

任务板是一张共享清单，任务之间还能声明阻塞关系（某任务没完成前，被它阻塞的任务不算"就绪"）。任务的生命周期由状态机管着：待认领 → 进行中 → 已完成，认领动作会记录认领人，防止两个队友抢同一件活。

它和工作区隔离是这样咬合的：

```
主控：创建任务 A、任务 B
主控：为 A 建独立工作副本（版本控制系统开出独立分支 + 独立目录），并绑定到任务 A
主控：为 B 同理
主控：派出 alice、bob
        │
alice 认领任务 A ──► 查到任务 A 绑定了工作副本
        │                 │
        ▼                 ▼
把"当前线程的生效目录"切到 A 的副本目录
        │
        ▼
此后 alice 线程里所有文件与命令操作，都落在 A 的副本里
bob 线程同理落在 B 的副本里 —— 互不覆盖
```

"生效目录"是靠线程私有存储实现的：每个线程可以各自记住一个目录，工具执行时先看当前线程有没有自己的目录，有就用，没有就退回全局根目录。于是在同一个进程里，主控仍然在主仓库活动，两个队友各自在副本里干活，谁也不碰谁的文件。

### 5. 定时调度与外部工具的接入方式

定时子系统由两条后台线程组成：一条每秒扫一次当前时间，某个定时任务的时间表达式命中了，就把它的提示词放进等待队列；另一条盯着队列，等智能体空闲了才放行队头。之所以要等空闲，是因为工具执行到一半时插入新指令，会把进行中的对话状态搅乱。登记的任务可以是一次性的（触发一次即删除）或周期性的，也可以标记为"持久化"——写进磁盘，进程重启后自动恢复，并刻意清空上次触发时间，避免被"同一分钟不重复触发"的保护误伤。本模块把登记、查询、取消三个动作暴露成工具，让模型自己管理自己的日程；调度线程与注入通路的完整接线，在专门的定时模块里演示。

外部工具服务器走的是另一条路：连接动作本身是一个工具，模型说"帮我连上文档服务器"，连接成功后该服务器的工具就注册进工具索引。每个外部工具的名字都带上**来源前缀**——"来自哪个服务器、叫什么"——再做小写化之类的名字归一化。这是防冲突的关键：两个不同服务器各有一个叫"搜索"的工具时，前缀让它们互不覆盖。教学版的外部服务器是进程内模拟的（一个管文档查询，一个管部署触发），但接口形状与真实协议一致；工具描述里还标了"只读"或"破坏性"的注记，为权限层提供判断依据。

### 6. 防打架：机制之间的时序契约

所有机制挤进一个循环，靠的是几条明确的时序契约：

- **压缩不动"配对"**。裁剪历史时，绝不允许把"模型的工具调用"和它对应的"工具结果"拆散——要么一起留，要么一起裁。拆散了，下一次请求会因为出现"没有回应的调用"而被服务端直接拒绝。裁掉的中间历史用一句占位文本（"已省略若干条"）顶替，位置感不丢。压缩按成本从低到高排：先裁中间消息，再把旧的工具结果换成占位符，再把超大输出落盘留个路径，最后才动用一次模型调用来生成全文摘要；如果服务端已经报"上下文太长"，就直接触发紧急压缩。
- **权限三重闸门，各有分工**。第一道查黑名单（命中高危模式直接拒绝）；第二道查规则（路径越界等结构性违规）；第三道问人（破坏性操作弹出行确认，非交互环境保守拒绝）。任一道拒绝即短路。此外执行命令的工具内部还自带一份更朴素的底线黑名单、两分钟超时强杀、超长输出截断到五万字符——就算权限层被绕过，工具自己还有最后一道保险。
- **错误永远以文本回灌**。工具找不到、执行抛异常、输出为空，全部转成一句错误文本塞进上下文，循环不崩。模型看到错误，下一轮自己调整。
- **恢复包装包住模型调用**。输出被截断就自动提高上限续写；上下文溢出就触发紧急压缩；限流和瞬时报错就指数退避（等待时间翻倍加随机抖动，封顶三十二秒），连续多次过载后切换备用模型。三条路径各治一种病，互不干扰。
- **入口处装配好但不强行接线**。压缩器、恢复包装、权限闸门在入口里都构造了出来，但这个教学入口刻意不把它们硬塞进循环——内核的挂载点就摆在那里，把哪个对象接到哪个挂载点上，正是留给读者的动手练习。

## 一次完整运行的流转

用户说："创建两个任务，各自绑定一个独立工作副本，然后派 alice 和 bob 自主干活。"

1. 这句话作为用户消息进入上下文，发起第一次模型调用。
2. 模型看到二十七个工具，先调用建任务工具两次，再调用创建工作副本工具两次并分别绑定任务，最后调用派队友工具两次。
3. 每个工具调用在执行前经过内核的工具前钩子（本入口未挂权限钩子，直接放行；工具内部的黑名单与超时仍然生效）。执行结果逐条回灌。
4. 派队友的调用触发了两条后台线程。alice 和 bob 各自拥有小循环：轮询信箱、读任务板、发现就绪任务、认领。
5. alice 认领到任务一，线程的生效目录切到对应副本；她用读文件、编辑文件工具干活，所有改动落在副本目录里，主仓库毫发无伤。bob 同理。
6. 干完后各自调用完成任务工具、用发消息工具向主控汇报。汇报躺在主控的信箱文件里。
7. 主控这边，模型在下一轮调用了查收件箱工具，读到两条汇报，向用户总结："两个任务都完成了。"
8. 模型这一轮不再要工具，输出最终答复，循环等待下一条用户输入。后台的队友线程仍在轮询——直到被关停协议请走，或到达安全轮数上限自行下线。

整个过程里，主循环只跑了一条；定时器、队友、信箱、任务板都在旁边各自运转，通过工具调用和消息回流与主循环交换信息。

## 设计取舍

- **共享进程而不是多进程**。队友是线程不是进程，信箱是文件不是套接字。代价是隔离不彻底（一个队友崩溃可能影响全局），收益是调试直观、消息可肉眼审计，教学价值远大于工程纯洁性。
- **模拟外部服务器而不是接真实协议**。真实的协议栈要处理传输、握手、能力协商，会把注意力从"外部工具如何进入循环"上引开。模拟版让概念聚焦在名字前缀防冲突、权限注记这些真正可迁移的思想上。
- **二十七个工具的上下文成本**。每个工具的描述都要占用提示词空间，工具越多模型选错工具的概率越高。这个模块选择"按子系统分组写清楚"，而队友的工具清单被刻意砍到七件——上下文预算是真实约束，不是可以无限堆的。
- **装配与接线分离**。能力包可以整体拔插，挂载点固定且稀少（只有四个），这让"机器上同时跑着十几个机制"成为可理解、可维护的结构，而不是一堆互相回调的意大利面。
- **有意留白**。权限、压缩、恢复三个机制在入口处只装配不接线，代码注释里明说了接线方式在权限模块的内核副本里——教学上，"自己把它接上"比"看它已经接好"记得牢。

## 在整个项目中的位置

这是前二十个模块的集大成者：一至六模块打地基（循环、工具、计划、子智能体、技能、压缩），七至十二模块补基础设施（任务、后台、权限、钩子、记忆、错误恢复），十三至十五模块扩边界（外部协议、推理模式、动态提示词），十六至二十模块上强度（定时、团队、协议、自治、工作区隔离）。到这里，"一台完整机器"第一次真正组装完毕——所有机制共享一个循环、一份上下文、一套工具表，并且有明确的时序契约保证互不踩脚。

再往后，模块二十四换一种组织方式重新审视同一台机器（以宿主的视角讲清每种机制从哪里进入循环、事件又如何回流到同一段对话），模块二十五则把循环的最外层再抬高一阶——用独立的目标判定器决定"这台机器什么时候才算干完了"。
