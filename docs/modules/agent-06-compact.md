# 模块 06：上下文压缩

> 上下文窗口总会满，所以要有办法腾地方——一套"由轻到重"的四层整理术：便宜的操作每轮都做，昂贵的操作很少做，任何一层都动不了的那份完整记录，永远先落盘。

## 这个模块要解决什么问题

模块 05 之后，智能体已经能干活、能查资料、能按需学知识，但它有一个致命的物理限制：**上下文窗口是有限的，而工作产生的垃圾是无限的**。

- 工具结果只进不出。读一个 450 行的文件，全文就永远躺在消息列表里；分析一个有 32 个源文件的项目，光是"读文件"这一件事就能把窗口塞满。
- 具体的失败形态：token 用量逼近上限后，请求直接被服务端拒绝——智能体不是"做错"，而是"做不下去"；即便没到上限，堆积如山的旧输出也在持续抬高每一轮的费用，并把模型的注意力泡在噪音里。
- 更隐蔽的是：这不是偶发问题。只要任务足够大（大项目分析、长会话、多阶段工程），它**必然**发生。

模块 05 解决"知识从哪来"，模块 06 解决"知识放不放得下"：**让会话从"一轮对话"变成"可以无限工作下去的现场"，同时做到——近期的工作现场永远完整，远期的来龙去脉永远可查。**

## 核心思想

三句话：

1. **便宜的先做，昂贵的最后做**。裁剪、替换这类本地字符串手术不花一次模型调用，能做就先做；让模型写摘要要花一次调用，实在不够了才上。
2. **压缩挂在固定入口上，模型无感知**。内核每次调用模型之前，都把消息列表交给压缩能力"过一遍手"；返回一份新列表就替换上下文，返回原样就照发。模型不需要配合，也不需要知道。
3. **压缩对内存是有损的，对档案必须是无损的**。任何一次会"删东西"的操作，都先把完整原文存到磁盘上，再动手。

一条贯穿全部四层的隐含价值观：**删的应该是"负载"，留的应该是"事实"**。旧工具结果的输出原文是负载，"我执行过某工具"是事实；中段对话的逐句过程是负载，"任务进行到了哪一步"是事实。压缩做得好不好，就看你删下去的每一刀，切的是不是负载。

```
每次模型调用前的整理管线（由轻到重）：

  消息列表 ──► L3 大输出落盘（单条消息总量超限）
           ──► L1 裁掉中段（消息总数超限）
           ──► L2 旧结果换占位符（结果数超过保留额度）
           ──► 仍超 token 阈值？──是──► L4 模型写摘要（花 1 次调用）
                        │
                        否
                        ▼
                    照常调用模型
```

## 工作原理

### 1. 挂载点：每次模型调用前的固定入口

压缩不是散落在各处的补丁，而是能力体系里的一个钩子：内核在每一次调用模型前遍历所有能力，把当前消息列表递给它们。压缩能力在这里跑完整条管线，把"手术后"的列表交回去，内核用返回值替换自己的上下文。约定很干净：返回同一个引用代表"没改"，返回新列表代表"请用这份"。

这个设计有两个直接好处：一是触发点天然全覆盖（每轮必经），不存在"忘了检查"的路径；二是压缩对模型完全透明——模型永远只看到一个"恰好不超限"的世界。

另外两点值得点破：

- **每轮都跑，而不是超限才跑**。前三层是幂等的本地手术：没超限就原样通过，几乎零开销。让它们常驻管线的意义在于"持续保洁"——上下文的膨胀是每轮发生的，清理也必须每轮发生，攒到爆仓再清理就晚了。
- **多能力共用同一入口，顺序即协议**。本模块之后，每次调用前的这个入口会挤进更多能力（下一模块的通知注入也挂在这里）。约定是按注册顺序依次过手、后一个看到的是前一个改完的列表——于是"先吸收新信息、再做瘦身"这类顺序默契得以成立，谁也不用感知谁。

### 2. L3：先给大输出"落盘留条"

管线第一步处理最极端的浪费：单条消息里塞了超大块的工具输出（比如一次列出了几千行目录、一次跑了个刷屏的构建）。规则是只盯**最新一条**工具结果消息：

- 把里面所有工具结果的总量算出来，超过单条消息的字节上限（约 20 万字符）才动手；
- 从最大的开始处理：超过持久化阈值（约 3 万字符）的结果原文写进工作目录下的一个输出文件夹，原位替换成一条占位内容——**完整输出的存放位置 + 前 2000 字预览**；
- 总量降到上限以下就停手，小结果原样保留。

思路是朴素的空间置换：**磁盘又大又便宜，上下文又小又贵**。模型拿到预览和文件路径，真需要细节时自己用读文件工具去取——主动权还在模型手里。

### 3. L1：裁掉中段消息

消息总数超过上限（50 条）时触发。做法是"保两头、砍中间"：

- **保头部**：最开头的几条（初始指令、任务背景）永远保留；
- **保尾部**：最近的几十条（当前正在进行的工作）完整保留；
- **砍中间**：被裁掉的条数汇总成一句占位文本（"已省略 N 条对话历史消息"）放在原位置。

有一条硬约束贯穿始终：**发起工具调用的消息和回带工具结果的消息绝不能拆开**。它们是协议上的配对，拆开请求就不合法。所以裁剪的边界会自动外扩——如果切口正好落在配对中间，就把边界挪到配对之外；万一挪完头尾都要重叠（说明根本没得砍），就直接放弃本次裁剪，原样返回。宁可这一轮不省，也不能发出非法请求。

### 4. L2：旧工具结果换成占位符

这是频率最高、最"日常"的一层，它利用了一个观察：**旧工具结果的原文价值衰减得极快**——三步之前那次读文件的全文，此刻几乎肯定用不上，但"我读过某个文件"这个事实还有用。

做法：

- 扫一遍消息列表，收集所有工具结果的位置，同时从配对的调用侧把"结果 → 工具名"对应关系记下来；
- 结果总数不超过保留额度（最近 3 条）就什么都不做；
- 超出额度的旧结果，原文替换成一句占位符："[已执行：读文件]"——**行为保留了，负载删掉了**。模型仍然知道自己做过什么、按什么顺序做的，只是看不到当时的输出内容。

顺带做一件小事：旧轮次里模型的原生思考块也替换成占位。各家的协议对回传历史思考的限制不一，而且旧思考留在列表里只会虚增 token 估算，没有上下文价值。

### 5. L4：让模型自己写摘要

前面三层都是本地手术、零调用成本；如果全部做完 token 仍超阈值，才动用唯一昂贵的一招——**花一次模型调用，把整段历史浓缩成摘要**。流程：

1. **先存档**：把压缩前的完整对话逐条写入本次会话的档案文件，拿到档案位置。这一步在任何删改之前；
2. **再摘要**：把对话文本（超长则截断到 8 万字符）连同固定提纲交给模型——要求写清"已完成的工作、当前状态、关键决策"，简洁但保留关键细节；
3. **记录元数据**：这次压缩的时间、原因、消息数、token 估算、摘要全文，都存进压缩历史，之后随时可查；
4. **重建上下文**：新列表极简——一条用户消息（压缩声明 + 档案位置 + 摘要），加一条助手确认（"收到，继续当前任务"），让消息序列保持合法。

其中有个点睛细节：新上下文的头部会**带上最近一条真实的用户请求原文**。否则很容易出现这种事故——压缩刚做完，模型拿着摘要兴冲冲继续，却忘了用户此刻到底让它干什么。摘要回答"我们干到哪了"，用户请求原文回答"正事是什么"，两者缺一不可。

### 6. 紧急兜底、手动压缩与透明仪表

- **紧急兜底**：前三层加上 L4 都没拦住、服务端直接返回"提示过长"拒绝时，走反应式压缩——保留首条用户消息和最近几条，中间塞进摘要与档案位置，立刻重试。它是最后一道保险，平时不出场。
- **手动压缩**：模型自己也能调一个"压缩对话"的工具，可指定压缩重点（比如"保留报错信息"）；用户也可以在控制台敲一条命令直接触发。两者走的都是同一条 L4 摘要流程，只是触发者和附带意图不同。
- **透明仪表**：一条查看命令能随时报告当前消息数、token 估算、阈值、使用率，并给出状态灯（正常 / 接近 80% 需关注 / 已超限建议压缩）。压缩策略再自动，也要让使用者看得见。
- **计数策略**：token 计数优先向服务端要精确值；服务端不支持时退回字符数除以四的粗估。阈值判断不必苛刻到字节，但必须**稳定且偏保守**——宁可早压，不可溢出。

### 7. 这套机制到底"保住"了什么

- **近期消息**：最近 3 条工具结果原文 + 尾部全部消息永远完整——模型此刻的"工作台面"永远不会被自己打扫掉；
- **任务状态**：摘要提纲强制包含"当前状态"，且最新用户请求原文随摘要一起进入新上下文——压缩之后模型依然知道"干到哪了"和"该干什么"；
- **完整历史**：每次压缩前全文落盘，事后调试、复盘、统计都能翻到无损原文。内存里丢掉的，档案里都有。

把四层的账本放进一张表：

| 层级 | 触发条件 | 成本 | 丢掉什么 | 保住什么 |
|---|---|---|---|---|
| 大输出落盘 | 最新一条消息总量超限 | 零次模型调用 | 超大输出的原文（留 2000 字预览 + 文件位置） | 细节随时可从磁盘取回 |
| 裁掉中段 | 消息总数超 50 条 | 零次模型调用 | 中段过程性对话（留"已省略 N 条"） | 头部背景 + 尾部现场 |
| 旧结果换占位 | 工具结果数超过 3 条 | 零次模型调用 | 旧输出的原文 | 全部工具调用的事实与顺序 |
| 模型写摘要 | 前三层后仍超 token 阈值 | 一次模型调用 | 几乎全部原文 | 摘要 + 最新用户请求 + 档案位置 |

观察规律：越往上越"无痛"，越往下越"伤筋动骨"——这正是"便宜的先做"把昂贵操作逼到几乎不出场的过程。

## 一次完整运行的流转

以剧本 s06 为例，用户说："分析这个项目里所有的 Python 文件，并逐个总结。"

1. 模型先跑一条查找命令，结果列出 32 个文件。它开始逐个读取——每读一个，一条几百行的源码就进列表一次。
2. 读到第十几二十个文件时，本轮调用前的管线开始频繁出手：L2 把早先的文件内容换成"[已执行：读文件]"占位符，只留最近 3 条完整。列表增速被摁住了，但 token 总量仍在爬。
3. 终于，仪表上的估算逼近上限（剧本里是 148231，阈值 150000）。这一轮管线依次执行：超大输出落盘、旧结果占位、（消息数尚可，中段未裁）、仍超阈值——触发 L4。控制台打出"自动摘要压缩已触发"：全文存档、模型写摘要、新上下文只剩"存档位置 + 当前用户请求 + 摘要 + 确认"，token 从 14 万级降到 4 万级。
4. 下一轮，模型看着精简后的上下文说："文件 1–18 已总结，继续处理剩余文件。"它既没跑题也没丢任务——**旧工具结果的原文可以被遗忘，工作进度本身不会**。

这场戏的要点：压缩不是在崩溃边缘的一次抢救，而是每轮都默默进行日常保洁；"能处理任意数量的文件"由此成立——工作的规模第一次不再受窗口大小约束。

顺手把"人怎么看"也走一遍：用户此时敲下查看命令，仪表会报告当前消息数、token 估算、阈值与使用率，状态灯显示"已超限，建议压缩"；再敲一条历史命令，能看到刚才那次压缩的完整记录——时间、原因（自动还是手动）、压缩前的消息数与 token 量、摘要内容。若用户等不及自动触发，也可以直接敲命令手动压一把，或让模型调用压缩工具并指定"重点保留报错信息"——同一条摘要流程，换个触发者而已。

还有一个值得点名的幸存者：**待办清单不怕压缩**。它从来不以对话消息的形式存在，而由独立的管理器维护，压缩重写的只是消息列表，清单原封不动——模型压缩后照常被催办提醒"三个回合没更新待办了"。这也预告了下一模块的方向：凡是需要跨越压缩活下来的状态，都应该长在消息列表之外。

## 设计取舍

- **分层 vs 单一策略**。只在"到 80% 就摘要"这条单策略路线里，绝大多数轮次其实用不着摘要，白花钱；而滑动窗口（无脑丢最旧 N 条）虽然便宜，却会把关键背景丢掉。分层让廉价清理持续进行、昂贵摘要罕见触发，各层只处理自己最擅长的那种浪费。
- **摘要替换全部 vs 摘要旁保留近期**。摘要与近期消息并存会出现"两份重叠的真相"：摘要说"我们决定用方案 X"，近期消息还在展示纠结过程，模型收到矛盾信号。所以 L4 是干净的替换——但把最新用户请求原文单独保留，作为唯一不许被摘要掉的东西。
- **触发要算"值不值"**。压缩不免费：摘要本身占 token，还要一次调用。如果上下文只有两万五千 token，压完可能只省五千，反而更差。所以阈值的设计原则是"预计节省明显大于一次摘要的固定开销才动手"，而不是简单的百分比。
- **有损压缩 + 无损档案**。不存档确实省磁盘，但出了问题就无从查起——"两小时前它为什么做这个决定"永远问不到了。选仅追加写入的行式文本作为档案格式：写起来安全、逐行处理方便、零依赖。
- **失败绝不中断对话**。任何一层出错（存档失败、摘要调用失败）都返回原始消息列表——压缩是优化，不是功能；优化失败了，大不了这一轮多花点 token，绝不能让正事卡住。
- **阈值可调，策略可关**。阈值是配置不是硬编码：想更省就把 token 阈值调低、保留条数调小；想观察裸奔行为，把阈值调到天文数字即可整体停用。教学项目尤其需要这种"能随手拨动的旋钮"——亲手把阈值调错一次，比读十遍文档更懂这套机制。
- **提示片段先行告知**。系统提示词里会写明"本智能体支持自动压缩上下文，也提供手动压缩工具"。这不是客套话：模型若不知道压缩的存在，可能在长会话里自作主张地"从头复述背景"来对抗遗忘，反而把刚省下的空间又吃回去。

## 在整个项目中的位置

- **相对模块 05 新增了什么**：05 管的是"知识怎么省着用"，06 管的是"记忆怎么活得久"。它没有增加任何新能力，却改变了会话的**时间属性**——从"上下文用完即止"变成"可以无限工作下去"。这是从"能干一件事"到"能干一个大工程"的分水岭。
- **为后续铺了什么路**：
  - 模块 07 的任务图之所以敢放到磁盘上，正是因为 06 证明了"内存里的东西随时可能被压掉"——凡是需要长期存活的状态，都不能只活在消息列表里；
  - "每次模型调用前的固定挂载点"从此成为标准扩展位，模块 08 的通知注入用的正是同一个入口；
  - 压缩历史 + 会话档案让"事后复盘智能体行为"成为可能，这是模块 10（钩子）与模块 11（记忆）在可观测性上的前身；
  - 模块 19 的长时自治运行，本质上就是"06 的压缩 + 07 的任务板 + 08 的后台执行"三件套的持续运转。
