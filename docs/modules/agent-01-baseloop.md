   # 模块 01：基础循环

> "一个工具 + 一个循环 = 一个智能体。" —— 这是整个项目的最小可行形态：模型透过一个命令行工具触碰真实世界，循环负责把每一次工具的真实结果递回模型眼前。

本文是系列的起点，不依赖任何前置模块；后面 24 个模块全部建立在这一章的骨架之上。

## 这个模块要解决什么问题

语言模型会推理、会写代码，但它被关在一个"只出不进"的盒子里：它读不到你的文件，跑不了任何一条命令，也看不到程序报了什么错。你让它帮忙建一个文件，它只能回你一段"你可以这样做"的说辞，剩下的全得你自己动手。

更隐蔽的问题是：就算模型能"发起"某个操作，一次操作往往也不够用。创建文件之后要验证内容、验证失败要换个写法、跑程序之后要看输出——这些步骤之间需要有人把上一步的真实结果递回去。在没有循环的实现里，扮演"递话人"的是你自己：每次手动复制工具输出、粘贴回对话框。换句话说，你自己就是那个循环。

本模块同时解决这两件事：给模型一只手（一个能执行命令行的工具），再给模型一台永动机（一个把工具结果不断回灌的循环）。

## 核心思想

把"智能体"这个神秘名词还原成两个零件： 

1. **一个工具**：执行命令行并返回输出。命令行本身就是通用接口——读写文件、运行程序、查进程、装依赖、发网络请求，全都是一条命令的事。拥有命令行的模型，已经是一个通用代理。
2. **一个循环**：向模型发起请求；如果回复里带着工具调用，就执行它、把结果追加进消息列表、再次请求；如果模型只回了文本，本轮就结束。退出条件只有一个——模型不再要用工具。

系统里没有任何规划器、任务队列或状态机。模型根据对话历史自行决定下一步执行什么命令；循环只是不停地问"接下来做什么"，直到模型不再要求工具为止。在这个层级加规划层属于过早抽象——模型的思维链本身就是计划。

## 工作原理

### 1. 一切从消息列表开始：用户输入如何进入历史

程序启动后先做一次会话装配：用户可以选择接着上次的对话（把本地保存的历史消息整段恢复进内存的消息列表），或者开一个新会话（列表为空）。之后进入外层大循环：读取一行用户输入；以斜杠开头的特殊命令（查看统计、退出等）在本地直接处理、不发给模型；普通输入则追加为一条用户消息。

所有对历史的写操作都收拢在同一个入口：无论是用户消息、模型的回复，还是工具结果，追加进列表的同时会同步写到本地快照。这样进程在任何时刻被关掉，对话都不会丢，下次启动还能原样续上。

### 2. 带着工具说明去请求模型

每次请求模型时，随消息列表一起发送的还有四样东西：

- **系统提示词**：角色定义、工具的详细用法说明、常用命令示例、工作原则（"优先直接行动，不要只给建议"、"破坏性操作先确认"、"命令失败就分析原因换方案"）。
- **工具清单**：本模块只有一项——执行命令行的工具。清单里写明工具的名字、一句话描述，以及它接受哪些参数（哪个必填、哪个可选、分别是什么类型）。
- **消息列表**：完整对话历史。
- **生成上限**：本次回复最多生成多少内容。

有个容易被忽略的细节：系统提示词末尾会自动拼接一段"运行环境说明"，告诉模型当前是哪个操作系统、工作目录在哪、命令会通过哪种外壳执行。实践发现，在 Windows 上如果不特别说明，模型会高频输出类 Unix 风格的命令然后反复碰壁。

请求发出前，已注册的能力还有一次对上下文"做手术"的机会（本模块没有注册任何能力，这个挂载点暂时空转——但它为后面的模块留了口子）。

### 3. 停止原因：循环的总开关

模型每次返回都附带一个"停止原因"，本项目把它抽象成三种：正常结束（说完了）、达到长度上限（回复被截断）、需要调用工具（想先执行些操作再继续）。

内层循环的继续条件就是"停止原因 = 需要调用工具"。相比"扫一眼回复里有没有工具调用块"这种土办法，停止原因是模型服务给出的权威判定：空工具调用、回复被截断这类边缘情况都已经被它覆盖。工程上还留了一个兜底——个别兼容服务明明返回了工具调用，停止原因却标成"正常结束"，所以判定时也会检查回复里是否真的带着工具调用。

循环退出后还有一道收尾检查：如果停止原因是"达到长度上限"，就打印一条醒目警告。这一步很重要——被拦腰截断的工具调用往往缺少收尾标记，若静默处理，下一轮请求会因为历史里躺着一条残缺消息而反复出错，形成最难排查的那种死循环。

### 4. 工具结果如何回灌

模型的一轮回复里可能包含多个工具调用，执行器逐个处理：

```
        模型回复（内含工具调用）
                 │
    ┌────────────┼─────────────────┐
    ▼            ▼                 ▼
 能力拦截     按名字在工具清单查找      执行
 命中拦截     找不到该工具            抛出异常
    │            │                 │
    └────────────┴────────┬────────┘
                          ▼
     三种情况都各自产生一条"工具结果"消息（拦截文案 / 找不到 / 错误文案 / 正常输出）
                          │
                          ▼
              全部追加进消息列表，再次请求模型
```

三个要点值得单独说：

- **失败也是一条结果**。无论成功、失败还是被拦截，都会生成一条工具结果消息。对话协议里并没有统一的"失败标记"字段，最通用的做法就是把错误写成一句可读文本（"错误：某某原因"）回灌——模型自己会读、会理解、会换思路重试。错误不是异常抛给用户，而是喂回给模型。
- **结果与调用一一对应**。每条结果都携带模型给出的调用编号，即使一轮里有多个调用，各自的结果也不会串线。
- **防御性短路**。如果这一轮扫下来一条有效的工具调用都没有，就直接跳出内层循环——继续请求只会在同样的输入上原地打转。

### 5. 命令行工具内部的四道保险

那个唯一的工具本身也不是"把命令丢给系统"这么简单：

1. **危险命令黑名单**：命中关机、重启、递归强删根目录这类模式的命令直接拒绝执行，只回一句"命令被拦截"。
2. **超时强杀**：单条命令最多等两分钟，超时强制结束进程。否则一句误发的交互式命令（比如不带参数启动某个解释器）会把整个智能体挂死在等待上。
3. **输出截断**：单次结果最多保留五万字符，超出的部分继续读取但不再拼接——"读而不存"是为了让子进程的输出管道能被排空、正常退出；结尾注明已截断。这防止一条列目录命令的洪流把上下文撑爆。
4. **流合并与编码适配**：错误输出并入标准输出一起读（分两条管道先后读，在大输出场景会互相等死）；不同外壳、不同操作系统按各自合适的字符编码读取，避免中文乱码。命令类型可由模型显式指定，不指定就按操作系统自动选择。

执行结束后如果退出码非零，返回"执行失败 + 退出码 + 全部输出"，模型据此判断是修正命令还是改走别的路。完全没有输出的命令则返回一句"(无输出)"而不是空字符串——让模型明确知道"命令跑成功了，只是没东西可打印"，而不是怀疑执行环节出了问题。

### 6. 两层循环：一张图看清控制流

把前面几节合起来，整个程序的控制流其实只有两层：

```
┌─────────────────────── 外层循环（对话层）───────────────────────┐
│  恢复历史 → 读用户输入 → 斜杠命令？─是→ 本地处理，回到读输入      │
│                              │否                                │
│                              ▼                                  │
│                    用户消息入列并落盘                             │
│                              ▼                                  │
│  ┌──────────────── 内层循环（工具层）────────────────┐           │
│  │  请求模型（历史 + 工具清单 + 系统提示词）            │           │
│  │                    ▼                             │           │
│  │        停止原因 ＝ 要用工具？                       │           │
│  │            是│              │否                    │           │
│  │             ▼              ▼                     │           │
│  │      执行全部工具调用      打印文本；检查是否被截断  │           │
│  │      结果回灌入列        内层循环结束              │           │
│  │            └──────▶ 回到"请求模型"                 │           │
│  └──────────────────────────────────────────────────┘           │
│                              ▼                                  │
│                 回到"读用户输入"，等待下一句话                     │
└─────────────────────────────────────────────────────────────────┘
```

外层循环回答"和谁对话"，内层循环回答"这一句话要做几步"。此后所有模块的扩展——加工具、加能力、加子智能体——都只发生在内层循环的内部或它的挂载点上，这两层的形状从未改变。

还有一个贯穿始终的细节：模型的每一次文本输出都会被立即打印出来。看似理所当然，实则是个修过的缺陷——早期的实现只在"有工具调用"的分支里打印文本，导致模型不调工具、纯粹回答问题的那类回复被整体吞掉，用户面对的是一片沉默。每一轮都打印，才保证任何回复都可见。

### 7. 循环何时退出，为什么一个工具就够

内层循环退出的唯一条件是模型不再请求工具；外层循环退出的唯一条件是用户主动退出。两次请求之间，模型可见的一切都在消息列表里——它看过自己发过的每条命令、也看过每条命令的真实输出，所以下一发命令永远是基于事实的下一步，而不是凭空想象。

至于"为什么一个工具就够"：命令行能读写文件、运行任意程序、在进程间传递数据、管理文件系统。任何额外的文件读写工具，都只是命令行已有能力的子集——增加工具并不会解锁新能力，只会增加模型需要理解的接口。模型只需学会一个工具的参数约定，工具实现不过百余行。这就是最小可行智能体：一个工具，一个循环。

## 一次完整运行的流转

以场景剧本里那次典型交互为例：用户想要一个打印问候语的脚本文件。

```
你: 帮我创建一个脚本，打印 "Hello, Agent!"
 │
 ① 用户消息入列并落盘 ──▶ 携带工具清单发起第 1 次请求
 │
 ② 模型回文字"我用命令行工具创建这个文件"，并附带工具调用：
 │    向文件写入一行打印语句              （停止原因＝要用工具）
 │
 ③ 内层循环启动：执行命令 ──▶ 命令成功但无输出 ──▶ 回灌"(无输出)"
 │
 ④ 第 2 次请求：模型没有直接宣布完成，决定再验证一下
 │    工具调用：查看刚才那个文件的内容
 │
 ⑤ 执行 ──▶ 文件里那行打印语句被原样返回 ──▶ 回灌
 │
 ⑥ 第 3 次请求：模型只回文本"完成了，你可以运行它看看效果"
 │                                          （停止原因＝正常结束）
 ▼
 ⑦ 内层循环退出，回到外层等待下一条用户输入
```

短短一轮对话里模型发了两条命令、说了三段话——一个"创建文件"这么小的任务，也完整走过了"动手 → 验证 → 汇报"的闭环。更关键的是：先写后验这第二步没有任何程序逻辑要求它发生，是模型自己看到"命令没有输出"后决定不能想当然。循环提供的只是机制，谨慎是模型自己长出来的行为。

## 设计取舍

- **一个工具，而不是一篮子工具。** 备选方案是从丰富的工具集（文件读写、网络请求、数据库）起步。放弃的原因：那会掩盖核心洞察——拥有命令行的模型已经是通用代理；而且从最小化起步，后续每个版本新增的能力都清晰可见。
- **不做规划框架。** 没有任务队列、没有状态机，模型在推理中隐式规划。代价是计划不可见、也不持久——一旦早期的思考滚出上下文，计划就丢了。这个伏笔在模块 03 用"待办清单"补上。
- **以停止原因驱动循环，而不是数工具调用块。** 代价是对个别兼容服务的怪癖多一次兜底判断；换来的是对空调用、截断等边缘情况的稳健处理，这是模型服务官方推荐的标准做法。
- **错误以普通文本回灌，而不是专门的成功/失败标记。** 因为最广泛使用的对话协议没有失败标记字段；统一用文本，任何后端都能工作，模型也能拿到足够的上下文去自我修正。
- **黑名单只是最后一道底线。** 危险命令黑名单防的是最灾难性的那几类操作；更完善的权限体系（可配置的允许/拒绝规则、执行前向用户确认）留给后面的能力模块去做，工具内部这层保底永远存在。
- **进程即子代理的雏形。** 模型执行命令时创建的是全新进程：有自己的环境、自己的输入输出，天然看不到父进程的任何对话。这是"委派"最原始的形态——模块 04 会把它升格为真正的子智能体。
- **每条消息即时落盘，而不是退出时一次性保存。** 增量写盘的代价是频繁的小额写入；换来的是任何时刻断电、崩溃、强退都不丢历史。对一个可能执行长任务、跑长命令的智能体来说，"随时可死"比"少写几次盘"重要得多。
- **会话恢复是整段回灌，而不是摘要。** 重启后历史消息原样回到消息列表，模型接着上次的现场继续干活。代价是历史越长、每次请求越大——这个包袱要到模块 06 的上下文压缩才被认真处理。

## 在整个项目中的位置

这是 25 个模块的地基。外层对话循环 + 内层工具循环的双层结构、消息列表的累积方式、工具结果的回灌约定、截断告警、会话持久化，此后每个模块原样继承——循环本身从第一版到最后一版几乎没有变过，后面所有章节都是在它周围加东西。

它同时埋了三条伏笔：

1. **工具清单机制**（模块 02 往这张清单里塞进一整个工具家族和搜索引擎）；
2. **请求前的上下文挂载点**（模块 03 用它注入催办提醒，模块 06 用它压缩历史）；
3. **"起一个全新执行体去干子任务"的思想**（模块 04 的子智能体、模块 07 的任务委派，都是这条思路的正式化）。

还有一个只有动手跑过才能体会的价值：这一版证明了"模型 + 命令行 + 循环"已经能干成很多事，所以后面每加一个工具、一个能力，你都能清楚看到它到底多解决了什么问题——而不是从一开始就被一堆机制糊住眼睛。
