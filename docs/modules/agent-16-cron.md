# 模块 16：定时任务

> 给智能体加上时间维度——它能自己登记"到点要做的事"，进程里的调度器到点把它叫醒干活，哪怕主循环此刻正卡在等你敲键盘。

## 这个模块要解决什么问题

到此为止，智能体都是**纯被动**的：人敲一句话，它动一轮；人不动手，它就永远停在那里。但很多真实需求天生带着时间属性：

- "每两分钟看一眼目录里有没有新日志，有就汇总一下"——周期巡检；
- "每天早上九点把昨天的进度整理成日报"——定点例行公事；
- "一分钟后提醒我检查构建状态"——一次性闹钟。

这些需求在现有体系里全部无解。会话机制（模块 06 起的恢复与压缩）解决了"记忆活得久"，但没有解决"没人来的时候谁来按开始键"。缺的是一个**时钟**和一套把"时间 + 要做的事"登记在案、到点唤醒执行的机制。

另一个隐藏难题：内核主循环阻塞在标准输入上等用户敲字，**外部没有任何办法往里"注入"一条消息**。就算有东西到点了，谁来叫醒、什么时候叫、叫醒时宿主正在忙怎么办——这些都要有答案。

## 核心思想

四句话：

1. **把时间变成模型可声明的资源**。给模型三个工具：登记一个定时任务（时间模式 + 到点要执行的任务描述）、查看现有任务、按编号取消。模型听懂人话里的时间意图后，自己翻译成登记调用。
2. **触发与执行彻底解耦**。调度器只负责"发现到点"，把任务描述放进队列就算完事；真正执行由宿主智能体在合适的时机完成。调度器不需要懂模型，宿主不需要懂时间。
3. **忙碌让路，永不硬闯**。宿主正处于一轮模型调用中时，任务描述回队列稍后再投——绝不与主循环并发改写共享上下文。宁可晚到，不可踩踏。
4. **可持久化，重启不丢**。登记时可以标记为"持久"；持久任务每次变更都写盘，进程重启后自动恢复进调度器。

```
   模型                    调度器（两条后台线程）                宿主智能体
   ────                    ────────────────────                ──────────
   登记/查看/取消 ────────► 任务表（内存，持久任务同时落盘）
                                │
                 扫描线程（每 1 秒）：对齐当前时间，
                 命中时间模式 → 入队 + 记录上次触发 + 防抖检查
                                │
                                ▼
                            待投递队列
                                │
                 分发线程（每 200 毫秒）：取队头 → 回调投递
                                │
                                ▼
                          能力包检查宿主忙不忙 ──忙──► 放回队列，稍后再试
                                │闲
                                ▼
                     单线程执行队列（同一时刻最多跑一个）
                                │
                                ▼
                     在宿主身上完整跑一轮工具循环
                （任务描述与执行痕迹都留在共享上下文里）
```

## 工作原理

### 1. 把"每隔一段时间做某事"表达成一个任务

一条定时任务由五样东西定义：一个时间模式、一段任务描述、两个开关（是否周期触发、是否持久化），外加调度器回填的两个时间戳（上次触发、下次预期触发）。

时间模式采用业界通行的**五字段表达式**（即经典的 cron 表达式），五个字段依次是：分钟、小时、日期、月份、星期。每个字段支持四种写法：星号（任意值）、逗号列表（这几个值都行）、横杠范围（这一段都行）、斜杠步长（每隔几个单位）。解析器把每个字段展开成各自的可取值集合，之后"某时刻是否命中"就只是查表。

两条值得记的语义细节：

- **日期与星期同时受限时，任一命中即触发**（"每月 1 号或每周一"这种写法在传统定时器里就是这个经典歧义），这与主流实现、也与本项目对应的原版教程保持一致；只限制一边就只看那一边，两边都是星号则必中。
- **解析期即校验**。登记工具在收到表达式时就地试解析，非法写法（字段数不对、范围越界、步长非正）立刻报错回给模型——而不是等调度线程扫到那一单才炸，让模型当场就能纠正。

模型侧的翻译由提示词片段教：人话里的"每 2 分钟一次"对应"步长 2 作用在分钟字段"，"每天 9 点半"对应"分钟 30、小时 9、其余全星号"，"N 分钟后提醒我"对应**一次性任务**（周期开关关掉，命中一次后自毁）。任务描述不是"提醒模型一声"，而是一句完整的任务指令，到点后会被当作一次真正的用户请求来执行。

几个典型意图与表达方式的对应关系：

| 用户的说法 | 五字段的落法 | 周期性 |
|---|---|---|
| 每 2 分钟一次 | 分钟字段步长 2，其余四个字段全任意 | 周期 |
| 每天 9 点半 | 分钟 30、小时 9、其余全任意 | 周期 |
| 每周一早 9 点 | 分钟 0、小时 9、星期一，其余全任意 | 周期 |
| 每月 1 号 0 点 | 分钟 0、小时 0、日期 1，其余全任意 | 周期 |
| 1 分钟后提醒我 | 分钟字段锁定一分钟后那一格 | 一次性 |

值得强调的是最后两个开关的分工：**时间模式回答"什么时候"，周期开关回答"几次"，持久开关回答"活多久"**。三个维度互相独立——"每天九点的日报"是周期 + 持久；"十分钟后提醒我"是一次性 + 临时；"每天检查构建、断电了也要继续检查"是周期 + 持久。模型按用户意图自由组合，而不是在少数几个预设套餐里挑。

### 2. 调度器：两条后台线程各司其职

调度器由两条**后台线程**驱动，进程退出时它们不会碍事：

- **扫描线程，每秒一次**。拿当前时间去逐个比对任务表。命中的任务做四件事：把任务描述放进待投递队列；记录"上次触发时间"；计算并更新"下次预期触发时间"（这个值纯粹给人看，扫描本身不依赖它）；把任务表的变化同步落盘。**防抖窗口**是这里的关键保险——距上次触发不足一分钟就跳过。没有它，秒级扫描会在同一个命中分钟里把同一任务反复入队（扫描线程一秒跑一次，而命中条件按分钟对齐，一分钟内要命中几十次）。
- **分发线程，每 200 毫秒一次**。从队头取一条任务描述，通过一个投递回调交出去。调度器自己不知道回调背后是谁——这个回调由能力包在启动时注入。回调暂时为空时，任务描述只在队列里攒着，**不会丢**。

登记与取消都是即时生效并立刻落盘的：登记时先解析表达式、算出首次触发时间，再进表；取消则是按编号出表。落盘时只挑持久任务写——临时任务（比如那类"稍后提醒我"的闹钟）的生命周期不该超过进程。

### 3. 命中之后：如何叫醒一个"正在等你打字"的会话

这是本模块最核心的工程问题。主循环阻塞在标准输入上，调度线程没有办法把一条消息塞进它的上下文——强行并发改写消息列表，轻则消息顺序错乱，重则请求发出去时配对关系是坏的。

解法是把"叫醒"设计成**协作式的三道门**：

- **第一道门：宿主忙不忙。** 能力包用两个钩子近似出一个"忙碌"信号：每次调用模型前把忙标记置位，拿到响应后清位。投递前先看这个标记——忙，就把任务描述放回队列，下一次分发再试。这里有个诚实的注脚：能力拿不到内核"正在忙"的真相，只能靠钩子近似；而近似就有漏标记的风险——如果某次模型调用抛了异常，"置闲"的钩子没跑到，忙标记就会卡在"忙"。所以忙标记带**过期自愈**：超过一个比最长请求超时还长的时限后，自动视为空闲，保证定时任务不会被一次异常永久饿死。
- **第二道门：串行执行。** 通过后，任务进入一个**单线程**的执行队列——同一时刻最多只有一个定时任务在跑，多个任务同时命中也乖乖排队。宿主的上下文在任何时刻只被一方改写。
- **第三道门：在宿主身上跑。** 执行不是另起一个独立智能体，而是**借宿主的工具表和上下文**，把任务描述当作一次完整的任务来运行（调模型、执行工具、回灌结果，直到产出结论）。于是任务描述和执行痕迹都留在共享上下文里——用户回过神来，能在对话里看到"刚才那两分钟它自己干了什么"，追问一句"刚才的巡检结果如何"，模型是知道来龙去脉的。

用户此时在终端上打字也不冲突：定时任务的输出会穿插着打出来（带着能力名前缀），用户敲完回车，主循环照常处理他的输入。两条线共享上下文但轮流持锁，互不打断。

### 4. 一次性、周期、错过与补跑

**一次性任务**（周期开关关闭）：命中入队后立即从任务表里移除，随后落盘。适合"提醒我""过会儿帮我做某事"这类一锤子买卖。**周期任务**则长期在册，每次命中更新触发记录。

**错过怎么办**——这是所有定时系统都绕不开的问题，本模块的语义是诚实的"**错过即过期**"：扫描线程拿的是**当前时间**去对齐表达式，不会回头检查"过去这段时间里本该命中几次"。进程停了一小时，期间本该跑三十次的任务，重启后只会等到下一个对齐时刻跑一次。不补跑是教学实现的取舍（补跑需要记录每次错过的点位并逐一执行，复杂度陡增），但有两道缓冲：其一，投递阶段的失败**会回队列重投**——那是"延迟"而非"补跑"，任务没有丢，只是晚了；其二，**持久任务重启恢复时会把"上次触发时间"清空**——否则恢复瞬间可能被"距上次触发不足一分钟"的防抖逻辑误判而跳过第一次命中，这个细节不处理，重启后的第一个周期就会神不知鬼不觉地丢掉。

### 5. 持久化、恢复与诊断

持久化文件放在工作目录下，登记、取消、命中三个时点都会全量重写（内容只含持久任务）。恢复发生在能力包启动时：读文件、逐条重新解析表达式、清空触发记录、算出下次触发、塞回内存任务表；表达式已经坏掉的任务跳过不恢复。控制台会打一行"持久任务已恢复 N 个"，让人确认状态回来了。

一条以斜杠开头的诊断命令随时可查：任务表（编号、表达式、是否周期、是否持久、任务描述原文）加上待投递队列的积压数量。队列积压持续增长通常意味着宿主长期忙碌或投递通道出了问题——它是这套机制最直观的体检指标。

### 6. 生命周期：从进程启动到退出的完整时间线

把这套机制按时间轴串一遍，各环节的归属一目了然：

- **能力注册时**：读配置（本能力无外部配置，取内定参数），与宿主交换引用。
- **会话启动时**：先从磁盘恢复持久任务，再拉起两条调度线程和单线程执行队列，最后打横幅报告恢复了几个。恢复先于扫描，避免"恢复了一半就开始命中"的竞态。
- **运行中**：登记/取消改任务表并落盘；扫描线程每秒对时入队；分发线程每零点二秒投递；执行队列串行消化；钩子持续维护忙标记。
- **进程退出时**：停调度线程、清空执行队列。内存里的临时任务随进程消亡，持久任务在磁盘上等下一次启动。

### 7. 它不是"后台任务"：与模块 08 的分界

项目里早就有后台执行（模块 08）：模型在一轮对话中把一件耗本事甩到后台线程，自己继续干别的，干完了通知它。定时任务和它看起来都"不占对话"，但机制上是两类东西：

| | 后台任务（模块 08） | 定时任务（本模块） |
|---|---|---|
| 谁发起 | 模型，在某一轮对话中 | 时间，由模型预先登记 |
| 触发条件 | 立即执行，只是不阻塞当前轮 | 表达式命中 |
| 产出方式 | 完成后向会话通报结果 | 以一次全新的任务执行进入上下文 |
| 生命周期 | 随当前会话 | 可跨进程重启（持久任务） |
| 解决的问题 | "一件事很慢，别等它" | "到点了，该做事了" |

一句话：后台任务改变的是**一次执行的空间安排**（在哪里跑、等不等它），定时任务改变的是**执行的起点**（什么时候开始跑）。自治运行（模块 19）需要的是后者——它要的不是"跑得快"，而是"没人喊也开工"。

## 一次完整运行的流转

用户："每 2 分钟帮我看一眼目录里有没有新的日志文件，有就写一份摘要；对了，1 分钟后提醒我喝水。"

1. **登记**。模型拆出两个意图，连续调用登记工具：周期任务（步长 2 作用于分钟字段，任务描述是巡检指令，标记持久）和一次性任务（1 分钟后命中，任务描述是提醒，不持久）。两个工具结果分别带回编号，模型向用户复述确认。
2. **第 60 秒**。扫描线程命中提醒任务 → 入队 → 分发线程取头 → 宿主空闲 → 单线程执行：控制台打出"触发定时任务"+ 提醒内容。这是一次完整的工具循环，哪怕模型只是说了一句话。随后提醒任务自毁、任务表落盘。用户此刻可能正在打字，这条输出带着前缀穿插进来。
3. **第 120 秒**。周期任务命中。不巧用户刚提交了一个问题、宿主正处在模型调用中——忙标记生效，任务描述**放回队列**；200 毫秒后再试，直到宿主空闲才执行：列目录工具检查新文件，有则写摘要文件并汇报。
4. **用户敲诊断命令**。看到两条任务（一条周期持久、描述完整；那条一次性的已经消失），队列积压为 0。
5. **重启进程**。启动横幅打出"持久任务已恢复 1 个"；那条一次性的提醒没有复活——它本来就不该活过进程。下一个对齐时刻，周期任务照常触发。
6. **追问**。用户问"刚才巡检发现了什么？"模型在共享上下文里翻到了定时任务的执行痕迹，直接作答——**没有人需要复述任何背景**。

## 设计取舍

- **每秒轮询对齐 vs 精确计时器**。为每个任务挂一个精确到点的计时器更"优雅"，但要处理任务增删时的计时器重排、进程休眠后的失准。每秒拿当前时间对齐表达式，实现十行、天然容错——进程被挂起再恢复，下一秒自然接上。教学项目里，简单与鲁棒值这个每秒一次的空转。
- **队列解耦 vs 命中即执行**。命中当场执行少一道队列，但"执行必须等宿主空闲"这件事无处安放。队列是触发与执行之间的缓冲带：忙时攒单、闲时投递、诊断时可观测，三件事都靠它。
- **钩子近似忙标记 + 过期自愈 vs 内核暴露真状态**。让内核暴露"我在忙"的接口当然更准，但要动内核契约；钩子近似零侵入，代价是不准——用"超过时限自动视为空闲"的自愈逻辑把不准确的后果（任务饿死）堵住。**宁可近似 + 自愈，不为准确性侵入内核**，这是能力体系一贯的边界纪律。
- **单线程串行 vs 并发执行**。并发跑多个定时任务快，但共享上下文的并发写是一颗雷，而定时任务之间本来也没有次序承诺。串行慢一点，换来"任何时刻只有一方在改上下文"这条铁律。
- **只持久化持久任务 vs 全量持久化**。把临时提醒也存盘，重启后会复活一堆过期的闹钟；把"是否跨过进程生死"交给登记时的一个开关，让模型按意图选择。数据该活多久，由业务语义决定，不由存储机制决定。
- **错过即过期 vs 补跑队列**。补跑在合规场景（错过一次告警都不能漏）是刚需，但需要记录错过的点位、逐一补偿、还要防止风暴式回放；巡检、日报这类任务，最新的那一次执行才有意义。本模块选择前者，并把"投递失败重投"和"恢复时清触发记录"这两个真正会造成丢失的漏洞单独堵死——**不补跑可以，静默丢不行**。
- **自写表达式解析 vs 引第三方库**。库的功能全（支持高级语法），但高级语法恰恰是教学噪音——本实现遇到不支持的语法就显式报错，把"这里不支持"变成即时反馈而非静默歧义，百余行换来全透明的可控。
- **一次性任务入队即移除 vs 投递成功才移除**。前者的极端情况是"入队后投递一直失败，任务表里已经没有它了"——但实际上任务描述已经在队列里排队重投，真正执行只是延后，不会凭空消失；后者的极端情况更糟：投递成功前任务还挂在表里，可能被同一表达式再次命中、二次入队。宁可让"表里没了、队里还有"这种中间态存在，也不让同一提醒响两次。
- **命中即落盘 vs 退出时统一落盘**。每次命中都重写一次文件看似浪费，但进程被强杀不会留下"内存里已变化、磁盘上还是旧账"的缺口。定时任务最怕的恰恰是"我以为它记着呢"——落盘节奏必须比死亡更勤快。

## 在整个项目中的位置

- **相对模块 15 新增了什么**：15 管的是"智能体是谁"（人格与边界），16 补上的是"智能体何时醒"（时间与主动性）。智能体第一次拥有了**自己启动工作**的能力——不需要人敲第一个字。同时它又是一个标准的"重工具型能力包"范本：三个工具、一条命令、一段提示片段、一组生命周期钩子、一份自持配置，五件套齐整。
- **为后续铺了什么路**：
  - 模块 19 的自治运行是它的直系延伸——把"定时到点唤醒"换成"连续不断地自我驱动"，需要的事件注入、忙碌保护、上下文共享这三件事，本模块已经全部演练过一遍；
  - 模块 17 的多智能体协作里，"成员空闲时轮询任务板、领到任务就跑"的模式与本模块"队列 + 空闲检查 + 在宿主身上跑"同构，只是队列里的东西从时间触发的任务描述换成了别人派来的活；
  - "宿主忙不忙"这个问题在这里第一次被严肃对待，模块 08 后台任务、模块 10 钩子的积累在此汇合——后续任何"从外部往会话里送东西"的需求，都要过这三道门。
