# 模块 08：后台任务

> 把等不完的命令扔给后台守护线程，智能体转头继续干活；结果通过一条通知队列，在下一次模型调用之前自动"寄回"对话——等待的时间第一次变成了可利用的时间。

## 这个模块要解决什么问题

到此为止，智能体所有命令执行都是**阻塞式**的：模型发起命令 → 循环原地等待 → 命令跑完 → 结果回灌 → 模型继续想。装依赖要几分钟、跑一遍测试套件要几分钟、构建镜像更久——这些时间里，模型和循环**双双空转**，什么也不做。

由此产生三个具体矛盾：

- **等待不等于思考停止**。跑测试的五分钟里明明有活可干（顺手修掉代码规范问题），但同步执行的模型只能干等；
- **无法并行**。用户说"一边跑测试一边修 lint"，旧模式只能先干完一件再干另一件，串行吃掉双倍时间；
- **长命令拖垮节奏**。一条跑十几分钟的命令悬在循环中间，对话停摆，体验崩坏。

模块 07 已经能从任务板上看出"哪几件事互不依赖、可以并行"，但并行本身缺一个执行机构。模块 08 补上的正是这块：**让"同时做两件事"从图纸变成现实。**

## 核心思想

一句话：**把时间用满**。手段是经典的"生产者—消费者"解耦：

```
主线程（智能体循环）                    后台守护线程
┌──────────────────────┐          ┌──────────────────────┐
│ 调用后台工具 → 立刻拿到回执  │  交给线程池  │ 线程 A：跑测试套件…        │
│ 继续调别的工具、继续推理     │ ────────► │ 线程 B：装依赖…           │
│                          │          │   干完 → 通知塞进队列       │
│ 下一次模型调用前：            │          └──────────────────────┘
│   排空通知队列 ────────────┐ │                     │
│   把结果注入消息列表          │◄────────────────────┘
│   模型"自然看到"结果，继续干活 │            通知队列（线程安全）
└──────────────────────┘
```

三个关键词：

1. **立即返回**。后台工具不等命令跑完，丢给线程池就回，模型当轮就拿到"已启动 + 任务编号"的回执；
2. **守护线程**。干活的后台线程被标记为守护性质——主程序退出时它们自动消亡，不会把进程吊住；
3. **通知队列**。后台线程与主循环互不认识、互不等待，唯一的接触面是一条线程安全的队列；主循环在**轮与轮之间**排空它。

一句话总结这套机制的角色分工：**工具负责"交出去"，线程负责"干下去"，队列负责"送回来"，注入负责"被看见"**——四个环节各管一段，谁也不阻塞谁。

## 工作原理

### 1. 启动：交出去，立刻回

"把命令放到后台运行的工具"接到一条命令后做四件事：生成一个 8 位十六进制的递增任务编号；把任务（编号、命令、状态置为运行中、开始时间）登记进一张线程安全的任务表；把执行体提交给线程池；**立刻**返回一句"后台任务某某已启动"（命令过长只摘前 80 个字符做摘要）。

关键就在"立刻"：模型这一轮拿到的工具结果虽然不含任何执行输出，却含一个**编号**。这个编号就是后续一切追踪的锚点——想查进度拿它，结果回来时也带着它，对得上号。

把时间轴摊开看，"并行"是怎么发生的（启动三条后台命令为例）：

```
时刻 ─────────────────────────────────────────────────►
主循环   启动A  启动B  启动C  写配置  搜索代码   [调用模型]
            │      │      │                         ▲
后台      A跑…  B跑…  C跑…                       │
            │      │      └─ 完成 ──► 通知入队 ────┤
            │      └──────── 完成 ──► 通知入队 ────┤ 排空队列，注入两条通知
            └─────────────── 完成 ──► 通知入队 ────┘ 模型下一轮一并看到三份结果
```

主循环的时间轴上没有一段是"等待"：提交即返回、接着干别的，结果在它下一次抬头看对话时已经躺在那里。三份通知一次性注入还能省轮次——一次吸收，而非分三次打断。

### 2. 执行：守护线程里的完整流程

后台线程独立跑完整套执行流程，与主循环零交互：

- **选壳**：按当前操作系统挑命令解释器，各类系统都能跑同一条命令；
- **定根**：工作目录固定在项目根目录，后台命令与前台命令看到的是同一个世界；
- **收输出**：标准输出与错误输出分开收集，错误输出单独拼在结果尾部，非零退出码也标注出来——成败信息一个不漏；
- **限时**：最多等 300 秒；到点没跑完就判定超时、**强制杀掉进程**，绝不让一个失控命令永久占着线程；
- **定局**：四种结局——已完成、超时、出错、被中断，连同截断到 5 万字符的结果一起写回任务表。

线程池里的线程全部是**守护线程**。这是刻意为之：如果主流程干完活要退出，而某条后台命令还挂着（等一个永不返回的调用、或陷入死循环），非守护线程会把整个进程吊成僵尸；守护线程则随主程序一起自然消亡——不需要任何清理代码，退出永远是干净的。

### 3. 汇报：一条队列，两种节奏

命令无论成败，线程最后都做同一件事：把一条通知塞进队列。通知里带任务编号、状态、命令摘要（截到 80 字符）、结果摘要（截到 500 字符）——各自限长，保证单条通知不会反过来把上下文撑爆。

这条队列是整个设计的支点：

- **后台线程不需要知道主循环在干嘛**。它不关心模型这会儿是在推理还是在执行工具，塞进队列就完事；
- **主循环不追着线程问**。没有轮询、没有忙等，它只在固定的时机顺路看一眼队列；
- **天然的时机安全**。注入永远发生在两次模型调用之间——绝不会把结果塞进一个正在组装的请求中间，也不会插进一次工具执行的中间。队列这个最简单的线程安全原语，直接消灭了回调地狱和竞态。

### 4. 注入：结果在下一轮"自然出现"

注入挂在那个熟悉的固定入口上——**每次调用模型之前**，内核把消息列表递给所有能力过一遍手。后台能力在这里排空队列：

- 队列是空的 → 原样返回，上下文一个字不动；
- 有通知 → 把全部通知拼成一段**带结构化标记的文本**（每条通知一个块，块内分列任务编号、状态、命令、结果），作为一条用户消息追加到列表末尾，交回内核。

于是模型在下一轮"读历史"时，自然看到后台任务干完了、结果是什么。它不需要被教会"怎么收结果"——结果就长在对话里，和任何一次工具结果没有本质区别。系统提示词里配套写明：**预计超过 5 秒的命令（装依赖、跑测试、构建、克隆仓库这类）都应该交给后台跑**，结果会自动送回来，不必轮询。

这套注入还和模块 06 的压缩共用同一个入口，顺序上也形成默契：通知先进来，压缩再整理——上下文吸收完新信息之后才做瘦身，谁也不干扰谁。

### 5. 主动查询、容量与退场

- **主动查询工具**：自动化注入之外仍保留一个"查看后台任务"的工具——带编号查单个任务的实时状态与已有输出；不带编号则列出全部。当模型想在结果回来之前确认"它还活着吗"，这是确定性的途径。
- **控制台命令**：用户也可以随时敲一条命令，直接看全部后台任务的状态表。
- **容量自洁**：任务表超过 100 条时自动清理——只清已结束的旧任务，按开始时间从最早开始删，运行中的绝不碰。
- **体面退场**：程序关闭时线程池先"温柔"关闭（不再接新活，给在跑的任务 5 秒收尾），超时才强制中断全部。生命周期管理收在能力内部，能力关闭即资源归还。

### 6. 与前台命令工具的分工：不是替代，是分流

引入后台执行之后，原有的阻塞式命令工具并没有被淘汰——两者按"要不要等结果才能走下一步"分流：

- **前台**：快命令，且下一步依赖它的输出。读个文件、改个配置、跑个五秒内的检查——结果马上要用，同步等着反而是最短路径。
- **后台**：慢命令，且当前不依赖它的输出。装依赖、跑全套测试、构建镜像、克隆仓库——结果晚点再说，先把时间让给别的活。

系统提示词里那句"预计超过 5 秒就交给后台"，本质是给模型的一条分流经验法则。判断错了也无大碍：把快命令丢后台，顶多多等一轮通知；把慢命令放前台，代价是整段对话陪它干等——所以阈值定得宽松些，宁可多后台化。

## 一次完整运行的流转

以剧本 s08 为例，用户说："运行测试套件，在跑的时候顺手把代码规范错误修了。"

1. **识别并行机会**。模型看到两件互不依赖的事：跑测试（慢）、修规范（快）。它决定"后台跑测试，前台修 lint"，先调用后台运行工具提交测试命令。
2. **秒回回执**。工具立刻返回：任务编号 00000001 已启动。后台线程此刻已在独立执行测试套件；主循环则完全没有停顿。
3. **前台干活**。模型紧接着调用普通命令工具修代码规范，结果回来：5 个文件里修掉 12 处。这几十秒里，后台的测试一直在跑——**两件事真正同时发生了**。
4. **结果自动寄回**。下一轮调用模型之前，注入钩子发现队列里躺着一条通知：任务 00000001 已完成，47 个用例通过、2 个失败，失败的是哪两个用例也写得清清楚楚。这段内容作为一条用户消息进入上下文。
5. **接力**。模型下一轮一并汇报："规范问题修完了；测试跑完 47 过 2 挂，我来修这两个失败的用例。"——它没有轮询过一次，没有等待过一秒，结果却准时出现在了它需要看见的时刻。

再快闪一个纯并行的剧本，验证"多条通知一次吸收"：用户要求同时等三条不同时长的命令。模型连发三次后台调用，拿到三个编号；接下来的轮次里，通知按各自完成的先后陆续入队；等模型下一次调用模型时，队列里可能已攒了两三条，一次性拼成一段注入——模型一条回复里同时消化三份结果。若它中途想确认某个还在跑的任务，带编号调一次查询工具即可，返回"运行中"和已有的部分输出。

对照串行的旧模式：先干等测试跑完（几分钟）、再修 lint，总耗时是两者之和；现在总耗时约等于**较长的那一件**，而且模型的注意力全程没有离开现场。

## 设计取舍

- **通知队列 vs 直接回调**。让后台线程直接调用主线程的函数，结果送达最快，但回调可能恰好在主线程组装请求的半路上触发，线程安全问题防不胜防；队列让双方只遵守"轮与轮之间"这一个约定，牺牲一点即时性，换来回路清晰、零竞态。
- **守护线程 vs 显式收尸**。非守护线程加超时等待可以更精细地控制关机，但生命周期代码又多又难测；守护线程"主程序一退全家跟着走"，绝大多数场景下行为恰好正确。配合线程池关闭时的 5 秒宽限，正常路径下任务仍能体面收尾。
- **自动注入 vs 只靠轮询**。只给查询工具，模型得记得反复去问，浪费轮次还容易忘；只做自动注入，模型又失去了"主动查一眼"的确定性。两个都要：注入管"结果必达"，查询管"过程可控"。
- **结构化通知 vs 纯文本**。把每条通知包进带字段的结构化块（编号/状态/命令/结果各归各位），模型解析起来不靠猜，后续想按状态过滤、按任务聚合也有的放矢；纯文本省事，但可读性和可处理性都差一截。
- **限长与限量无处不在**。结果截到 5 万字符、通知截到 500 字符、命令摘要截到 80 字符、任务表封顶 100 条、单条命令 300 秒强杀——后台化解放了时间，也放大了失控的每一维度，所以每一处都设了闸门。**并行必须以可控为前提。**

把这张防护网单独列出来看更清楚——每一维失控各有一道对应的闸：

| 失控维度 | 若不设防会怎样 | 本模块的闸门 |
|---|---|---|
| 时间 | 一条死循环命令永久占住线程 | 300 秒超时，到点强制杀进程 |
| 体量 | 一条刷屏命令把上下文灌爆 | 结果限 5 万字符、通知限 500 字符 |
| 数量 | 任务表无限膨胀耗尽内存 | 封顶 100 条，自动清最旧的已结束任务 |
| 生命周期 | 主程序退出了进程却挂着不退 | 守护线程随主程序消亡，线程池 5 秒宽限后强停 |

## 在整个项目中的位置

- **相对模块 07 新增了什么**：07 解决"计划的结构"（什么该先做、什么能同时做），08 解决"时间的结构"（同时做的事怎么真正同时做）。任务板上的"就绪且互不依赖"只是并行资格，后台执行机构才把资格兑现成并行事实——"边跑测试边修代码"从此是一句话的事。
- **为后续铺了什么路**：
  - 模块 16 的定时任务本质是"到点自动往队列里送活"的后台执行变种；
  - 模块 17 的多智能体团队，把"多个后台线程"升级成"多个各带循环的智能体"，而通知队列的通信模式原样升级成智能体间的消息机制；
  - 模块 19 的自治长循环，靠的正是"后台跑长活 + 主循环持续推进 + 结果注入再决策"这套永不停摆的节奏；
  - 模块 20 的工作树隔离，则为"多个后台任务同时改文件会互相踩"提供了空间上的答案——时间的并行（08）与空间的隔离（20）合在一起，才是完整的并发工程。
