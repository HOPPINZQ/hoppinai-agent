# 模块 02：工具家族

> "几个各司其职的工具，覆盖九成以上的编程任务。" —— 循环一点没变，变的是模型手里那只手的精细程度：从一把万能锤，变成一整面工具墙。

本文建立在模块 01 之上：双层循环、消息列表、停止原因、结果回灌这些机制原样沿用，本模块只做一件事——把"一个命令行工具"扩展成"一组专用工具 + 两件搜索武器"。

## 这个模块要解决什么问题

模块 01 证明了命令行万能，但"万能"的另一面是"全都别扭"：

- **引号与转义地狱**。让模型用命令行读写文件，它得正确处理嵌套引号、特殊字符、多行文本。文件内容里一旦出现引号或美元符号，拼出来的命令轻则写错内容，重则执行了意料之外的语句。实践中这是模型犯错最多的一类地方。
- **读取不可控**。用命令行看文件，输出多长、从哪开始、有没有截断，全看命令怎么写；模型经常读到一半内容就自以为看全了。
- **精确修改做不到**。想改文件里的某一处，靠命令行的文本替换工具遇到特殊字符就崩，而且替换错了没有任何回滚。
- **安全面失控**。每一次文件操作都是一次不受约束的外壳调用：路径可以指到机器任何角落，没有校验、没有边界。
- **找代码靠运气**。在陌生项目里定位"哪个文件包含某个函数"，靠模型一条条猜路径去列目录，既慢又费上下文。

解决方案不是给命令行打补丁，而是把这些高频操作从外壳里请出来，做成参数结构清晰的专用工具。

## 核心思想

从单一工具到工具家族：**加工具不需要改循环**。智能体内核只认一张工具清单，每个工具用同样的三件套登记——名字、描述、参数说明（哪些必填、什么类型、取值范围）。调度器按名字在线性表里查找，找到就执行，然后把返回的字符串当作工具结果回灌。

于是"扩能力"被降格成"加登记项"：写一个参数说明、写一个执行函数、往清单里加一行。循环体、停止原因判断、结果回灌逻辑，一个字符都不用动。本模块最终登记了六件工具：

| 自然语言描述 | 解决的问题 |
|---|---|
| 执行命令行的工具 | 跑程序、装依赖、查进程——一切非文件IO的系统操作 |
| 读取文件的工具 | 带着明确语义读整个文件，不再拼命令 |
| 写入文件的工具 | 创建或整体覆盖文件，自动补建父目录 |
| 编辑文件的工具 | 精确替换文件中的一段文本 |
| 按名字模式找文件的工具 | 用通配模式列出匹配的文件与目录 |
| 搜索代码内容的工具 | 用正则在全项目范围内定位代码行 |

前四件覆盖了绝大多数编程任务；后两件是给"在陌生代码库里导航"配的眼睛。工具数量是刻意克制的——工具越多，模型要在越多选项里做选择，选错的概率随之上升；更少的工具也意味着更少的参数说明要维护、更少的边界情况要处理。

## 工作原理

### 1. 工具登记表与统一调度

每个工具在登记表里是同等地位的一条记录。请求模型时，整张表连同各自的名字、描述、参数说明一起发给模型；模型回复中的每次工具调用只带一个名字和一组参数，调度器拿名字去表里线性匹配：

```
模型回复：调用"编辑文件的工具"，参数{文件路径, 旧文本, 新文本}
              │
              ▼
   在登记表中按名字查找 ──找不到──▶ 回灌"工具没有找到"
              │找到
              ▼
   把参数整理成工具期望的形式 ──▶ 执行 ──▶ 返回字符串
              │
              ▼
   作为该次调用的专属结果回灌，请求下一轮
```

参数说明是协议中立的一份描述，由各协议适配层翻译成自家格式。这带来一个重要性质：模型没法传进格式错乱的输入——参数类型、必填项在执行前就被校验，一整类"模型输出格式漂移导致解析失败"的问题被直接消灭。

### 2. 一个工具的两种接入姿势

登记表对"工具执行体"的形态不做假设，留了两种接法：

- **松散式**：执行函数直接收一段原始文本参数，自己负责解析。灵活，适合参数结构特殊的工具（比如模块 01 那个命令行工具的兼容接法）。
- **紧凑式**：参数说明里声明的结构直接对应一个带类型的数据骨架，执行函数拿到的是已经装填好的对象。少写一遍手工解析，类型对不上在进入执行体之前就被挡下。

新写的文件工具全部采用紧凑式。这不是代码洁癖：工具越写越多之后，"解析参数"这段谁都要写的胶水会重复出现，且每份都有自己的坑；统一由登记表在入口处完成转换，工具作者只写业务逻辑。

### 3. 文件读写编辑三件套

**读取**最简单：把路径解析成实际位置，整读成文本返回。语义清晰，输出可预期。

**写入**负责"从无到有"和"推倒重来"：自动创建缺失的父目录，把内容以统一编码整体写入，返回"写入了多少字节到哪个文件"这类确认信息——确认信息看似啰嗦，实则是给模型的定心丸，让它不必再读一遍文件来验证。

**编辑**是三件套里最讲究的，它要求模型给出"旧文本"和"新文本"，然后执行一次受控替换：

```
读原文件 ──▶ 文件不存在且旧文本为空？──是──▶ 直接创建新文件
                │否
                ▼
        统计旧文本出现次数（先做空白归一化）
                │
     ┌──────────┼──────────────┐
   出现0次    出现1次         出现多次
     │          │              │
  报错"没有   执行替换       报错"出现多次，
  找到旧文本"  并保留原        应该只有一次"
              文件换行风格      │
                │              │
                └──────┬───────┘
                       ▼
            每种结果都以可读文本回灌给模型
```

两处细节值得展开。一是**空白归一化**：匹配前把回车换行统一成换行、制表符折算成空格，匹配后再按原文件的换行风格写回——这样模型因为缩进风格或换行符差异而"看走眼"的编辑不会莫名失败，文件也不会被悄悄改掉换行风格。二是**唯一性约束**：旧文本必须恰好出现一次才动手，零次或多于一次都拒绝执行。宁可让模型带着明确的错误信息重试，也不替它赌一个"可能改错地方"的结果。

### 4. 两件搜索武器

**按名字找文件**：接受一个通配模式，支持单个星号、递归双星、按扩展名过滤、只列目录等常见形态；结果统一换成相对路径、正斜杠分隔、排序输出，目录带斜杠标记。这给模型一双"看目录结构"的眼睛，而不用拼一条列目录命令再去解析文本。

**搜内容**：接受正则表达式和可选的搜索路径、文件类型过滤、大小写开关，返回"路径:行号:内容"格式的匹配行。工程上有三层保障：

- **引擎优选**：优先使用本机安装的高速搜索工具（按内置副本、环境变量、系统路径的顺序定位），没有就自动降级到内置的纯实现，保证工具在任何机器上都可用。
- **结果限流**：最多返回五十行匹配，超出则截断并注明总数；单次结果还有字节级上限，防止一个宽泛的正则把上下文吞掉。
- **进程加固**：搜索以子进程方式运行时，错误输出由独立线程持续排空（防止管道写满互相等死）、三十秒超时强杀、超限即中断并提示模型缩小搜索范围。

搜索工具是这六个里对"智能体体验"影响最大的一个：它把"找东西"从反复试错变成一次查询，省下的不只是时间，更是大量本会被中间输出占掉的上下文空间。

### 5. 路径沙箱

所有文件操作都过同一个路径解析关卡：

```
模型给的路径
    │
    ├─ 相对路径 ──▶ 以工作根目录为基准拼接 ──▶ 归一化（消解"上一级"段）
    │                                            │
    └─ 绝对路径 ──▶ 直接归一化 ──────────────────┤
                                                 ▼
                              校验结果是否仍落在工作根目录之内
                                     │是        │否
                                     ▼          ▼
                                   放行     拒绝并说明越界
```

相对路径允许模型用简洁写法操作项目内文件；但一旦解析出来跑到了根目录之外（比如靠一串"上一级"跳出去），就拒绝执行并返回原因。绝对路径同样要求落在根目录内。另有一个显式的无限制开关供特殊情况使用——默认关闭。这就是模块 01 里"每次命令都是不受约束的安全面"的答案：把高频操作收进专用工具后，边界校验有了统一的收口位置。

### 6. 错误的形状：让失败可读、可恢复

六个工具的失败全部以一句话文本回灌："路径不能为空"、"旧文本没有在文件里"、"旧文本出现了两次"、"路径必须在项目目录内"、"搜索超时，请缩小范围"……这些文案是写给模型看的，不是写给日志看的。模型读到"出现了两次"，下一轮就会带上更长的上下文片段重新编辑；读到"越界"，就会换相对路径。工具层把失败原因说清楚，智能体循环才能把失败变成迭代。

## 一次完整运行的流转

场景剧本：用户要求"给那个脚本文件加一个接受名字参数的问候函数"。

1. **用户消息入列**，发起第一次请求。工具清单里有六件工具，模型这次没有选命令行，而是选了**读取文件的工具**——专用读取工具提供了更清晰的文件访问语义，模型知道"看文件内容"该用它。
2. 执行读取，文件当前内容（一行打印语句）作为工具结果回灌。
3. 第二次请求。模型决定**整体重写**：调用写入文件的工具，一次性给出包含新函数的完整文件内容。写入工具返回"文件写入成功"的确认。
4. 第三次请求。模型只回文本："我已经更新了这个文件，添加了一个接受名字参数的问候函数。"停止原因为正常结束，循环退出。

对比模块 01 里同样的场景：那需要拼一条带转义的写入命令、再拼一条带转义的查看命令，任何一处引号处理失误都会导致返工。这一轮里模型没有写过一条命令——它用三个结构化的调用干净利落地完成了"读、写、汇报"。四个（六件）工具胜过一个工具的道理就在这里：不是能力变多了，而是高频操作的表达变可靠了。

## 设计取舍

- **小工具家族，而不是大而全。** 有人会问为什么不一步到位加上"列目录""发请求""查数据库"。原因是命令行已经覆盖这些用例，专用化只对"高频且易错"的操作才划算；每多一件工具，模型的选择成本和维护成本都在涨。后续模块确实还会加工具，但每一个都遵循同样的准入逻辑。
- **严格的参数说明，而不是自由文本解析。** 另一条路是让模型自由输出、再用正则去抠内容——那很脆弱，模型换个措辞解析器就崩。结构化参数说明用一点灵活性换来了可靠性：输入在校验阶段就定型，执行函数拿到的永远是符合约定的东西。
- **编辑工具宁可拒绝，不可猜错。** "旧文本必须唯一匹配"这条硬约束经常让模型第一次编辑就失败，看似不友好，实则把歧义暴露在执行前而不是写坏文件后。配合空白归一化，大多数"看起来该匹配"的情况都能匹配上，剩下的失败都是真歧义。
- **搜索工具双引擎。** 依赖外部高速搜索工具能拿到最好的性能，但要求每台机器都装好不现实；内置纯实现保底但慢。优选 + 降级的组合让工具"永远能用，能用得快就用得快"。
- **沙箱默认收紧，例外显式开启。** 工作目录限制会偶尔挡住模型的合理请求（比如它想看项目外的一个配置），但默认姿态应该是安全的；真需要放开时由使用者显式打开开关，责任清晰。
- **模型依然是唯一的决策者。** 本模块依旧没有路由器、没有决策树、没有工作流引擎。智能体行为从模型中涌现，而不是由框架定义——程序只是把模型和工具接起来的管道。
- **工具描述本身是提示工程的一部分。** 六件工具的描述文案里埋着行为引导：命令行工具的描述里写明"当前处于哪个操作系统""打不开路径就试试绝对路径"；写入工具强调"会自动创建文件"。模型对工具的选择和用法，很大程度由这几句话决定——调工具行为，先调描述。
- **写入的确认信息是给模型的反馈，不是给用户的日志。** "写入了多少字节到哪个文件"让模型不必再读一遍文件来确认成功，省掉一整轮往返。工具结果的每个字都占上下文，也都是一次潜在的省轮次机会。

## 在整个项目中的位置

模块 02 确立了此后所有能力扩展的基本套路：**登记表 + 统一调度 + 结构化参数 + 文本回灌**。后面技能、待办、子智能体、任务委派，全部是往这张表里加登记项，循环再也没有变过。

它还补齐了两块地基：

1. **搜索与文件导航**让智能体第一次能在"陌生的大型代码库"里干活，而不是只在玩具目录里列文件——模块 03 的多步规划、模块 04 的子任务委派，都默认模型已经具备"自己找资料"的能力。
2. **路径沙箱与工具级校验**确立了"安全约束做在工具层"的原则，后续的权限能力在此基础上叠加可配置规则，而不是另起炉灶。

一句话概括这个模块的遗产：循环是骨架，工具是肌肉——从这里开始，项目的演进方式就是不断地、有节制地往骨架上长肌肉。
