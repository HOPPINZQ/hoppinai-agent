# 模块 17：智能体团队

> 从单打独斗到协作团队：负责人把大任务拆给多个队友并行去干，每个队友跑自己的智能体循环，彼此只通过一套基于文件的"消息总线 + 邮箱"异步通信。

## 这个模块要解决什么问题

到上一模块为止，智能体已经能被定时唤醒干活了，但它始终只有"一个人"：

- **上下文装不下大任务**。一个横跨数据库、接口、测试的重构，做到第三步时第一步的细节早已被挤出上下文。单循环只能串行处理，注意力被摊薄。
- **子智能体是"一次性临时工"**。前面模块引入的子智能体确实能把一件子事交出去，但它是同步的：主循环停下来等它干完，交回一段结论就销毁。你没法在中途给它补充指示，它也没法在干完之后再主动说一句。
- **并行需求无处安放**。"同时检查测试和更新文档"这类互不依赖的活，在单循环里只能排队。

这个模块要补的是"能通信的长期工"：每个队友有自己的上下文、自己的工具、自己的循环，生命周期横跨多轮对话；负责人随时可以派活、追问、补充材料，队友随时可以汇报进度。

## 核心思想

三个词：**隔离、异步、邮箱**。

```
   用户 ──> 负责人（前台主循环，跟你对话的这个）
                │
                │ 拉起队友（立即返回，不等待）
                ├───────────────┐
                ▼               ▼
          队友 A 后台循环    队友 B 后台循环
          自己的上下文       自己的上下文
          自己的工具子集     自己的工具子集
                │               │
                │  写入对方的收件箱 │
                ▼               ▼
        ┌───────────────────────────────┐
        │  消息总线：每人一个收件箱文件      │
        │  负责人 / 队友A / 队友B ...      │
        └───────────────────────────────┘
                ▲
                │ 负责人每轮调用模型前，把收件箱整箱取走并注入对话
```

- **隔离**：队友与负责人不共享任何对话记忆，也不共享工具表。这既是安全边界（队友只能干派给它的事），也是正确性边界（并行执行流互不踩上下文）。
- **异步**：拉起队友这个动作立即返回。负责人继续回应用户、继续干自己的事，队友在后台慢慢跑。
- **邮箱**：两个隔离的执行流之间，唯一的通道就是收件箱。发消息 = 往对方收件箱末尾追加一条带发送方、接收方、正文、类型、时间戳的记录；读消息 = 一次取走全部并清空。

## 工作原理

### 1. 两个角色：负责人与队友

**负责人**就是一直跟你对话的那个智能体。它在原有基础工具之外多了三件团队工具：

- **拉起队友**：给一个名字、一段角色描述、一份具体任务说明，后台立刻多出一条执行流；
- **发送消息**：把一段话投进某个队友（或自己人）的收件箱；
- **查收邮箱**：主动看一眼自己收件箱里的未读消息。

**队友**不是一个新概念，而是一套完整但缩小版的智能体循环：同样有系统提示词、对话上下文、工具调用、多轮循环。差别有三处——

1. 它的系统提示词是按"你叫什么名字、你的角色是什么、你的任务是什么、干完要汇报"现场拼出来的；
2. 它的工具是负责人给的一个**子集**（教学版里是读写文件和执行命令这类干活工具；它的系统提示词里另外声明了发消息这个汇报通道）；
3. 它跑在一条独立的后台执行流里，跑完就结束，不占负责人主循环的时间。

负责人与队友在系统提示词里被明确告知各自的纪律：负责人"派完活不要干等，下一轮自然会收到回执"；队友"不要反复请示，尽可能自主完成"。

### 2. 消息总线：一人一箱，读即消费

消息总线的实现刻意做到极简：在工作区下一个隐藏目录里，**每个成员对应一个收件箱**，收件箱是"一行一条记录"的追加式文本。

- **发送**：把消息（发送方、接收方、正文、类型、时间戳）序列化成一行，追加到接收方的收件箱末尾。目录不存在就顺手建好，所以第一次通信前不需要任何初始化仪式。
- **读取**：把整个收件箱的行全部解析出来，然后**立刻清空文件**。

"读即消费"是这里最关键的一条语义：同一条消息绝不会被消费两次。负责人和队友都在各自循环里轮询自己的箱子，如果读到的消息还留在箱子里，下一轮就会被重复注入对话，上下文立刻被垃圾填满。

注意消息类型这个字段：本模块里绝大多数消息都是普通消息，但它为下一个模块的"协议消息"（关停请求、审批请求……）预留了空间。收件箱是无状态的纯文件，任何一方拿同一个总线实现去读写，看到的就是同一批邮箱——这让后面的协议能力可以作为一个独立能力包插进来，却和团队能力共享同一套通信设施。

### 3. 拉起队友：独立的上下文与工具子集

拉起队友这条链路做了四件事：

1. **现场构造一个缩小版智能体**：把负责人正在用的模型接口、采样温度传进去，配上装配方预先圈定的队友工具子集；
2. **独立的对话上下文**：从一张白纸开始，把负责人派下来的任务说明作为第一条用户消息放进去；
3. **线程级身份标记**：把队友的名字记在它自己这条执行流的私有上下文里。之后这个队友发出的任何消息，发送方都自动是它的名字；而负责人主线程里发出的消息，发送方自动是"负责人"。同一条发消息逻辑，不用传参就能区分"谁在说话"；
4. **立即通知上线**：队友的执行流一启动，先给负责人收件箱投一条"我上线了"，让负责人知道这个队友已经活着。

因为队友是后台执行流，拉起动作立刻返回"已启动"，负责人完全不会被阻塞。多个队友就是多条并行执行流，各自有各自的上下文与邮箱。

### 4. 队友的循环：消费邮箱 → 干活 → 收尾汇报

队友的循环是标准智能体循环外面套了一层邮箱消费，每一轮做五件事：

```
每一轮开始
   │
   ├─ ① 读自己的收件箱（读即消费）
   │      ├─ 收到"关停请求" → 回一句"收到，退出"，直接结束
   │      └─ 收到普通消息   → 拼成新的用户消息注入自己的对话
   │
   ├─ ② 调用模型（带上自己的系统提示词与工具子集）
   │
   ├─ ③ 打印文本回复；逐个执行模型要的工具调用，把结果回灌
   │
   ├─ ④ 判停：本轮没有任何工具调用 → 结束；
   │        结束原因不是"还要继续调工具" → 把结果回灌一次后结束；
   │        轮数用完（上限 10 轮）→ 强制结束
   │
   └─ ⑤ 收尾：如果全程没主动发过消息，
          把最后一轮的文本补一条"<名字> 已完成：<摘要>"发给负责人
```

第 ⑤ 步是**兜底汇报**，它保证了"即使队友忘了汇报，负责人也一定能拿到结果"。如果队友中途抛了异常，异常文本同样会被投进负责人邮箱——负责人至少知道这个队友是带着错误退出的。

### 5. 负责人一侧：每轮调用模型前自动收信

负责人不需要频繁手动查邮箱。团队能力向内核注册了一个**模型调用前钩子**：每次（包括工具循环内的每一轮）调用模型之前，先取走负责人收件箱里的所有消息，逐条包装成"［来自某人］内容"的用户消息追加到本轮上下文尾部，再把替换后的上下文交给模型。

这个设计的巧妙之处在于**内核不需要知道邮箱的存在**：钩子只是"拿到当前上下文列表，返回一个可能更长的新列表"。邮箱、消费、注入，全部封在团队能力内部。于是：

- 队友干完活的回执，会在负责人的**下一轮**对话里自然出现；
- 负责人也可以随时用"查收邮箱"工具主动看一眼，消费语义与钩子一致，不会重复。

### 6. 防跑飞与生命周期管理

多一条并行执行流，就多一份跑飞的风险。本模块的防护有四道：

- **轮数硬上限**：队友单次任务最多 10 轮模型调用，用完强制收尾并汇报，防止某个队友无限打转；
- **判停条件**：本轮没有工具调用、或模型明确表示不需要再调工具，循环即止，不空转；
- **异常兜底**：任何异常都转成一条错误消息投回负责人邮箱，队友安静退出；
- **统一收尾**：负责人进程结束时，所有还活着的队友执行流会被逐一打断，不留僵尸线程。

此外还有一个团队状态的斜杠命令：列出已拉起的所有队友及其存活状态，方便观察"谁还在跑、谁已经结束"。

## 一次完整运行的流转

以"给项目补一个建表脚本"为例：

```
你：让队友小艾帮我把数据库表结构整理成一个建表脚本

负责人：好，我拉起小艾（角色：数据库工程师）……已启动
        （与此同时：负责人继续回应你，比如解释接下来的安排）

        └─ 小艾后台启动
             ├─ 给负责人发："我上线了"
             ├─ 第 1 轮：读项目里的模型定义文件
             ├─ 第 2~5 轮：写脚本、自查语法、修正字段类型
             └─ 第 6 轮：没有更多工具调用，循环结束
                  └─ 兜底汇报进负责人邮箱："小艾 已完成：建表脚本已写入项目，共 5 张表"

你：跑得怎么样了？

负责人：（调用模型前，钩子先收信，回执注入本轮上下文）
        小艾已经完成，脚本里建了 5 张表，其中订单表我加了索引……
```

关键观察点：

- 负责人从"拉起"到"收到回执"之间**没有等待**，它一直在响应你；
- 小艾的 6 轮调用发生在后台，负责人主循环完全无感；
- 回执不是靠你手动查到的，而是下一轮对话自动出现的；
- 如果同时拉起小艾和小博，两条后台流并行推进，各自只有各自的邮箱与上下文，互不知晓也互不干扰。

## 设计取舍

- **文件邮箱，而不是内存队列或网络通信**。文件是最低 common denominator：无状态、可跨能力共享、崩了还能翻看现场。代价是**读即焚**——消费完就清空，事后想复盘"队友到底说过什么"只能看控制台日志；也没有历史检索能力。
- **读即消费，而不是读后标记**。实现只要一行"清空文件"，且天然防重复注入。代价是没有"未读回执"概念，消息没被消费就被覆盖的场景不存在，但误清空也无法恢复。
- **队友工具是子集，而不是全量**。最小权限：队友不需要改团队结构、不需要定时任务、不需要协议工具。好处是队友的系统提示词短、误调用面小；代价是队友能力受限，遇到超出子集的活只能汇报而非自救。
- **轮数上限而不是时间上限**。轮数与模型调用次数直接挂钩，是"花销"最直观的代理指标。教学版没有做真正的预算控制，轮数上限就是预算。
- **负责人只在被唤醒时收信**。钩子挂在模型调用前，意味着如果用户一直不说话、也没有定时任务触发，队友的回执会安静地躺在邮箱里。这是异步设计的固有延迟，下一个模块的自主运行会缓解它。

## 在整个项目中的位置

- **相对模块 16（定时调度）**：16 解决"没人说话时谁唤醒智能体"，17 解决"唤醒之后一个人干不过来怎么办"。定时能力在本模块被原样保留，定时产生的提示同样走邮箱进入对话。
- **相对模块 04（子智能体）**：子智能体是同步的一次性调用，交回结论即销毁；队友是异步的长期执行流，可多轮通信。两者不是替代关系——顺手的小事仍该用子智能体，需要来回沟通的并行任务才值得拉队友。
- **为模块 18（团队协议）铺垫**：消息里的"类型"字段已经预留，收件箱里即将流动的不只是闲聊文本，还有带唯一编号的关停请求与审批请求。
- **为模块 19（自主运行）铺垫**：队友循环里已经留好了"空闲时问一句还有没有活"的回调位，本模块它还是空的，下一个模块会往里塞一个任务板。
- **为模块 20（工作区隔离）铺垫**：多个并行执行流同时读写同一个目录，迟早互相覆盖——正是这个隐患催生了按任务隔离工作副本的需求。
