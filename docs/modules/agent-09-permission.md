# 模块 09：权限系统

> 给自主性装上刹车：每一次工具调用在真正执行之前，都要先通过三道权限闸门。

## 这个模块要解决什么问题

前几个模块里的智能体已经能执行命令、读写文件、派出子智能体、在后台跑任务——它的"手"越来越长，却没有任何东西检查这只手伸向哪里。模型偶尔会做出危险动作：

- 一条递归强删命令，可能把整块磁盘清空；
- 提权命令、格式化盘符，一旦执行不可挽回；
- 写文件时带上"向上一级"的路径，内容就落到了工作区之外；
- 更多时候是灰色地带：删一个日志文件、强制推送一个分支——不算灾难，但用户未必愿意让它悄悄发生。

核心矛盾在于：智能体的价值来自自主行动，而自主行动的风险恰恰是"不等用户确认就行动"。把所有操作都禁掉，智能体退化成聊天机器人；全都放行，一次幻觉就足以造成不可逆的伤害。这个模块在两个极端之间架起一条流水线：动作发生之前，先过三道闸门。

## 核心思想

**拦截发生在执行之前；拒绝不是终点，而是信息。**

两条原则贯穿整个模块：

1. **闸门只读，执行在闸门之后。** 判定逻辑只能看到"工具名 + 参数文本"，它自己不碰文件系统、不碰终端。所以闸门永远不会造成伤害，也永远不会被绕过——因为它是内核在执行前无条件调用的，不是模型"自愿遵守"的约定。
2. **拒绝要回灌，而不是终止。** 被拦截的调用既不让循环崩溃，也不被静默丢弃：拦截原因会作为这次调用的"结果"原样交还给模型。模型读到"已拒绝"加上具体理由，就知道此路不通，会换一条路或者向用户解释。权限系统因此不是一堵墙，而是一个让模型学会守规矩的反馈回路。

## 工作原理

### 一、拦截点：内核在工具执行前预留的检查位

内核的智能体循环在拿到一轮工具调用之后，对每个调用依次做两件事：先询问所有已注册能力"这次调用可以执行吗"，只有全部放行才真正执行；任何一方给出非空答复，即视为拦截——真实执行被跳过，答复文本被当作这次调用的结果回灌，控制台同时打印一行"拦截"提示。

判定逻辑本身不写在内核里，而是收拢在一个可整体拔除的能力包中：能力向内核注册一个"工具执行前"钩子，内核完全不感知权限的任何细节。删掉能力目录和装配处的一行注册，智能体就退回无护栏状态；把目录复制进别的模块再加一行注册，护栏就跟着搬过去。权限是横切关注点——它不产生任何新工具，却作用于所有工具的执行前，这正是钩子挂载点与工具注册的本质区别。

### 二、三道闸门的流水线

判定按固定顺序过三关，任何一关拒绝即短路，全部通过才放行：

```
          工具调用（工具名 + 参数文本）
                      │
   ┌──────────────────▼───────────────────┐
   │ 闸门一：危险命令黑名单（只审命令执行）    │
   │   递归强删 / 提权 / 格式化盘符 /         │
   │   强删系统盘 / 写物理设备 / 炸弹循环      │
   │        命中 ───► 拒绝（不再往下走）      │
   └──────────────────┬───────────────────┘
                      ▼ 通过
   ┌──────────────────────────────────────┐
   │ 闸门二：规则检查（只审三个文件工具）       │
   │   路径解析、规范化后必须仍落在工作目录内   │
   │        命中 ───► 拒绝（不再往下走）      │
   └──────────────────┬───────────────────┘
                      ▼ 通过
   ┌──────────────────────────────────────┐
   │ 闸门三：破坏性命令确认（只审命令执行）     │
   │   删除 / 强制推送 / 硬重置 ───► 问用户   │
   │     明确肯定答复 ───► 放行              │
   │     其他任何输入（含直接回车）──► 拒绝    │
   └──────────────────┬───────────────────┘
                      ▼
                  真正执行工具
```

各闸门的管辖范围划分得很清楚：

| 工具类型 | 要过哪些关 |
|---|---|
| 命令执行工具 | 闸门一（黑名单）+ 闸门三（破坏性确认） |
| 读、写、改三个文件工具 | 闸门二（路径越界） |
| 其余所有工具（搜索、列目录、待办、子智能体等） | 不做检查，直接放行 |

三关的"严重程度"递减、"触发频率"递增：第一关拦的是绝不允许发生的事，第二关拦的是越界的事，第三关把判断权交还给用户。整体立场是保守的——第三关里用户直接回车、不给出明确肯定答复，也按拒绝处理；在无法弹出确认的非交互环境里，破坏性命令一律拒绝而不是放行。

### 三、黑名单：绝对不许发生的事

第一关维护一张十条左右的硬编码模式表，逐条与命令文本做不区分大小写的匹配：

- 递归强删根目录、家目录、当前目录通配符；
- 提权命令（临时切换管理员身份的两种写法都在列）；
- 窗口系统下的强制静默删除系统盘、递归删除系统盘；
- 格式化盘符；
- 把数据直接写进物理磁盘设备；
- 自我复制的炸弹循环。

命中的命令在抵达终端之前就被拦下。拒绝理由会带上命中的具体规则与原始命令文本——这是给用户看的排障信息，让他知道是哪条规则、拦下了什么，而不是一句干巴巴的"不允许"。

黑名单的另一层价值是**表达力**：它把"这个智能体绝不做的事"写成了一张可读的清单。用户看一眼就知道边界在哪，模型（通过系统提示词）也知道。

### 四、路径越界：规范化之后再看住在哪

第二关只检查读、写、改三个文件工具的路径参数，分两步走：

1. **解析并规范化**：把路径折算成绝对路径，连续的"向上一级"在这一步被折叠掉；
2. **判断归属**：折叠后的路径必须仍落在工作目录之内，否则拒绝。

规范化是关键一步——"工作目录/上级/秘密文件"这种写法在字符串层面看不出问题，折叠之后立刻现形。这也是为什么不能简单地用"路径里有没有两点一杠"来做判定：必须先折算再判断，否则稍微绕一下的写法就能骗过检查。

解析失败时按越界处理——**宁可错杀，绝不因异常放行**。这条"拿不准就拒绝"的原则贯穿整个闸门设计：任何没有把握的情况，答案都是拒绝。

### 五、破坏性确认：把最后的选择权交给用户

第三关维护另一张模式表，收录"有破坏性、但有时确实该做"的操作：各类删除命令、强制推送、硬重置、把文件移进黑洞设备。命中后不直接拒绝，而是停下来问人：

- 提示以高亮颜色打印"权限确认"字样，并**原样展示即将执行的完整命令**——用户看到的是命令本身，不是模型的转述；
- 只有明确输入那个约定的肯定答复（大小写均可）才放行；
- 直接回车、或输入任何其他内容，一律按拒绝处理——默认答案是"不"；
- 在没有控制台输入可用的非交互环境（比如被脚本拉起运行），直接拒绝，理由写明"需要用户确认但当前为非交互模式"。

值得强调的是：第三关确认的粒度是**每一次调用**，而不是"这个会话里允许过一次就永远放行"。同一个删除模式第二次出现时依然会重新问——这是刻意的保守（见设计取舍）。

### 六、拒绝之后：把"此路不通"教给模型

拒绝不是流程的终点。拦截文本统一以固定前缀开头、后接具体原因，被包装成这次调用的结果消息进入上下文，循环照常继续。模型读到的信息是"这个动作被拒绝了，原因是……"，而不是一个含糊的失败。

与此同时，能力包会向系统提示词注入一段静态说明，告诉模型三件事：

- 存在三道闸门，任何工具调用都会先被审查；
- 被拒的结果以什么前缀开头，读到它意味着什么；
- 最重要的一条：**不要尝试绕过权限规则**，被拦了就如实向用户解释原因、建议替代方案。

没有这段配套提示，模型很容易把拒绝当成一次偶发故障，原样重试形成死循环——权限系统拦住了危险的命令，却可能制造出更烦人的循环。

### 七、如何验证这套护栏

| 对它说 | 期望 |
|---|---|
| 执行递归强删临时目录的命令 | 闸门一拦截 |
| 执行提权更新软件的命令 | 闸门一拦截 |
| 把内容写到工作目录之外 | 闸门二拦截 |
| 删除某个具体的旧日志 | 闸门三弹出确认提示 |
| 读取工作目录内的普通文件 | 全部放行，正常执行 |

## 一次完整运行的流转

用户说："帮我把构建产物清理一下，顺便把临时目录也删了。"

1. 模型发起一次命令执行调用，参数里是一条递归删除临时目录的命令。
2. 内核在执行前询问所有已注册能力的工具执行前钩子，权限能力接管，进入闸门流水线。
3. 闸门一：命令里包含递归强删根目录的写法——命中黑名单，流水线立刻短路，返回带固定前缀的拒绝文案。真实执行从未发生，终端完好无损。
4. 内核把拒绝文案当作这次调用的结果放进上下文，控制台打印一行"拦截"，随后带着结果再次请求模型。
5. 模型读到"已拒绝"及原因，明白是命令本身触发了黑名单，于是改口问用户："临时目录里哪些文件还需要保留？"——而不是原样重试。
6. 用户指定了具体文件。模型发起第二次调用：删除某个具体的旧日志。这次闸门一放行（不在黑名单），闸门二不涉及（不是文件工具），闸门三命中"删除"模式，控制台弹出高亮的确认提示，展示即将执行的完整命令。
7. 用户输入肯定答复，闸门三以放行结束，命令真正执行，结果回灌，循环继续。
8. 假如用户此刻直接回车，命令会被拒绝，模型收到"用户拒绝执行命令"的文案，转而提出替代方案（比如把文件移进回收目录而不是删除）。

整个过程中，用户的参与被压缩到唯一必要的时刻：真正有破坏性、又不在黑名单里的那一步。而模型的"错误"（想删临时目录）被转化成了一次澄清式提问，任务本身没有中断。

## 设计取舍

**为什么三关而不是一关？** 只留黑名单，灰色地带无处安放；只留询问，用户会被高频弹窗轰炸到机械按键，护栏形同虚设。三关把"绝对禁止""规则禁止""人类裁决"分层，让人的注意力只花在刀刃上。代价是规则表需要维护，而且"哪些工具归哪关管"的边界需要向使用者解释清楚。

**为什么每次都问，而不是记住选择？** 引入"会话内记住"就必须回答：按什么粒度记（按原样命令？按模式？按目录？）、记多久、怎么撤销。这些都没有显然正确的答案，而答错的代价是把护栏变成一次性橡皮章。当前实现选择最保守的路线：宁可多问一次，也不让任何一次破坏性操作悄悄溜过。白名单放行、会话内记忆选择，是留给后续模块的扩展空间。

**为什么路径规则只看文件工具？** 因为文件工具的路径是结构化的单一参数，判定可靠；而命令文本是自由语言，想从中可靠地抽取出"到底访问了哪些路径"需要真正的语法解析。用粗糙的模式匹配去审命令路径，会同时产生漏判和误判。代价是：命令里访问上级目录不会被第二关拦截。这条边界靠两件事兜底——黑名单拦住最狠的那些命令，系统提示词里已告知规则、引导模型自觉在工作目录内活动。

**为什么拒绝要回灌而不是直接结束会话？** 终止循环当然最安全，但它把"模型犯了一次错"放大成"整个任务失败"。回灌保留了模型的自主纠错能力：它知道墙在哪里，能绕路走。代价是个别情况下模型会反复试探边界、浪费轮次，所以"不要尝试绕过"的提示词约定是必要配套，而不是可有可无的礼貌用语。

**为什么做成能力包而不是写死在内核？** 权限需求高度场景化：本机开发助手、只读分析工具、持续集成环境里的无人值守任务，需要的护栏完全不同。写死在内核意味着每换一个场景都要改循环代码；做成可拔插的能力包，护栏本身就成了配置项。这也正是它被安排在钩子系统（模块 10）之前的原因——先有了"执行前检查"这个具体用例，把检查点抽象成通用挂载点才有依据。

## 在整个项目中的位置

相对第八模块，09 第一次向循环里引入了"非工具型"的能力：它不注册任何新工具，却影响每一次工具调用。它确立了两个此后被反复复用的惯例——"工具执行前钩子返回非空即拦截"，以及"能力包 = 一个目录 + 一行注册"的插拔方式。

往回看，它是压缩管理、任务编排、后台执行这些能力之后第一个纯横切能力，把能力契约的适用范围从"给智能体加工具"扩展到"管智能体的行为"；往前看，它直接为模块 10 铺路——钩子系统要做的，正是把 09 里这种"执行前检查"从权限专属推广为任何人都能挂的通用扩展点。再远一点，模块 13 的外部工具接入、模块 23 的沙箱隔离，最终都要回答同一个问题：能力越来越强的智能体，在动作落地之前，谁替用户把最后一道关。
