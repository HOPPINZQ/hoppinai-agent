# 模块 20：工作区隔离

> 并行不互相干扰的空间隔离：给每件任务开一份独立的代码副本（类似版本库工作树），队友在各自的地盘里改文件，干完后要么保留成果、要么整体清理，主工作区从头到尾不被打扰。

## 这个模块要解决什么问题

上一模块让队友能自己认领任务、并行推进，但也把一个隐患放大成了必然事故：

- **互相覆盖**。小艾的任务是"重构认证模块"，小博的任务是"重构登录页"，两人都在同一个目录里干活。小艾写配置文件，小博也写配置文件，后写的把先写的整个抹掉。文件工具没有"这是谁的改动"的概念。
- **改不动对方的半成品**。小艾改到一半的代码，恰好是小博要读取的依赖。小博读到的是中间态，跑出来的测试结果毫无意义，还会把"失败"反馈回自己的循环，越修越乱。
- **无法干净回滚**。任务做完发现方向错了，想撤掉小艾的全部改动——但同一个目录里混着两个人的改动和主工作区自己的改动，根本分不清哪一行属于谁。

前面几个模块解决了"谁干什么"（任务板）和"怎么沟通"（消息总线与协议），但始终没有回答"**在哪干**"。本模块补上这块：空间隔离。

## 核心思想

**任务管目标，副本管地盘，认领时对号入座。**

```
                 版本库（同一个仓库）
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   主工作区          隔离副本·认证        隔离副本·登录页
   （谁也不碰）      专用分支·认证        专用分支·登录页
                    独立目录·认证        独立目录·登录页
                        ▲                ▲
                        │                │
   小艾认领任务#1 ───────┘                └────── 小博认领任务#2
   （这条执行流的读写只落在左边的目录）      （只落在右边的目录）
```

关键认识是：**同一份代码历史可以同时检出多份**。每份检出挂在仓库里一个专属分支上，拥有自己独立的目录。在同一份检出里随便改、随便跑，其它检出和主工作区一行代码都不会变；改完的成果留在那个专属分支上，天然带着"这些改动属于这件任务"的归属信息——回滚就是丢弃那个分支，合并就是合并那个分支，再也不是在文件堆里考古。

## 工作原理

### 1. 创建副本：开一块新地盘

创建副本这个动作做四件事：

1. **校验名字**：名字不能为空；目标目录已经存在同名副本则直接拒绝。名字同时充当目录名与分支名，一人一名，不会混淆。
2. **定位仓库**：从当前工作区出发向上逐层查找版本库的根目录，找到就以它为操作基准（找不到就退化到工作区本身，让后续命令自己报错——报错会被如实带回给模型）。
3. **开分支并检出**：调用版本库命令，新建一个以副本名命名的专属分支，并把它检出到隐藏副本目录下的同名子目录。优先基于主分支创建；主分支不存在就退回基于当前所处位置创建。这个先后顺序保证了副本尽量从"干净的主线"出发，而不是从某个可能不干净的当前状态出发。
4. **可选绑定任务**：把副本名字记到任务板的那条任务上。于是"任务 → 副本"有了一张对照表：任务#1 在认证副本里干，任务#2 在登录页副本里干。任务板从此不只是"干什么"的清单，还带着"在哪干"的地址。

### 2. 线程级工作目录：工具如何落到副本里

副本建好之后，真正决定"改动落在哪"的是**工具执行时用的基准目录**。本模块引入了一个线程私有的工作目录上下文：

- 队友这条执行流如果携带着某个副本路径，它的读写就以副本目录为基准；
- 没携带任何副本（比如负责人主线程，或在别的目录里干活的队友），就退回默认的主工作区。

```
文件工具被调用（读 / 写 / 编辑 / 列目录）
        │
        ▼
问当前执行流："你有自己的地盘吗？"
        │
   有 ──┴── 没有
   │         │
   ▼         ▼
副本目录    主工作区
   │         │
   └────┬────┘
        ▼
以基准目录 + 相对路径 解析出真实位置再动手
```

这个设计的含义是：**同一套工具、同一套提示词，落在哪个目录完全由执行流决定**。负责人在主工作区读文件看全局，小艾在认证副本里写代码，小博在登录页副本里写代码，三个执行流调的是同样的文件工具，谁也碰不到谁的地盘。相对路径的语义也没有被破坏——队友仍然写"配置文件"这样的相对路径，只是这个相对路径相对于它自己的副本。

（一个教学版的已知边界：执行命令类工具当前没有跟随这个目录切换，命令的起始目录仍是进程默认位置。空间隔离主要通过文件类工具生效，这一点在设计取舍里展开。）

### 3. 生命周期：创建、保留、清理

副本是有生命周期的，三个动作对应三种归宿：

```
创建 ──> 使用中 ──┬──> 保留：标记"这个副本和它的分支要留着"
                  │        （成果是干净的一条分支，供日后审阅或合并）
                  │
                  └──> 清理：两种力度
                        ├─ 丢弃式：强制删掉副本目录，连同它的分支一起删除
                        │          （任务作废 / 方向错误，抹掉一切痕迹）
                        └─ 摘挂式：只把这份检出从仓库的登记里摘掉，
                                   目录内容和分支原样留下
                                   （想先腾出登记名额，成果暂不销毁）
```

几个值得注意的语义：

- **清理只作用于那一份副本**。删掉"认证"副本，"登录页"副本和主工作区毫发无伤——因为它们本来就是三份独立的检出。
- **丢弃式清理是兜底加强版**：正常删除失败时会退化为直接递归删除目录，保证不留下删不掉的僵尸目录；分支删除失败则安静忽略（分支留着不碍事）。
- **保留动作在教学版里是一个明确的"标记"**：它向模型与日志宣告"这份成果要留"，但不会自动做合并——合并是显式的下一步，不藏在清理动作里偷偷发生。

### 4. 改动如何回到主线

这是隔离方案最容易被追问的一点：副本里干完的活，怎么回到主工作区？

答案藏在"副本是仓库里的一条正式分支"这个事实里。它不是临时文件夹，不是复制粘贴出来的备份，而是版本库亲生的检出——所以成果的归宿就是版本控制的标准动作：

- **想留**：什么都不用做。改动已经在那个专属分支上了，副本目录清掉也不影响分支里的提交历史。
- **想合并**：把那条分支合并回主线，走的是团队平时 review 与合并的正常流程——恰好和上一模块的"方案审批"协议接上了：先审方案、再动手、干完的成果以分支为单位送审合并。
- **想撤销**：丢弃式清理，一条命令抹掉目录与分支，主工作区从头到尾没被碰过。

对比没有隔离时的回滚方式（在同一堆改动里逐个文件手工挑拣），这是质的差别：**归属单位从"行"变成了"分支"**。

### 5. 与任务板、团队、协议的合流

本模块没有引入新的通信机制，它做的事是把前几个模块的零件拼成一条完整流水线：

```
负责人：拆任务 → 为任务创建副本（并绑定） → 拉起队友
队友：认领任务 →（任务带着副本地址）→ 在副本里干活
      → 完成 → 任务板上标记完成
负责人：验收 → 保留副本（成果留分支）或丢弃式清理（方向错了重来）
```

负责人一方的系统提示词也随能力注入了新的工作指南：先给任务开隔离工作区，再派活；收尾时要么保留、要么清理。能力包的形式依旧——三个工具（创建 / 保留 / 清理）加一段提示词片段，复制目录加一行注册即可插拔。

## 一次完整运行的流转

以"同时重构认证模块和登录页"为例：

```
你：认证和登录页两个重构并行推进，别让它们互相踩

负责人：创建两个副本并各自绑定任务
        副本"认证"  ← 分支·认证  → 任务 #1 重构认证模块
        副本"登录页" ← 分支·登录页 → 任务 #2 重构登录页
        拉起小艾、小博

        └─ 小艾认领 #1，执行流携带着"认证"副本地址
             ├─ 读配置文件 → 读到的是认证副本里的那份
             ├─ 写鉴权过滤器 → 落在认证副本目录
             └─ 跑自测 → 用的是副本里的中间代码
        └─ 小博认领 #2，一切同理，但落在"登录页"副本

        两人同时改了同一个文件名——各自目录里各有一份，互不可见
        主工作区此刻保持着你打开时的原样

        小艾完成 → 任务板 #1 标记完成 → 汇报
        小博完成 → 任务板 #2 标记完成 → 汇报

你：登录页那个方向不对，重来；认证的留下

负责人：丢弃式清理"登录页"副本（目录 + 分支一并抹除）
        保留"认证"副本（分支留在仓库里，随时可合并）
        主工作区全程未被改动
```

关键观察点：

- "两人同时改同一个文件"从灾难变成了两份互不相干的正常操作；
- 回滚的单位是副本（连同分支），而不是散落的文件改动；
- 任务板上的任务自此携带地址，认领即"对号入座"。

## 设计取舍

- **用版本库工作树，而不是简单复制目录**。复制一份目录也能隔离，但复制件与仓库断开了血缘：没法提交、没法合并、没法回滚。工作树方案里每份副本都是仓库的正式成员，隔离的同时保留了版本控制的一切能力，代价是要求工作区必须在一个仓库里（不在的话创建会直接报错）。
- **优先从主分支开分支，退回当前位置**。理想情况是永远从干净的主线出发；主分支不存在（比如仓库刚建、或处于分离状态）时退而求其次，保证功能可用。教学版不做更复杂的基线协商。
- **隔离作用在文件工具的基准目录上，而不是切换进程目录**。教学版选择影响面最小、语义最清晰的切入口——文件类工具的路径解析。执行命令类工具没有跟随切换，这意味着队友在副本里跑构建命令时需要显式带上路径。这是教学上刻意的留白：它把"进程级沙箱"这个更重的主题留给后面的沙箱模块。
- **保留动作只是标记，不自动合并**。合并是一个有风险、需要人判断的动作（冲突、评审、回归），藏在自动清理里悄悄发生是大忌。教学版把它显式化：保留就是保留，合并是下一个明确的决定。
- **绑定关系放在内存对照表里**。任务与副本的关联教学版记在任务板的内存里，重启即失。更稳妥的做法是随任务一起落盘——这是一个明确的"留给读者"的改进点，代码注释里也直说了这是为教学简洁做的取舍。
- **校验从简**：拒绝空名字与重名副本，但不做路径穿越等更严格的名称白名单校验。名字来自模型输出，生产化实现应当把这一课补上。

## 在整个项目中的位置

- **相对模块 19（自主运行）**：19 让队友自己找活干，解决了"谁来干"；20 解决"在哪干"。两者合起来，并行才真正安全——没有空间隔离的自主，等于让一群人挤在一张桌子上同时写一份稿子。
- **相对模块 18（团队协议）**：审批通过的是"方案"，落到磁盘上的是"分支"。副本让方案与成果一一对应，审批—实施—合并形成了完整的责任链。
- **相对模块 17（智能体团队）**：团队给并行执行流；隔离给并行执行流各自的地盘。到本模块为止，"多智能体协作"的三要素——通信（邮箱）、纪律（协议）、空间（副本）——全部齐备。
- **为模块 21（综合）铺垫**：综合模块会把这三大件与任务板、定时、记忆、权限等一起装配成一个完整系统；工作区隔离是其中"多任务并行不互相污染"的基石。
- **为模块 23（沙箱）铺垫**：本模块隔离的是**文件改动**，没有隔离**执行行为**——命令还能访问整台机器。把"隔离地盘"推进到"隔离环境"，是沙箱模块要回答的问题。
