# 模块 04：子智能体

> "大任务拆小，每个小任务配一副干净的上下文。" —— 把上下文当成最稀缺的资源来经营：脏活累活派出去，主对话只收一句话的结论。

本文建立在模块 03 之上：待办清单能力原样保留（主智能体照常记计划、被催办），本模块新增第八件工具——委派子任务的工具。它让主智能体第一次可以"雇人干活"，而不是事事亲力亲为。

## 这个模块要解决什么问题

智能体工作得越久，消息列表越胖。每一次读文件、每一次跑命令的输出都会**永久**留在上下文里。几个具体的痛点随之而来：

- **调研成本高得离谱**。"这个项目用的什么测试框架？"这种问题，模型可能要翻五六个文件才能回答。但主对话真正需要的只是一个词。为了一句话的结论，主上下文被塞进了五个文件的原文。
- **杂音淹没主线**。主线任务做到一半，中途穿插的调研、试错、验证留下的内容全部堆在同一份历史里，模型往后每一步都要在这些噪音里分辨什么还重要。
- **交叉污染**。两件事混在一个上下文里处理时，前一件事的细节会不自觉地渗进后一件事的判断——模型会"记岔"。

本质上，上下文窗口是有限的：花在无关细节上的每一分空间，都是从正事手里抢来的。模块 06 将会从"压缩已有历史"的角度治理这个问题，本模块的思路相反——**从一开始就不要让那些细节进主上下文**。

## 核心思想

**用全新上下文的子智能体隔离子任务。**

主智能体获得一件新工具："把一段任务描述交出去"。工具被调用时，系统当场造出一个全新的智能体实例：消息列表从零开始、只有任务描述和一份专属系统提示词、只配三个文件工具，然后让它独立跑完自己的工具循环，最后只把**一段总结文本**交回主对话。

于是发生了两个方向的压缩与隔离：

```
   主智能体（父）                          子智能体
 ┌──────────────────┐              ┌──────────────────┐
 │ 消息列表：很长     │   交出任务    │ 消息列表：[]（全新）│
 │ 工具：全套 8 件    │ ──────────▶ │ 工具：读写编辑 3 件 │
 │                  │              │                    │
 │                  │   独立循环    │ 自己读文件、自己改   │
 │                  │ ◀────────── │ 几轮甚至几十轮       │
 │ 收到：一条工具结果 │   只回摘要    │ 全部过程随之丢弃     │
 └──────────────────┘              └──────────────────┘
```

- 子智能体几十轮的折腾，在父上下文里只占**一条消息**的位置；
- 父智能体上百条消息的历史，子智能体**一个字都看不到**。

两个"看不到"合在一起，就是上下文隔离：子任务有子任务的专注，主线有主线的清净。

## 工作原理

### 1. 委派工具长什么样

委派工具的参数简单到只有一项：**给子智能体的任务描述**。没有工具清单参数、没有"继承哪些上下文"的开关——因为这些都不该由模型临场决定，而是由系统写死（下一节）。工具描述里讲清楚子智能体擅长什么（具体的文件操作任务）、以及"只返回摘要、不污染主上下文"这个承诺，让模型学会在合适的时机用它。

一个容易被忽略的接线细节：子智能体要跑，就得知道用哪个模型、走哪条接入配置。能力在注册时会捕获宿主的引用，到时直接**复用父智能体正在用的那套模型接入**——父子用同一个模型、同一个协议配置，避免"子智能体悄悄走了另一条通道"这种排查起来要命的偏差。

### 2. 子智能体如何被造出来

工具执行的那一刻，系统做四件事：

1. **配一张最小工具面**：只有读取、写入、编辑文件三件工具。没有命令行工具（子任务不该有执行任意命令的权限），没有搜索工具（不需要在项目里自由导航），没有待办清单工具（子任务短平快，用不上计划管理），**更没有委派工具**（子智能体不能再雇孙智能体）。
2. **写一份专属系统提示词**：一句话人设——"你是一个子智能体，已接收一个具体任务，用可用工具完成它，完成后直接返回结果。"不包含父智能体那一大段角色定义和工作环境说明。
3. **给一个空的消息列表**：不拷贝父上下文，不分叉父历史。子智能体看到的世界里只有那条任务描述。
4. **不接会话持久化**：子智能体的对话是易耗品，用完即弃，不落盘、不可恢复。

然后调用内核自带的"任务模式循环"开跑。注意这个执行基座是**内核的一部分**而不是委派能力的私有逻辑——这正是后面任务委派模块能直接复用的底座。

### 3. 任务描述必须自足：委派的提示词纪律

上下文隔离有一个必然的推论：**父智能体没法指望子智能体"自己看上文"**。任务描述就是子智能体的全部输入，所以它必须一次说清——改哪个文件、要达成什么、边界在哪、做完交回什么。

这看似是负担，实则倒逼出一种好习惯：委派者必须先想清楚任务，才能委派任务。一个写得含糊的委派（"帮我弄一下测试"）会得到一份含糊的结果；一份合格的委派（"为某文件编写单元测试，覆盖这几种情况，完成后报告用例数"）几乎总能换回一份合格的交付。委派质量的上限，被机制钉在了任务描述的质量上。

同理，反方向的"汇报纪律"也由工具描述约定：子智能体只回摘要——做了什么、结果如何、有什么要注意的，不逐轮复述过程。

### 4. 子任务循环与主循环的三点不同

子任务循环的骨架和主循环一样（请求模型 → 有工具调用就执行回灌 → 再请求），但有三个关键差异：

- **非交互**。主循环等人输入，子循环吃一条任务说明就开跑，中间没有任何人可以插话。
- **两种出口**。其一：模型某轮只回了文本、不再调用工具——这段文本就是任务结果；其二：模型调用了一个约定的"任务完成"工具，把最终结果作为参数交回来——系统直接采信并返回。第二种出口给了模型一个明确的"交卷"动作，比"沉默即完成"的推断更可靠。
- **顺手记账**。循环过程中把每一轮请求的输入与输出规模累加起来，任务结束后和结果一起返回。父智能体由此可以知道"这个子任务花了多少"，为后续的预算控制留了数据口子。

循环里同样保留着主循环的那些防御：工具找不到、执行抛异常都以可读文本回灌；回复被截断时给出警告，避免残缺的工具调用引发静默死循环。

### 5. 结果如何回到父上下文

子智能体跑完后，返回的东西被拼装成**一条**工具结果：摘要正文 + 一段规模统计说明。父智能体把它当普通工具结果收进消息列表，然后继续干自己的活——它不需要知道、也永远看不到子智能体中间读了哪些文件、试错了几次。

这里有刻意的取舍：交回来的是"对已完成工作的总结"（写了什么、做了什么决定、遇到什么问题），不是完整对话历史的转储。整个子任务交互在父上下文里被压缩成一条消息，这正是本模块存在的意义。

### 6. 防递归与最小权限

父子工具面对照：

| 能力 | 父智能体 | 子智能体 |
|---|---|---|
| 执行命令行 | 有 | 无 |
| 读 / 写 / 编辑文件 | 有 | 有 |
| 按名字找文件 / 搜内容 | 有 | 无 |
| 待办清单 | 有 | 无 |
| 委派子任务 | 有 | **无** |

不给委派工具是最关键的一条：它从工具面上根除了"子智能体再派子智能体、孙智能体再派曾孙"的无限递归。想限制一个智能体能惹出多大的乱子，最有效的手段不是在执行时层层拦截，而是根本不让它拥有那个入口。另外，单次子任务的最大循环次数也有一个预留的上限配置（当前尚未接入循环，属于给未来挂载留好语义的占位）——递归防护先靠工具面，深度防护靠次数上限，两层思路。

最后把一次委派的完整时序摆在一起看：

```
 父上下文                                子上下文（易耗）
 ─────────                           ────────────────
 待办：某项任务标为进行中
        │
        │ 调用委派工具（一段自足的任务描述）
        ├──────────────────────────▶ 造新实例：空列表 + 3 件文件工具
        │                             请求① → 读源文件 → 结果回灌
        │                             请求② → 写测试文件 → 确认回灌
        │                             请求③ → 复查 → 决定交卷
        │                             （每轮顺带累计输入/输出规模）
        │◀────────────────────────── 摘要 + 规模说明，作为一条工具结果
        │
 主对话里只多了一行；子上下文整体丢弃
        │
 待办：该项任务标为已完成
```

父上下文自始至终只增长了两个工具结果的大小；子上下文里那几十条消息从未与主线见过面。

## 一次完整运行的流转

场景剧本：用户要求"重构那个计算器：拆分成模块，并补上测试"——一件既费上下文又适合并行的事。

1. **主智能体接活、立计划。** 它先按模块 03 的规矩用待办工具列计划，随即做出判断：测试编写是独立的子任务，委派出去；重构拆分自己来。
2. **交出任务。** 主智能体调用委派工具，任务描述是一段完整、自足的指令："为计算器脚本编写单元测试，覆盖四种运算以及除零等边界情况。"注意这段话必须自足——子智能体看不到主对话，父智能体得把"在哪个文件、要覆盖什么"一次说清。
3. **子智能体降生。** 系统创建全新实例：空消息列表、三个文件工具、专属提示词。它独立跑自己的循环：读取计算器代码、分析运算逻辑、写出测试文件、复查内容。这几轮的全部输出都只存在于子智能体自己的上下文里。
4. **交卷。** 子智能体以"任务完成"交回一段总结："已创建测试文件，包含八个测试用例，覆盖全部运算与除零边界。"
5. **主线继续。** 这段总结作为一条工具结果进入主上下文。与此同时父智能体并行推进自己的部分：把单文件拆分成运算模块与命令行入口两个文件。子任务的几十轮细节在主对话里只占了一行。
6. **收尾汇报。** 主智能体回复："已重构为两个模块，测试由子智能体完成，全部通过。"循环退出。

如果这五步全由主智能体亲力亲为，读源码、写测试、跑验证留下的大量中间输出会把主上下文塞得满满当当，重构阶段模型就得在测试细节的噪音里找路。委派把这些细节整个关在了另一个上下文里。

## 设计取舍

- **全新上下文，而不是共享或分叉父历史。** 共享能给子智能体更多信息，但也会用无关细节淹死它，挤占它自己干活的空间；分叉（拷贝一份父上下文）是折中，可依然在无关历史上白白花费预算。从零开始最省，代价是父智能体必须把任务描述写得自足——这个负担落在了提示词纪律上，而不是机制上。
- **不给工具，而不是给一套继承来的工具集。** 给子智能体全套工具（尤其命令行）会让它完全自主，但立刻引出递归问题和管理成本；给"父工具的子集"是中间方案，却需要定义一套继承策略。本模块选择了最窄的三个文件工具，把"执行命令"这类有副作用的动作留在父层——子智能体专注规划、分析与代码生成，执行权归父。
- **只回一条摘要，而不是返回完整历史或结构化报告。** 返回全史会让父上下文膨胀，隔离形同虚设；结构化输出（固定字段）好解析，却会丢掉自然语言的细腻。单个文本字符串是模型最能自然生成的格式，配合"任务完成"工具这个明确的交卷动作，简单且可靠。
- **复用宿主的模型接入，而不是另起一套。** 早期实现里子智能体自己重新创建模型接入，与宿主用的不是同一实例——配置漂移时父子行为不一致，极难排查。现在能力在注册时记下宿主引用，父子共用同一套配置。
- **保留待办能力，主次分明。** 委派并没有取代计划：主智能体的待办清单继续追踪整体进度，子任务只是清单上某一项的执行手段。计划管全局，委派管隔离，两者互补而非竞争。
- **子智能体的会话是易耗品，不落盘。** 父对话有完整的持久化与恢复机制，子智能体什么都没有——它被造出来就是为了跑完即弃，中间状态没有留档的价值；真要重跑，父智能体重新委派一次就是。区别对待的原因很朴素：持久化是为"要接着用"的东西准备的。
- **规模记账随结果一起回。** 子任务消耗的输入与输出规模被逐轮累加，跟摘要一起交回父层。这个信息当前只是附在结果末尾的一行说明，但它为后续的预算控制备好了原料：什么时候该委派、委派划不划算，将来都要看这本账。

## 在整个项目中的位置

模块 04 把模块 01 埋下的"进程即子代理"思想正式化为系统机制，同时解锁了一条全新的扩展轴：

1. **任务模式循环成为内核底座**。子智能体跑的那个"非交互、吃一条任务、只回结果"的循环就长在内核里。模块 07 的任务委派工具会把它拿去做正式的多智能体调度——可以并行派发多个子任务、聚合各自的结果，本模块只是它的单机版。
2. **"压缩进一条消息"的思想**。把大量轮次压缩成一段摘要，这是治理上下文的两条路线之一；模块 06 的自动压缩走的是另一条（对既有历史做手术），两者一攻一守。
3. **工具面即权限边界**。不给某工具就不能做某事——这个原则之后被反复使用：技能模块限制加载来源、权限模块按规则拦截调用，都是同一思路的变体。
4. **委派也是一种上下文策略**。本模块证明"少给上下文反而干得更好"在很多场景成立；模块 06 的自动压缩、后续模块的记忆管理，都在这个共识上继续做文章——上下文不是越多越好，而是越相关越好。

到这里，项目的前四个模块拼出了一个完整的小世界：模块 01 的循环给了它心跳，模块 02 的工具给了它手脚，模块 03 的清单给了它记性，模块 04 的子智能体给了它分身。之后的模块——技能、压缩、任务、协同——都是在这个小世界身上继续长出更专业的器官。
