# 模块 24：执行骨架（Harness）

> 智能体 = 会决策的模型 + 一层不会思考的工程骨架。前面 23 个模块反复改造的那段"外壳代码"，在这里被正式命名：它是宿主，是执行骨架，是产品级智能体真正的底盘。

## 这个模块要解决什么问题

从第 1 个模块开始，每一章都在做同一件事：复制一份智能体循环，然后往里加一点东西。加到第 23 章时，问题暴露出来了——

1. **骨架代码重复了 23 份**。读文件、执行命令、追加消息、调用模型，这些一模一样的代码在每个模块里各躺一份，改一处要同步二十多处。
2. **机制之间互不相认**。定时调度、后台任务、队友协作、外部服务接入，各章各自为政，没人回答"它们到底从哪里进入同一个循环、产生的事件又如何回到同一段对话"。
3. **工程职责和智能职责搅在一起**。谁负责在什么时候调用模型？工具表怎么维护？上下文快满时谁去瘦身？危险命令谁来拦？这些都是纯工程问题，模型一行代码都不用写，却被塞在循环的各个角落里。

这个模块不引入任何新机制。它做的事情是把前面所有章节的组件**接到同一个循环上**：二十九个工具、七个子系统，全部挂在一条"调用模型 → 检查有没有工具调用 → 执行工具 → 把结果追加回上下文 → 下一轮"的主干道上。循环本身从第 1 章到现在没有变过。

## 核心思想

把"模型的智能"和"工程的骨架"彻底分开：

- **模型只负责决策**——这一轮读哪个文件、跑哪条命令、要不要继续；
- **骨架负责其余一切**——何时调用模型、以什么上下文调用、结果如何呈现给人、出错怎么恢复、危险操作怎么拦。

骨架对模型的全部认知只有一件事：返回里有没有工具调用。有就执行再回来，没有就收工。所有复杂的机制都不碰这条主干，它们只是蹲在循环的几个固定位置上，等自己的时刻到来。

```
                ┌────────────────────────────────────┐
                │            执 行 骨 架              │
 用户输入 ────▶ │ 记录 → 注入外部事件 → 压缩 → 组装提示 │ ────▶ 调用模型
                │                                    │        │
                │ 工具表 · 权限闸门 · 钩子 · 会话持久化 │ ◀──────┘
                │                                    │   有工具调用
                │ 呈现输出 · 记账 · 截断告警 · 收尾钩子 │ ◀── 执行工具后回到调用
                └────────────────────────────────────┘
```

一句话概括这套分层：**循环是常量，机制是插在循环固定位置上的变量**。

## 工作原理

### 一、骨架的四份固定职责

**循环调度。** 外层是对话循环：读一行用户输入，处理完再等下一行。内层是工具循环：只要这一轮回复里还有工具调用，就执行完把结果追加回去、再请求一次。两层循环共用同一个退出判据——"没有待处理的工具调用"。骨架还埋了两处防御：如果一轮下来一个有效工具调用都没有，直接断开内层，避免无限请求；如果回复被输出上限截断，明确打印警告，因为截断的工具调用是不完整的，静默继续只会死循环。

**工具注册。** 工具表在装配时一次性建好：六个基础工具（执行命令、读文件、写文件、编辑文件、列目录、搜内容），加上定时、后台、协作、协议、任务板、隔离工作区、外部服务接入共二十多个。骨架按名字分发调用，找不到就如实把"工具不存在"作为结果回灌给模型，让它自己纠正。同名工具先注册者生效，这个去重规则让后续能力的接入变得安全。

**上下文管理。** 所有想进对话的消息都必须走同一个入口——这一条纪律换来的好处是：每条消息进来时可以同步落盘、同步统计。骨架在每次调用模型之前给"压缩"留了一个位置：先裁掉中段的旧消息，再把久远的工具结果替换成占位符，把超大输出挪到磁盘，实在不够才请模型做一次摘要——便宜的手段在前，昂贵的在后。

**输出呈现与记账。** 模型的文字、每次工具调用和它的结果都实时打印到界面；每次模型调用的用量被记进会话账本；重启后骨架能把持久化的历史灌回上下文，让人接着上次的对话继续聊。

### 二、事件挂载点：骨架伸出的四个把手

骨架不认识任何具体机制，它只在自己身上的四个位置广播事件，谁感兴趣谁来订阅：

| 挂载点 | 时机 | 能做什么 |
|---|---|---|
| 模型调用前 | 每次请求之前（含工具循环内的每一轮） | 对上下文动手术：返回一份新列表就替换原上下文 |
| 模型返回后 | 响应到手、入库之前 | 读停止原因和用量，做统计或旁路记录 |
| 工具执行前 | 每个工具调用之前 | 返回拦截文案即可否决这次调用，文案会作为工具结果回灌 |
| 工具执行后 | 每个工具调用之后 | 观察结果：记日志、告警、汇总 |

执行顺序就是注册顺序，前一个钩子的输出是后一个钩子的输入。拦截语义被刻意设计得很简单：**返回一段文字 = 否决**，这段文字模型看得见，所以被拒绝时模型知道自己为什么被拒，下一轮会换一种做法。

### 三、子系统如何挤进同一个循环

这是本模块最值得看的地方：七个子系统没有一个改动循环主干，它们全都在"请求模型之前"或"工具执行那一刻"插队。

**定时调度**靠一条守护线程每秒扫一遍表达式，命中就把提示语放进队列；主循环每次请求模型前先把队列排空，到点的提醒就像一条用户消息一样进入对话——"三分钟后提醒我"因此不需要任何轮询界面，模型下一轮自然接得住。

**后台任务**走的是"先回执、后注入"两段式：模型要求后台编译时，骨架把命令丢进线程池，立刻回一句"任务已受理"，主循环完全不等它；命令在后台跑完后，结果排进通知队列，下一次请求模型之前被排空注入。长命令从此不再阻塞对话。

**队友协作**给每个队友开一条独立的守护线程：它有自己的对话、自己的邮箱文件、自己的一小份工具集，空转时轮询任务板自动认领活计。主控与队友之间不共享上下文，只通过磁盘上的邮箱文件互发消息——这条窄窄的消息通道就是全部耦合。

**协议交互**在邮箱之上加了一层状态登记：关停请求、方案审批都有一条带编号的记录，状态从待处理走到已回应或已通过。主控读到收件箱时按消息类型路由——普通消息回灌对话，审批请求登记在案等主模型拿主意，回执则销账收尾。

**外部服务接入**演示了工具表的动态生长：连接一个服务后，它的工具带着服务名前缀注册进工具表，下一轮模型就能看到并调用。前缀避免了不同服务同名工具互相覆盖。

**隔离工作区**把"每个队友在哪个目录里干活"变成任务板上的一个属性：创建工作区、绑定任务、认领之后骨架自动把后续文件操作重定向到那片隔离目录，互不踩脚。

### 四、提示词是装配出来的，不是写死的

系统提示词由骨架按段组装：身份、工具清单、工作目录与操作系统、记忆索引，各段注册时自带一个启用条件——工具清单段只在确实注册了工具时渲染，记忆段只在记忆文件存在时挂上。同一种上下文只装配一次，结果缓存复用。技能目录在启动时被扫描一遍，每个技能的名字和一句话说明拼进提示词，模型因此知道自己"会什么"。

骨架还会自动补一段模型看不见就会闯祸的话：当前是什么操作系统、命令该用什么语法、工作目录在哪。经验是，不说明命令行解释器的类型，模型在特定平台上会高频输出错误语法的命令。这段"环境提示"由内核统一追加，装配者永远不必操心。

### 五、安全与恢复：骨架兜底，模型免责

权限是三重闸门的流水线：先查危险命令黑名单，命中即拒；再按工具和参数查规则，比如路径是否越出工作目录；最后才轮到人——破坏性操作弹回终端请求确认。任一闸门拒绝就短路，拒绝原因原样回灌给模型。命令执行工具自身还有一道兜底黑名单、单条命令的强杀超时和输出长度上限，防止一条挂起的交互式命令把整个骨架拖死。

模型调用被一层恢复包装裹住：输出被截断就自动抬高输出上限续写；上下文超长报错就触发一次紧急压缩再重试；瞬时限流或网络错误按指数退避重试，连续失败到一定次数就切到备用模型。骨架把这些脏活全部揽下，模型调用方看到的永远是"一次普通的请求"。

### 六、一副骨架，多种外壳

骨架层与呈现层是分离的。同一个内核循环，接上终端读入器就是命令行智能体；接上网络入口、数据库会话和异步推送，就是网页对话产品——网页版只是把"读一行输入"换成了"收一条消息"，把"打印到屏幕"换成了"写库并推送"，循环、工具、压缩、记账一行都不用动。

这正是真实产品级编码智能体的组织方式：会话管理、权限确认、钩子系统、上下文压缩、子进程工具、后台任务……这些骨架件与模型无关，可以被任何外壳复用；模型换一代，骨架还是那副骨架。本模块的骨架可以和这类产品逐件对上号——你在终端里用到的每一次确认弹窗、每一条压缩提示，背后都是这里的一个挂载点。

## 一次完整运行的流转

设定一个能同时踩中七个子系统的任务："后台编译项目，同时检查一遍仓库，三分钟后提醒我开会，再把两个子任务派给队友。"

```
启动
 │  骨架装配 29 个工具、扫描技能目录、恢复上次会话、打印可用命令
 ▼
用户输入 ──▶ 记录入上下文并落盘
 │
 ▼
请求模型前：排空定时队列和后台通知 → 压缩管线 → 组装系统提示词 → 请求
 │
 ▼
模型要求：后台编译 ──▶ 丢进线程池，立即回"任务已受理"（主循环不等待）
 │        模型继续读文件、检查代码
 ▼
模型派生两名队友 ──▶ 两条守护线程上线：各自独立对话 + 邮箱 + 自动认领 + 隔离工作区
 │
 ▼
三分钟后：调度线程命中 → 提示语入队 → 下一轮请求前注入 → 模型如约提醒开会
 │
 ▼
编译结束：结果入通知队列 → 注入 → 模型向用户汇报编译结果
 │
 ▼
队友提交方案审批 → 协议登记待审 → 主模型审批通过 → 队友继续干活
 │
 ▼
模型停止调用工具 ──▶ 停止钩子收尾（统计、清理）──▶ 回到等待输入
 │
 ▼
退出：骨架关闭后台线程池，给进行中的任务几秒钟收尾
```

值得观察的三处：后台任务**没有阻塞**任何一轮对话；定时提醒**没有打断**正在进行的工具循环，它等到下一轮才自然出现；队友的输出**从不直接进**主控的上下文，只有经过邮箱和审批的消息才会。

## 设计取舍

**装配清单还是能力注册。** 本入口用一份直白的装配清单：一行一个子系统，先建管理器，再注入工具层，最后把工具列给模型。骨架同时支持另一种风格——把工具、钩子、命令、提示词片段打包成一个"能力"整体注册。前者好读，后者好拔。教学上先亮清单，让人看清每个机制的接线位置。

**拦截返回文字，而不是抛异常。** 钩子否决一次工具调用，靠的是返回一段说明文字。这比异常简单，模型也能从文字里学到"为什么被拒"；代价是约定全靠纪律——返回空值表示放行，这个语义必须所有钩子共同遵守。

**外部事件伪装成用户消息。** 定时提醒、后台结果都以一条用户消息的身份进入对话，而不是另开一条独立通道。好处是模型端零改动、注意力机制天然适用；代价是必须小心标注来源，避免模型分不清哪句是人说的、哪句是系统注入的。

**每个模块自带一份内核副本。** 二十五份重复代码听起来是坏味道，但这是刻意为之的教学选择：每章自包含、可独立运行、可逐行对照。真实工程里应当抽成共享依赖——这正是本模块把骨架"命名"之后自然引出的下一步。

**压缩便宜优先。** 裁消息、换占位符、挪磁盘都是零成本的本地操作，只有前三层不够时才花一次模型调用做摘要。省下的每一次模型调用，都是实打实的延迟和费用。

## 在整个项目中的位置

作为倒数第二章，它是前 23 章的收束点：

- 第 2 章的工具调用在这里变成一张二十九个工具的注册表；
- 第 6 章的压缩、第 12 章的错误恢复，挂进"请求模型前"这个位置；
- 第 8 章的后台、第 16 章的定时，统一成"请求前注入外部事件"这一个模式；
- 第 9 章的权限、第 10 章的钩子，落位为工具执行前后的标准闸门；
- 第 17 章的协作、第 18 章的协议、第 20 章的工作区隔离，作为平级子系统接入同一个循环；
- 第 13 章的外部服务接入演示了工具表的动态生长，第 15 章的提示词装配成为骨架的标配部件。

它回答了本教程后半程一直悬着的问题：机制这么多，循环为什么始终没变？因为它们从来不是循环的分支，而是循环的挂载点。

而骨架还留了最后一个空位没有填：循环的退出判据，从第 1 章起一直是"模型不再调用工具"。模型想停，循环就停——这件事本身对不对？最后一章就是为了推翻它而来的。
