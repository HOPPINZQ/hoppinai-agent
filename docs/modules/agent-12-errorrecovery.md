# 模块 12：错误恢复

> 让循环在故障中依然前进：截断、溢出、限流、断网——每类故障都有自己的恢复路径，而不是一崩了之。

## 这个模块要解决什么问题

到目前为止，智能体循环对故障的态度基本是"打印错误，然后放弃"：

- 模型回复到一半被输出上限截断，工具调用可能残缺，循环要么死等、要么静默丢消息；
- 对话一长，模型服务直接拒收请求（上下文超长），本轮任务当场中断；
- 服务端限流、过载、网络抖动——这些**过几秒就能自愈**的瞬态故障，也会让整轮对话戛然而止；
- 工具执行失败倒是会把错误文本回灌给模型，但这层保护只覆盖工具，覆盖不了模型调用本身。

智能体循环的特点是把故障放大了：一次任务动辄几十次模型调用，任何一次失败都会让前面几十轮的心血作废。任务越长，"失败即全弃"的期望损失越大。而当智能体走向无人值守（定时任务、自主循环），"出错就等人来重启"更是不可接受。这个模块要做的，是把"故障"从循环的终点变成循环里的一个普通弯道。

## 核心思想

**先分类，再恢复；不同故障走不同的路，不可恢复的才抛出去。**

三条原则：

1. **故障必须先被识别成有限的几类。** "调用失败了"这个信息不足以决定怎么办——上下文超长该压缩，限流该等待，参数写错该放弃。分类是恢复的前提，而分类依据只能是异常携带的文本与因果链。
2. **能自己好的就等，能换路走的就换，实在不行才认输。** 瞬态故障用退避等过去；输出不够就把上限调大再来一次；上下文装不下就砍掉中间历史再试。三条路径覆盖了实践中绝大多数失败。
3. **恢复的状态要跨尝试延续，但要有限度。** 升级过的输出上限在整个会话里保持生效（说明这个任务就是需要长输出）；重试次数却有硬上限，超过就放弃——恢复机制自己不能变成新的死循环。

## 工作原理

### 一、故障是分层被捕获的

理解这个模块之前，先看清故障在循环里被处理的三个层次：

```
  第 1 层（内核·工具层）   工具找不到 / 工具执行抛异常
                          └─► 错误文本作为该次调用的结果回灌，
                              模型自行纠正，循环继续           ← 一直就有
  第 2 层（内核·对话层）   模型响应里没有消息 / 回复疑似被截断
                          └─► 打印错误或警告，结束本轮，等待
                              用户下一句输入                   ← 一直就有
  第 3 层（本模块·调用层） 模型调用本身失败或返回不完整
                          └─► 分类 → 恢复 → 重试，上层完全无感  ← 本模块新增
```

前两层是既有的善意设计：工具失败从来不是异常，而是一条"错误: ……"文本，模型读得懂就会换思路——这是"让模型自行纠正"的最原始形态。本模块把同样的哲学推到了最深一层：**模型调用本身**。保护的覆盖面也因此是无死角的——工具循环里的每一轮调用、每一句新输入后的调用，走的都是同一个被包住的入口。

### 二、错误分类器：从异常文本里读出故障类型

模型服务不会把失败原因结构化地递给你，能依赖的只有异常对象携带的信息：错误消息、异常类型名、以及一层层包裹的因果链（最多向下挖五层）。分类器把这三者拼在一起做关键词匹配，落进五类：

| 类别 | 典型表现 | 恢复动作 |
|---|---|---|
| 上下文超长 | 服务端明确说请求太长、装不下 | 应急压缩历史后重试 |
| 限流 | 服务端要求降低请求频率 | 指数退避后重试 |
| 过载 | 服务端正忙、容量不足 | 指数退避；连续命中则切换兜底模型 |
| 瞬态网络 | 超时、连接被拒、管道断裂、域名解析失败 | 指数退避后重试 |
| 不可恢复 | 以上都不是（参数错、鉴权错等） | 立即抛出，不做无谓重试 |

两类值得注意的细节：匹配是**不区分大小写、且贯穿整条因果链**的——真正的根因往往藏在最内层；而"都不匹配就归类为不可恢复"这条默认规则，保证了未知故障不会被错误地送进重试循环空转。这套思路与模块 11 的记忆抽取一脉相承：让模型或系统自由产出，但用严格的格式与分类卡住它的产出，坏输入进不了下一步。

### 三、三条恢复路径

**路径一：输出截断 → 调大上限再来一次。** 回复以"达到输出上限"收尾，说明任务本身需要更长的输出。此时把单次输出上限一次性放大 8 倍并立即重试；若已在最大档位，就接受截断——尽力而为，但绝不无限升级。升级过的上限**在本会话内保持生效**：既然这个任务需要长输出，后续每一轮都按新上限来，避免反复截断、反复升级。

**路径二：上下文溢出 → 应急压缩。** 服务端拒收请求时，对历史做一次外科手术：

```
  压缩前： [第1条] [第2条] …… [第24条] [第25条] …… [第30条]
                         │
                         ▼
  压缩后： [第1条（任务目标）] [系统说明：已省略23条历史，请继续]
           [最近6条：第25条～第30条]
```

保留首条——那是用户最初交代的任务目标，丢了它智能体就忘了自己在干嘛；保留最近 6 条——当前工作状态；中间全部用一条说明替代。这是一种**应急**压缩：目标不是摘要质量，而是立刻能继续跑（讲求质量的主动压缩是模块 06 的职责）。压缩设了最小门槛：历史本来就没几条时无从压缩，此时恢复层放弃并向上抛出——承认救不了，好过假装救了。

还有一个容易被忽略的边界：这次压缩**只动内存里的上下文**。会话存储里逐条落盘的完整历史原封未动，重启会话时恢复的仍是完整历史。好处是不丢任何原文；隐患是重启之后上下文又满了，可能再次触发溢出——应急压缩治的是当下这一跑，不是病根。

**路径三：瞬态故障 → 指数退避，必要时换模型。** 等待时长按"基础值乘以 2 的尝试次数次方、封顶 32 秒"计算，再叠加一段随机抖动：首次约半秒，之后逐次翻倍。抖动的作用是让多个同时失败的调用错开重试时间，避免"惊群"——大家一起在整秒上重试，只会把刚喘过气来的服务再次打趴。连续多次（阈值 3 次）命中过载时，若配置了兜底模型就切换过去；切换只发生一次，防止在两个都不堪重负的模型之间来回震荡。本仓库默认单模型、不配兜底，此时只剩退避一条路——机制留好了，开关不打开。

### 四、重试循环与会话级恢复状态

三条路径被组织进一个包装层：它包住模型调用的出口，每一次调用都先走它，再由它决定"放行、等待后重试、压缩后重试、还是抛出"。整个循环有硬约束——最多尝试 6 次，耗尽就把最后一次的异常原样抛给上层，绝不无限重试。调用成功时，重试计数与连续过载计数双双清零，但升级过的输出上限保留。

这些计数与配置放在一份会话级共享状态里，是有讲究的：**有些信号必须跨尝试延续，有些必须跨调用延续。** 输出上限属于后者——它是关于"这个任务"的判断，不是关于"这一次调用"的；而"连续过载"必须在调用成功时清零，否则几小时前的一次过载，会让下一次偶发故障直接触发模型切换。状态的生命周期设计，本质是在回答"哪些经验值得记住、记到什么时候"——和模块 11 的记忆是同一个问题的两个尺度。

| 状态 | 何时变化 | 何时清零 |
|---|---|---|
| 重试计数 | 每次失败加一 | 调用成功即清零 |
| 连续过载计数 | 每次过载加一 | 调用成功即清零 |
| 输出上限 | 截断时一次性升级 | 会话内不清零 |
| 是否已切换兜底模型 | 达到阈值时置一次 | 永不复位，防止来回震荡 |

### 五、失败如何回灌给模型

恢复机制处理的是"系统层"故障，而循环里还有大量"任务层"失败（命令报错、文件不存在、参数写错）。本模块延续了既有的回灌哲学，并把它补全成一套完整的话术：

- **工具失败**：错误文本作为结果回灌（既有机制），模型读得懂就会改参数重试或换路——最经典的"让模型自行纠正"；
- **回复截断**：除了系统层的升级重试，能力还向系统提示词注入一段约定——"如果某轮回复被截断，请在下一轮继续，不要重复已输出的内容"。系统层管重试，提示层管衔接，两边配合才不会出现"重写一遍"的浪费；
- **不可恢复的失败**：直接抛给装配层，打印后结束本轮——对不可恢复的错误，最快的恢复就是不恢复。

另有一条查看命令，随时能看当前生效的模型（是否已切换）、输出上限、连续过载计数与退避策略，让恢复过程可观察而不是黑箱。

### 六、为什么包装调用，而不是挂在钩子上

这是本模块在架构上最有意思的决定。内核唯一的调用前挂载点只能改写上下文，**接管不了调用本身**——重试必须"包住"调用，而不是在调用前后做事。理论上可以给钩子契约新增一个"调用失败"挂载点，但那要修改内核的异常处理路径，还要同步改回权威源。本模块选择了零侵入的替代方案：把恢复逻辑做成调用出口的一层包装，由装配处在构造智能体**之前**用包装后的入口替换原始的（智能体的调用入口一经构造便不可替换，所以包装必须发生在更早的位置）。所以这个能力注册的钩子列表是空的——它对主循环的全部影响，都藏在装配顺序里。代价是可发现性差：读代码的人必须看到装配处，才能意识到每次模型调用其实先穿过了一层恢复逻辑。

## 一次完整运行的流转

一次长会话，三种故障先后登场。

**故障一：上下文溢出。** 用户与智能体已经聊了几十轮，新一轮请求发出，模型服务直接拒收："请求太长。"

1. 调用抛出异常，包装层接住，分类器读遍消息、类型名与因果链，判定为"上下文超长"。
2. 走路径二：应急压缩——保留首条任务目标，插入一条"已省略几十条历史消息"的说明，保留最近 6 条，控制台打印压缩明细。
3. 原地重试，这次请求被接受，循环继续。因为压缩是原地生效的，后续每一轮都基于瘦身后的历史，短时间内不会再触发。

**故障二：限流。** 几轮之后，服务端返回限流。

1. 分类器判定为"限流"，走路径三：等待约半秒（含抖动）后重试，成功，计数清零。
2. 整个过程用户只感到一次略长的停顿——恢复层的意义就在于此：好的恢复是用户感知不到的恢复。

**故障三：输出截断。** 用户要求写一份很长的说明文档，回复到一半戛然而止。

1. 包装层检查回复的结束原因，发现是"达到输出上限"，走路径一：上限一次性放大 8 倍并重试。
2. 重试后完整输出。与此同时，系统提示词里的约定开始起作用——即便某轮最终仍被截断，模型在下一轮也会接着写，而不是从头再来。
3. 本会话后续所有轮次都按新上限执行，不再反复触发。

**尾声：断网。** 网络中断，连续六次尝试分别等待约半秒、一秒、两秒、四秒……仍全部失败，重试次数耗尽，异常被抛出，控制台打印错误后本轮结束。用户看到的是一条清晰的错误提示，而不是一个卡死的程序；网络恢复后，下一句话就能继续。

### 如何验证

| 做法 | 期望 |
|---|---|
| 把输出上限临时改到极小，问一个需要长回答的问题 | 观察到"输出截断 → 上限升级 → 续写" |
| 进行十几轮长对话 | 触发"上下文超长 → 应急压缩 → 重试成功" |
| 临时指向一个无效的服务地址 | 观察到指数退避逐次翻倍，六次后放弃并报错 |
| 配置兜底模型并模拟连续过载 | 观察到一次性切换到兜底模型 |

## 设计取舍

**为什么分类靠关键词匹配，而不是结构化的错误码？** 理想情况当然是从异常类型上判断，但不同模型服务、不同接入方式给出的失败描述五花八门，文本匹配是唯一能在多处通用的低成本手段。代价是脆弱：服务端换一种措辞，分类就可能失效。缓解手段有二——匹配范围覆盖消息、类型名与整条因果链；默认归类为"不可恢复"，宁可放弃重试也不错误地空转。

**为什么应急压缩这么粗暴？** 因为触发它的时刻是"请求已被拒收"——此刻的首要目标是让下一发请求能通过，任何"用模型生成高质量摘要"的方案都要再花一次调用、还可能再次失败。保留首条加最近若干条的做法零成本、零风险、立即生效。质量的欠账由模块 06 的主动压缩来还：在还没溢出时就按节奏压缩，就轮不到应急手段出场。

**为什么重试上限只有 6 次？** 指数退避下，6 次意味着累计等待已接近一分钟量级；还不通，大概率不是抖动而是故障（服务宕机、本地断网、配置错误）。此时继续等只会让用户面对一个"看起来还活着"的假象。快速失败加清晰报错，比无限重试更尊重用户。

**为什么兜底模型默认关闭？** 单模型场景下没有真正的"兜底"——切到一个同样过载的实例只是自我安慰。兜底切换的价值依赖多模型部署，且引入新问题：不同模型的输出风格差异会让会话前后不一致。所以机制留好了（状态、阈值、一次性切换的标志），默认不启用。

**为什么没有检查点与回滚？** 面对失败，更重的方案是给每个工具执行做检查点、失败时回滚到上一个安全状态。本模块没有走这条路，因为循环里的故障绝大多数发生在**模型调用层**——那一层没有需要回滚的副作用，等一等或压一压就够。工具层的破坏性后果，防线在模块 09 的权限闸门（事前拦截），而不是事后回滚。两种思路分别守两层，比在同一层堆两个机制更清晰。

## 在整个项目中的位置

相对模块 11，12 在架构上开了一个新口子：它是第一个**不占用任何钩子挂载点**的能力——钩子只能在调用前后做事，而恢复必须包住调用本身，于是它以包装调用出口的方式接入，把"能力改变循环行为"的第二种形态（改上下文之外的另一种）演示了出来。

往回看，它把此前"出错即停"的循环补成了"出错能走"的循环：工具失败回灌、调用失败重试、上下文溢出压缩、输出截断续写，故障的每一层都有了去处。往前看，它为三件事铺路——模块 13 接入外部工具后，网络故障会成倍增多，恢复层从"可用"变成"必需"；模块 16 的定时任务与模块 19 的自主循环跑在无人值守环境里，"出错等人来修"不再成立，指数退避与有界重试正是无人值守的生存底线；而"恢复状态该记什么、记多久"的设计，与模块 11 的记忆、模块 06 的压缩共同指向同一个母题：在有限的上下文与有限的耐心里，决定什么值得被留住。
