# 模块 22：多模态

> 让原本"只能读字"的智能体长出眼睛——图像作为消息内容的一部分进入上下文，模型"看到"之后再决定下一步调用什么工具。

## 这个模块要解决什么问题

前面二十一个模块里，上下文里流动的清一色是文字。可现实中的求助场景大量以图像形式出现：

- "程序崩了，你看这个报错弹窗"——一张截图；
- "照着这张设计稿把页面写出来"——一张设计图；
- "这张流程图里的逻辑对不对"——一张示意图；
- "帮我看看日志截图里第二行是什么"——一张照片。

旧的处理方式是把图片转成文字描述再喂给模型，可这一步本身就丢掉了绝大部分信息：布局、颜色、字体、控件位置、报错的高亮行，全都没了。要真正"看图"，图像必须以图像的身份进入对话，而不是以一段转述文字的身份。

这个模块回答三个问题：图像怎么放进一条消息里？工具采集到的图像怎么交给模型？模型"看到"之后如何继续行动？

## 核心思想

**图像不是工具结果的附赠品，而是消息内容的一种类型。**

在此之前，一条用户消息就是一段文本；一条工具结果也是一段文本。这个模块把"消息内容"升级为**内容块的列表**：一条用户消息可以由若干块拼成——一块文本、一块图像、再一块文本，顺序任意。图像块带着两样元信息：它是什么图像格式，以及它的像素数据经过编码后的那串长文本。

同时保留一条底线：**降级通路**。并不是所有模型都支持看图。开关一关，所有图像立刻退化为一句占位描述（"一张某格式、某大小的图片"），功能从"看图"降级为"知道有图"，但整个系统不崩、不阻塞、行为可预期。

于是有两条并行的图像通路：

```
通路一：用户消息携带图像块（模型真的看）
   用户命令 → 读文件/编码 → 图像块 + 文本块 → 协议适配层翻译 → 模型

通路二：工具结果回传（受协议限制的降级形态）
   模型调用读图工具 → 工具返回"图像描述文本"（含编码数据与类型标记）
                    → 模型知道有图、有多大，但看不真切
```

## 工作原理

### 1. 消息的多内容块结构

消息模型在原有"角色 + 文本"的基础上，为用户角色增加了一个可选的内容块列表。每个内容块自带类型标记：文本块只有文字；图像块带图像格式标记（比如图像格式加子类型的那串标准记号）和编码后的像素数据；文件块带文件名和文字内容。

关键在发送环节。消息模型是协议中立的，而各家模型服务对"怎么在消息里放图"的规定不同：一家的写法是"带数据前缀的图片地址"，把编码数据直接塞进地址字符串；另一家的写法是"图像内容块"，格式标记与数据分字段放。协议适配层负责把中立的图像块翻译成各自的写法——上层逻辑只造一次图像块，两家协议都能发。

两类协议在细节上还有差别：前一类把每个内容块（文本块、图像块）平铺成一个数组，图像以"自解释的数据地址"出现，格式信息就写在地址的开头；后一类则要求图像块显式声明自己的来源类型与格式标记，数据单独一个字段。翻译层吸收了这些差异，上层因此不需要知道"现在连的是哪家"。附带的收益是：将来接入第三家协议，只需在翻译层多写一个转换分支，能力包与命令逻辑原封不动。

文件块的处理也值得一提。内容块类型里预留了"文件"这一种：它带文件名和文字内容，发送时被翻译成一段"方括号包着文件名，再跟正文"的纯文本。它不是图像，走不了视觉通道，但让"附一份文件"这件事与"附一张图"在消息结构上共享同一套骨架——多模态不只是图，而是一整类"非纯文本内容"的统一入口。

### 2. 工具结果通路为什么"看不了"

一个容易被忽略的协议约束：**工具结果在协议上只能承载文本**。工具调用之后，回灌给模型的那条结果消息没有图像块的容身之地。

所以读图工具的返回被设计成一个描述性的文本：里面写明"这是一张图像"、标出格式和数据量，再附上完整的编码数据。模型读到它，知道确实有一张图、什么格式、多大；但编码数据对模型而言只是文本，不会在视觉层面被"看见"。真要让模型看，得走通路一——把这张图以用户消息的身份重新附上。这就是为什么模块的说明里明确写着：工具通路是降级形态，附图命令才是真正的看图入口。

这个限制来自协议本身，绕不过去；诚实地把它讲清楚，比假装"工具返回了图片"更接近真实工程。

两条通路对照着看更清楚：

| | 通路一：用户消息附图 | 通路二：工具结果回传 |
|---|---|---|
| 图像以什么身份进入 | 真正的图像内容块 | 包着编码数据的描述文本 |
| 模型能不能看见 | 能（协议原生支持） | 不能，只知道有图、什么格式、多大 |
| 由谁触发 | 用户用附图命令 | 模型调用读图或截屏工具 |
| 典型用途 | "看这张图回答问题" | "程序自己采一张图看看" |
| 会话落盘 | 剥离编码数据，留描述 | 文本原样留存，可追溯 |

### 3. 图像的采集：读文件与截屏

多模态能力向内核注册了两个工具：

**读文件工具（图像增强版）**。流程如下：

```
拿到路径 → 拼上工作目录、做规范化
   → 系统探测文件类型；探测不到就按扩展名猜（图、文、数据各有各的猜法）
   → 是文本类：原样返回文字
   → 是图像类：读出全部字节 → 编码成文本 → 包成图像描述
   → 是其它二进制：不硬读，返回一句"某类型、某大小"的描述
```

**截屏工具**。调用操作系统的屏幕抓取能力，把整个屏幕截成一张位图，转成标准图像格式，再编码。它先做一次环境探测：在没有任何显示器的"无头"环境里抓屏必然失败，此时不抛出难懂的异常，而是返回一句友好说明。工具结果同样按"看图开关"决定返回编码数据还是占位描述。

两个工具共用同一套"识别类型 → 读取字节 → 编码 → 包装"的骨架，差异只在图像来源是磁盘还是屏幕。

### 4. 附图命令与命令分发的小改造

除了工具，能力还贡献了一条用户命令：输入"命令 + 图片路径 + 可选的问题"，就直接把图片以用户消息的身份附给模型。这条命令的执行流程：

```
识别命令前缀
   → 解析参数：第一个词是路径，其余（若有）作为随图提出的问题
   → 读文件、验证确实是图像
   → 看图开关打开：造一个图像内容块
     看图开关关闭：造一个文本块，内容是降级占位描述
   → 再追加一个文本块（问题本身；没写问题就用默认的"请描述这张图片"）
   → 拼成一条多块用户消息，加入上下文
   → 下一轮模型调用时，模型真的（或名义上）"看到"了图
```

这里有个实现层面的坎：内核的用户命令是按名字精确匹配的，而这条命令后面跟着参数，"命令加参数"并不等于"命令"。解法是入口在命令分发处包了一层：先按前缀判断是不是这条命令，是就转交能力自己解析参数；不是就回落到内核原有的命令处理器。能力的命令清单在注册时已合并进命令表，帮助信息照常展示。

### 5. 能力化：多模态是一个可整体搬走包裹

这个模块没有改动内核的任何一行。所有多模态逻辑——两个工具、一条命令、一段系统提示词片段、一份"是否支持看图"的配置——都收拢在一个独立的目录里。接入它只需要两步：把目录复制过去，在入口加一行注册。

提示词片段是三句话：读文件遇到图像会自动转编码数据、截屏可抓取当前屏幕；用户给图时先描述图再回答；若当前模型不支持看图，图像已被降级为文字描述，请明确告诉用户。最后一句很重要——降级状态下模型自己必须知道自己是"瞎"的，才不会对着一句占位描述编造图像内容。

### 6. 成本账：大图为什么贵，这个模块怎么省

图像的编码数据是按字节展开的长文本，编码后还要再膨胀约三分之一。一张全屏截图动辄几百上千 KB，编码后是几十万字符——如果直接塞进上下文，一次调用就可能顶掉几万次普通对话的预算，而且**每一轮循环都要原样重发一遍**：上下文是全量重放的，图附一次，之后每次请求模型都带着它。

这个模块的应对手段有三层，都是"避"而不是"压缩"：

- **总开关**。配置里一个布尔开关决定模型是否支持看图。关闭时所有图像退化为一句几十个字符的占位描述，成本几乎归零。默认模型的看图能力如何，开关就设成什么，绝不让编码数据白白流进一个根本看不见它的模型。
- **落盘剥离**。会话历史持久化到磁盘时，图像块不写编码数据，只写"某格式、多少字符"的描述行。否则一次附图就会把会话文件撑到几十 MB，恢复会话时还要原样读回来。代价是：恢复出来的会话里那句话变成了占位描述，图像本身不在了——这是用"可追溯性换体积"的明确取舍。
- **工具结果的字数控制**。命令输出类的工具结果本就有超长截断，防止一次大输出撑爆上下文；图像数据不走这条路（截断编码数据会得到一张损坏的图），而是靠开关在上游就拦住。

### 7. 恢复会话时会发生什么

落盘剥离的代价在恢复会话时显现。重开进程、加载历史会话后，那条曾经附过图的用户消息只剩一句"图像：某格式、多少字符"的占位描述——编码数据已经不在了。这意味着两件事：

其一，恢复后的对话里，模型无法再"看见"之前那张图。用户接着问"刚才那张图的左下角写了什么"，模型只能看到占位描述，正确的做法是请用户重新附一次图。其二，这也是一种保护：假如编码数据原样落盘，恢复会话会把整段数据重新灌进上下文，每一轮请求都为一张旧图持续付费——剥离等于把这笔账在会话边界上结清。

设计上这是"会话文件管对话轨迹，不管原始素材"的定位。原始素材属于文件系统：图在磁盘上一直都在，需要时随时再读、再附。会话要轻，素材要活，两者各管各的。

值得说明的是：这个模块**没有**做图像缩放、裁剪或重采样——生产系统里通常会把大图先压到合理分辨率再发，教学版把这一层留给了读者。

## 一次完整运行的流转

场景一：用户输入"附上设计图，照这个把按钮排一下"。

1. 命令分发层识别出前缀，转交多模态能力解析：路径指向那张设计图，问题是后面那半句。
2. 能力读取文件，系统类型探测确认是图像；看图开关开着，于是把字节编码成数据串，造出图像块；问题文本作为第二个内容块跟上。
3. 这条多块消息加入上下文并落盘——磁盘上只留下"图像：格式、长度"的描述，编码数据不落盘。
4. 下一轮请求模型，适配层把图像块翻译成当前协议的图像写法，模型真的看到了设计图。
5. 模型先描述图里看到的布局（系统提示词要求"先描述再回答"），然后调用命令工具去查看现有的界面代码，再调用编辑工具改文件——"看"与"做"在同一条循环里无缝衔接，这正是多模态的意义：视觉输入直接驱动工具行动。

场景二：用户输入"截个屏看看现在是什么界面"。

1. 模型调用截屏工具；工具先探测显示环境，正常则抓取全屏、转格式、编码。
2. 若看图开关开着，工具结果里带着完整编码数据——模型能从中获知图的元信息，但如前所述，工具通路在协议上到不了"看见"那一层；模型据此向用户说明，并建议用附图方式再看一次，或直接基于已知信息作答。
3. 若开关关着，工具返回占位描述，模型如实告知用户"当前模型不支持看图"——系统提示词片段已经教过它这么做。

## 设计取舍

- **默认关闭看图**。项目默认接入的模型不支持图像输入，开关置关。诚实面对"当前模型看不见"，比发一堆无效数据好得多；换一个支持看图的模型，改一行配置即可开启。
- **两条通路分工明确，而不是硬造一条全能通路**。工具结果受协议限制只能带文本，那就让它承担"元信息+可追溯"的角色；真正的视觉输入走用户消息通路。与其在协议缝隙里造黑魔法，不如把约束摊开讲清楚。
- **落盘剥离编码数据**。会话文件的可恢复性、可传输性优先于图像的完整留存。需要长期留图的场景，应该在业务层单独存文件、上下文里只留路径。
- **不做图像压缩**。缩放重采样是生产必备，但会把教学焦点从"图像如何进入对话"挪到"图像如何被处理"。留白即考题。
- **能力包裹自持配置**。"是否支持看图"这类特性开关跟着能力目录走，而不是堆在全局常量里——拔掉多模态，这个开关也一并消失，内核永远不知道"图像"这个词。

## 在整个项目中的位置

排在这个位置有讲究。模块二十一把所有机制织成了一台完整机器，但那台机器是"盲"的——它的上下文模型里只有文字。本模块在整机之后再做一个干净的小切口：只扩展"什么可以进入上下文"这一件事，顺带演示了能力包裹的完整集成形态（复制目录、一行注册、配置随包走）。

它与前后模块的呼应也很清楚：向后看，模块二十四的宿主视角会再次梳理"各种内容与事件从哪里进入循环"，图像通路正是其中一条；向前看，凡是涉及"模型直接观察真实世界"的延伸——屏幕操作、界面验证、图表理解——都建立在这里确立的两个基点上：图像以内容块的身份进消息，以及不支持时优雅降级。
