# 模块 03：待办清单

> "没有计划的智能体走哪算哪。" —— 把计划从模型的脑子里搬出来，变成一张双方都看得见、可追踪、还会被反复催更的任务表。

本文建立在模块 02 之上：六个文件与搜索工具原样保留，本模块新增第七件工具（待办清单工具），并第一次引入"可插拔能力"的集成方式——功能不再焊死在主程序里，而是作为一个可以整体摘除的部件挂上来。

## 这个模块要解决什么问题

多步任务里，模型会丢进度：重复做已经做过的事、跳过某一步、或者干脆跑偏。对话越长越严重——工具结果源源不断地涌进上下文，系统提示词的影响力被逐渐稀释。一个十步的重构，往往做到第三步就开始即兴发挥，因为第四到第十步早被挤出了注意力。

模块 01/02 里模型当然也会"计划"——在思维链里默默排步骤。但内部规划有两个致命属性：**不可见**（用户和开发者都看不到它打算干什么）和**短暂**（一旦那些思考滚出上下文窗口，计划就永久丢失了，模型只剩眼前这步）。

还有一个工程层面的老问题：如果直接把待办逻辑写进主循环，以后每加一个类似功能都要再改一次内核，内核很快变成谁都动不得的一坨。本模块要同时回答这两个问题——计划怎么外化，功能怎么插拔。

## 核心思想

三句话：**把计划外化成一个工具；用硬约束逼模型好好维护它；模型忘了就催。**

1. **计划外化**：给模型一件"待办清单工具"。它每接一个像样的任务，第一步就是把拆好的步骤连同状态（待处理 / 进行中 / 已完成）提交给这张表。计划从不可见的思维链，变成消息流里一条条具体的工具调用。
2. **约束先行**：清单不是随便写的——内容不能为空、状态只能三选一、总量有上限、同一时刻只允许一个任务处于进行中。约束做在管理器里，不合规的提交直接拒绝并说明原因。
3. **自动催办**：模型跟人一样会忘记更新进度。系统盯着清单的版本号，连续几个回合没有动静，就在下一次请求前悄悄往上下文里塞一条提醒。模型于是被"拉"回计划轨道。

两种规划方式放在一张表里对比，本模块的选择就一目了然：

| | 模型内部规划（01/02 的做法） | 外化清单（本模块的做法） |
|---|---|---|
| 用户能否看到 | 不能，只能看到行动结果 | 能，第一步就是那张表 |
| 开发者能否调试 | 不能，无从检查 | 能，本地命令随时查看 |
| 早期步骤滚出上下文后 | 计划随之丢失 | 清单仍在历史里，可随时翻回 |
| 会不会被遗忘 | 经常会 | 忘了会被催 |

值得注意的是：外化并没有取代内部规划，而是给它加了一层"可持久、可检查的外壳"。模型依然自己决定怎么拆任务、先做哪步——机制只负责让这些决定留下来、被看见、被追踪。

整个待办功能——工具、催办钩子、本地查看命令、提示词片段——被打包成一个自持的**能力包**。内核只提供固定的挂载点，不感知任何具体能力；想移除待办功能，删掉能力目录、去掉装配处的一行注册即可，内核一尘不染。

## 工作原理

### 1. 一个能力如何接入内核

内核向能力开放五条通道，能力按需取用：

```
                 内核（智能体循环）
   ┌────────┬────────┬─────────┬──────────┬─────────┐
   ▼        ▼        ▼         ▼          ▼         ▼
 注册工具  挂载钩子  注册命令   贡献提示词   生命周期    …
   │        │        │        片段        回调
   │        │        │           │
   ▼        ▼        ▼           ▼
 待办工具  每次请求前  本地查看   任务管理策略  启动时捕获
          检查是否   清单（不   写进系统提示   宿主引用
          要催办     发给模型）
```

装配时的次序有讲究：先注册能力（工具并入清单、同名跳过、钩子与命令各自入册），再设置会话管理器（命令清单在会话初始化时收集），最后把各能力贡献的提示词片段拼接到基础系统提示词之后。多个能力挂载点上的执行顺序 = 注册顺序，这让行为可以预期。

### 2. 待办工具与"整表替换"语义

待办工具的参数说明是本项目第一个**嵌套结构**：一个列表，列表里每项包含任务编号、内容描述、状态（取值限定三种）、以及一个可选的"进行中展示名"（动词短语，渲染时跟在进行中的任务后面，比如"正在编写工具类"）。

它的语义是**整表替换**：每次调用提交的是完整的任务列表，而不是"新增一条""修改第几条"这样的增量操作。这看起来浪费，实则聪明——模型永远不需要记住"上一次提交了什么"，每次都是对着当前事实重新声明一遍全局状态，出错后自我修复也简单：重新提交一张正确的表就行。

### 3. 管理器的三条铁律与版本号

管理器接收提交后逐项校验，任何一条不过就整体拒绝：

| 约束 | 理由 |
|---|---|
| 内容不能为空 | 空任务没有任何信息量，纯占上下文 |
| 状态只能是待处理/进行中/已完成 | 拼写错误的第四种状态会破坏渲染与统计 |
| 总量有上限（二十项） | 防止计划膨胀：冗长的任务表吃掉宝贵的上下文，而且多半执行不完 |
| 同时只有一个进行中 | 防止伪并行——语言模型本质是串行的，"多任务"只是快速切换，结果是上下文碎片化、每件事都做不深 |

通过校验后，整表生效，**版本号自增一**。这个看似不起眼的计数器是下一节催办机制的基石：它让"模型最近有没有维护计划"变成一个可以直接比较的数字，而不用去猜"刚才那次工具调用算不算更新"。

通过校验后立即渲染返回——用三种符号标识状态（待处理、进行中、已完成），进行中的那行追加展示名，末尾附上"几项共几项已完成"的进度统计。模型每提交一次，立刻能看到格式化后的全表，这个回显本身就是一次状态确认。

### 4. 渲染即反馈：一张会说话的表

每次提交通过校验后，管理器立即把整张表渲染成文本返回给模型：

```
[ ] 初始化配置文件            ← 待处理
[>] 编写工具类 <- 正在编写工具类 ← 进行中，后跟"正在进行的是什么"的短语
[x] 创建项目目录              ← 已完成

(1/3 已完成)                  ← 进度统计
```

这份回显一举三得：对模型，它是一次强制性的状态确认——你刚提交的状态现在长这样，写错了当场就能看见；对上下文，它是一条紧凑的状态快照，后续轮次里模型随时能从历史中翻到"自己在哪一步"；对用户，它原样出现在终端上，计划第一次变得肉眼可见。

### 5. 催办钩子：模型健忘的保险丝

每次向模型发起请求**之前**，钩子都会被调用一次，做这件事：

```
取当前清单版本号
     │
     ├─ 比上次见到的版本号新？──是──▶ 模型在好好维护：计数器清零，本轮不打扰
     │
     └─ 否 ──▶ 计数器加一
                 │
                 ├─ 还没到阈值（三回合）──▶ 静默放行
                 │
                 └─ 到了 ──▶ 造一条提醒消息，追加到本轮上下文末尾，
                             然后计数器清零（每个周期只催一次，避免刷屏）
```

两个设计点值得注意：

- **挂在"请求前"而不是"工具执行后"**。早期的实现把提醒塞进工具结果里，但那个挂载点在某些内核上根本不会触发；能力化之后改挂在真正每次都会经过的请求前钩子上，行为稳定。挂载点选在哪里，比提醒文案写什么更重要。
- **提醒是一条用户角色的消息，且只影响本轮**。它不进持久化的历史，不污染后续对话；模型看到提醒后更新了清单，版本号一变，计数器自动归零，催办自然停止。这是一个自我消解的负反馈回路。

### 6. 提示词片段与本地命令

催办是"事后拉回来"，提示词片段是"事前讲规矩"。能力贡献的一段任务管理策略被拼进系统提示词：接新任务先建清单、进行中定期更新、完成立即标记、上限多少、连续几回合不更新会被提醒。规则讲在前面，催办就只是兜底。

另有一个本地命令让用户随时查看当前清单——它只在终端渲染，不发给模型，属于"给人看"的旁路视图，调试智能体行为时特别有用。

## 一次完整运行的流转

场景剧本：用户要求"构建一个支持加减乘除的命令行计算器"——典型的多步任务。

1. **先立计划，再动手。** 模型的第一个动作不是写代码，而是调用待办工具，提交四项任务：创建带参数解析的计算器脚本（进行中）、实现四种运算（待处理）、添加错误处理（待处理）、测试所有运算（待处理）。管理器校验通过，返回渲染好的清单："一项进行中，三项待处理，零已完成"。
2. **按计划执行。** 模型调用写入文件的工具，一次性写出包含四种运算的完整脚本；返回"写入成功"。
3. **自测。** 模型调用执行命令行的工具，运行脚本算一道题，得到正确结果。
4. **更新进度。** 期间模型按提示词里的规矩更新清单：把已完成的任务标为已完成，把下一步标为进行中。每次提交都会收到新的全表回显，进度一目了然。
5. **（岔路）假如模型忘了更新。** 设想它在第三步之后连续三个回合只顾埋头改代码，清单版本号纹丝不动。于是第四回合请求发出前，钩子往上下文末尾追加了一条提醒："您已经若干回合没有更新待办列表了，请检查任务状态、更新已完成项、调整优先级。"模型读到后重新提交一张表，版本号一变，计数器归零，催办自动停歇——没有人手动干预。
6. **收尾汇报。** 全部任务完成后，模型回复文本："计算器已构建并测试，所有运算正常工作。"循环退出。

整场下来，用户在任何时刻都能说出"它现在做到第几步了"——这在模块 02 里是不可想象的：那时计划的唯一载体是模型的思维链，转瞬即逝。

## 设计取舍

- **外化计划，而不是相信思维链。** 内部规划有效但不可见且短暂；扩展思考功能倒是可见于界面，但用户之外的角色（下游工具、测试脚本）都无法检查它。一条条工具调用是最笨也最通用的计划载体：可渲染、可持久化、可统计。
- **同一时间只允许一个进行中。** 备选方案是允许多个并行任务，看似更快，实际是让模型在任务间反复横跳，上下文碎片化、质量下降。强制单一进行中，等于逼模型在每一步都做出明确的优先级决策。
- **上限二十项。** 太少（比如五项）装不下真正复杂的任务；太多（比如二十项以上）会催生在有限上下文里根本执行不完的庞大路线图。二十是经验值，配上"接近上限就先完成再加新任务"的策略，兼顾分解能力与计划纪律。
- **整表替换，而不是增量修改。** 增量接口（加一条、删一条、改状态）省一点传输，却要求模型精确维护"服务器上现在长什么样"的心智副本——这正是它最不擅长的事。整表替换把状态机的复杂度收进管理器，模型只负责声明事实。
- **提醒以临时用户消息注入，而不是塞进工具结果。** 前者挂载点稳定、不进历史、可自我消解；后者会和真正的工具输出混在一起，还依赖一个未必触发的回调。
- **能力自持，而不是内核硬编码。** 早期版本的待办管理器靠入口类的静态字段桥接给工具定义，配置散落在内核常量里；能力化之后，管理器实例、上限配置、催办阈值全部收进能力包内部。拔除一个功能不再是一场外科手术。
- **集成方式刻意朴素：复制目录 + 一行注册。** 没有插件加载器、没有依赖注入容器、没有配置文件格式。一个能力就是一个可整体拷贝的目录，加上装配处的一行注册语句。对教学项目而言，"看一眼就懂全部接线"比"架构上无懈可击"更值钱；代价是能力之间无法独立升级，可这正是本项目的模块化粒度选择——按模块整存整取。
- **管理器的读写方法全部加锁。** 待办状态在理论上可能被并发触达（子智能体、多任务场景），管理器从诞生起就把所有读写方法声明为互斥执行。这是花一次成本买来的"以后不用想"——本模块单线程跑不出问题，但状态类组件的线程安全不该等到出事那天再补。

## 在整个项目中的位置

模块 03 是项目从"拼功能"转向"长能力"的分水岭，两件事从这里开始定型：

1. **能力包模式**。工具、钩子、命令、提示词片段、生命周期五条通道在内核上开好口子，之后每个特性（技能、压缩、任务委派……）都以同样的方式挂载。模块 01 里预留的"请求前上下文挂载点"在这里第一次被真正用起来——它马上还将在模块 06 承担更重的活：整段压缩历史。
2. **可见状态**。待办清单是系统里第一个"模型写的、给人看的、也被模型自己反复读的"持久状态。它直接为模块 04 铺路：当主智能体开始把子任务委派出去，正是这张清单让"哪些在手上、哪些委派了、哪些完成了"依然有据可查。

一句话概括：模块 02 给了模型工具，模块 03 给了模型纪律——外加给开发者一个能插拔这些纪律的插槽。
