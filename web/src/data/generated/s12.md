# s12: Error Recovery（错误恢复）

`s01 > ... > s10 > s11 > [ s12 ] > s13 ...`

> *"输出被截断就升级、上下文溢出就压缩、限流就退避重试"* — 三条恢复路径让 agent 在异常下继续运行。

## 问题

到 s11 为止，agent 一旦 LLM 调用失败就崩：输出超长被截断（`stop_reason == max_tokens`）、上下文超限（`prompt_too_long`）、API 限流（429 / 529）、网络抖动。这些异常在生产中很常见，但教学版之前要么直接抛出，要么简单重试。

**核心矛盾：**
- ❌ 输出截断 → 模型话没说完，结果残缺
- ❌ 上下文溢出 → 直接崩，无法继续
- ❌ 限流/抖动 → 没有退避策略，连续失败
- ❌ 高峰过载（529）→ 不知道切 fallback 模型

## 解决方案

![Error Recovery Overview](/agent/error-recovery-overview.svg)

引入 **RetryWrapper** — 包装 LLM 调用，把异常分类后路由到三条恢复路径：

| 触发条件 | 恢复动作 |
|---------|---------|
| `stop_reason == max_tokens`（输出截断） | 升级 maxTokens 8K → 64K，让模型续写 |
| `prompt_too_long`（上下文溢出） | 触发 `ReactiveCompactor.compact`：保留首条 user + 最近 6 条，中间摘要替代 |
| 429 / 529 / 网络抖动 | 指数退避 `min(500×2^attempt, 32000) + jitter`；连续 3 次 529 切 fallback model |

每条路径用 `RecoveryState` 跟踪尝试次数、当前 maxTokens、当前模型。

## 工作原理

### 1. RecoveryState — 跟踪恢复进度

```java
public class RecoveryState {
    public int attempt = 0;
    public int consecutive529 = 0;
    public int maxTokens;          // 当前 maxTokens（可能被升级）
    public String model;            // 当前 model（可能切到 fallback）
    public String fallbackModel;    // 可为 null
}
```

### 2. ErrorClassifier — 异常分类

把原始异常/响应映射到 5 种类型，决定走哪条路径：

```java
public enum ErrorType {
    PROMPT_TOO_LONG,   // → ReactiveCompactor
    RATE_LIMIT,        // → 退避
    OVERLOAD,          // 529 → 退避 + 可能切 fallback
    TRANSIENT,         // 网络抖动 → 退避
    FATAL              // 无法恢复，抛出
}

public static ErrorType classify(Throwable t, String stopReason) {
    if (stopReason != null && "max_tokens".equals(stopReason)) return MAX_TOKENS;
    if (t.getMessage().contains("prompt_too_long"))             return PROMPT_TOO_LONG;
    if (status(t) == 429)                                       return RATE_LIMIT;
    if (status(t) == 529)                                       return OVERLOAD;
    if (t instanceof IOException)                               return TRANSIENT;
    return FATAL;
}
```

### 3. ReactiveCompactor — 紧急压缩

`prompt_too_long` 触发，不动文件，只在内存压缩 `messageParams`：保留首条 user + 最近 6 条，中间用一次性 LLM 调用生成摘要替代：

```java
public List<MessageParam> compact(List<MessageParam> msgs) {
    if (msgs.size() <= 8) return msgs;
    MessageParam head = msgs.get(0);
    List<MessageParam> middle = msgs.subList(1, msgs.size() - 6);
    List<MessageParam> tail = msgs.subList(msgs.size() - 6, msgs.size());
    String summary = summarizeOnce(middle);   // 一次单独 LLM 调用
    List<MessageParam> out = new ArrayList<>();
    out.add(head);
    out.add(new MessageParam("user", "[earlier conversation summary]\n" + summary));
    out.addAll(tail);
    return out;
}
```

### 4. RetryWrapper — 三路径调度

```java
public Response call(Function<RecoveryState, Response> paramBuilder,
                     RecoveryState state,
                     List<MessageParam> history) {
    while (true) {
        try {
            Response resp = paramBuilder.apply(state).send();
            state.consecutive529 = 0;
            if ("max_tokens".equals(resp.stopReason)) {
                // 路径 1：升级 maxTokens 续写
                System.out.println("[recovery] 升级 maxTokens → 64000 并续写");
                state.maxTokens = 64000;
                continue;
            }
            return resp;
        } catch (Exception e) {
            ErrorType t = ErrorClassifier.classify(e, null);
            switch (t) {
                case PROMPT_TOO_LONG:
                    System.out.println("[reactive compact] 保留首条 + 最近 6 条");
                    history = ReactiveCompactor.compact(history);
                    break;
                case RATE_LIMIT:
                case TRANSIENT:
                case OVERLOAD:
                    state.attempt++;
                    if (t == OVERLOAD) state.consecutive529++;
                    if (state.consecutive529 >= 3 && state.fallbackModel != null) {
                        System.out.println("[recovery] 连续 529，切到 fallback 模型");
                        state.model = state.fallbackModel;
                    }
                    long backoff = Math.min(500L * (1L << state.attempt), 32000L);
                    long jitter = (long)(Math.random() * 100);
                    Thread.sleep(backoff + jitter);
                    break;
                case FATAL:
                    throw e;
            }
        }
    }
}
```

### 5. ZQAgent 集成

`ZQAgent` 新增 `retryWrapper / recoveryState / fallbackModel` 三字段。`chatMessage` 内部判断：有 `retryWrapper` 时走 `RetryWrapper.call(...)`，paramBuilder 接收 `RecoveryState` 从中取当前 model / maxTokens。RecoveryState 在首次调用时按 model / fallbackModel 懒初始化。

## 相对 s11 的变更

| 组件 | s11 | s12 |
|------|-----|-----|
| 异常处理 | 直接抛 / 简单重试 | 三路径分类恢复 |
| 新增类 | — | RecoveryState、ErrorClassifier、ReactiveCompactor、RetryWrapper |
| max_tokens 截断 | 输出残缺 | 升级续写 |
| prompt_too_long | 崩 | 内存压缩后重试 |
| 429/529/抖动 | 崩 | 指数退避 + 可能切 fallback |

mvn -pl hoppinzq-module-agent-12-errorrecovery -am compile

四个场景：

1. **触发输出截断**：临时把 `AIConstants.MAX_TOKENS` 改到很小（如 64），问一个需要长回复的问题，看 `[recovery] 升级 maxTokens → 64000 并续写`
2. **触发上下文压缩**：进行 10+ 轮长对话，下一轮命中 `prompt_too_long`，看 `[reactive compact]` 日志
3. **触发退避**：临时把 `AIConstants.BASE_URL` 改到无效地址，看 `[recovery] 退避 Nms（base=X, jitter=Y）`
4. **连续 529 切 fallback**：设置 `FALLBACK_MODEL` 非 null 后模拟连续 529，看 `[recovery] 连续 529，切到 fallback 模型 xxx`
