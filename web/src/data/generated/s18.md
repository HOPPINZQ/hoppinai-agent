# s18: Team Protocols（团队协议）

`s01 > ... > s16 > s17 > [ s18 ] > s19 > s20`

> *"队友之间要有约定"* — request-response 模式 + 状态机驱动协商。

## 问题

s17 的 teammate 能干活了，但协调是松散的：Lead 发消息，teammate 回复，没有结构化的协议。两个场景暴露了问题：

**关机**：Lead 想让 Alice 关机。直接杀线程，Alice 写了一半的文件留在磁盘上。需要握手：Lead 发请求，Alice 确认收尾后关机。

**计划审批**：Bob 想重构认证模块，属于高风险操作。应该先让 Lead 看 Bob 的计划，审批通过后再动手。

这两个场景结构完全一样：一方发请求，另一方给回复，请求和回复通过同一个 ID 关联。有状态机追踪：`pending → approved / rejected`。

## 解决方案

![Team Protocols Overview](/agent/team-protocols-overview.svg)

s18 在 s17 的文件邮箱基础上加入结构化协议。新增三样：**ProtocolState**（请求状态追踪）、**ProtocolDispatcher**（按消息类型路由到处理器）、**ProtocolRegistry**（match_response 通过 request_id 关联回复与请求，含类型校验）。

两种协议，一套机制：

| 协议 | 方向 | 用途 |
|------|------|------|
| shutdown_request / response | Lead → teammate | 体面关机握手 |
| plan_approval_request / response | teammate → Lead | 计划审批 |

## 工作原理

### 1. ProtocolState — 请求状态

每个协议请求创建一条状态记录：

```java
@Data @AllArgsConstructor
public class ProtocolState {
    private String requestId;    // 唯一 ID，如 "req_004281"
    private String type;         // "shutdown" | "plan_approval"
    private String sender;       // 发起方
    private String target;       // 接收方
    private String status;       // pending | approved | rejected
    private String payload;      // 计划文本或关机原因
    private long createdAt;
}

private final Map<String, ProtocolState> pending = new ConcurrentHashMap<>();
```

发请求时创建记录，收回复时通过 `requestId` 找到对应记录，更新状态。

### 2. 四步协议流程

以关机为例：

```
① Lead 发请求
   String reqId = newRequestId();           // "req_004281"
   pending.put(reqId, new ProtocolState(reqId, "shutdown", "lead", "alice", "pending", ...));
   BUS.send("lead", "alice", "shutdown_request", metadata={requestId: reqId});

② teammate 收到 → dispatch
   inbox = BUS.readInbox("alice");
   String type = msg.type;                   // "shutdown_request"
   → 路由到 handleShutdownRequest()

③ teammate 回复
   BUS.send("alice", "lead", "shutdown_response",
            metadata={requestId: reqId, approve: true});

④ Lead 收响应 → match
   registry.match("shutdown_response", reqId, true);
   pending.get(reqId).setStatus("approved");
```

`requestId` 是贯穿全链路的关联键，请求带着它出去，回复带着它回来。

### 3. ProtocolDispatcher — 按类型路由

teammate 的 inbox 不只收普通消息，还收协议消息。dispatcher 按消息类型分发：

```java
public class ProtocolDispatcher {
    public DispatchOutcome dispatch(String agent, MailboxMessage msg, List<MessageParam> messages) {
        String type = msg.getType();
        String reqId = msg.getMetadata().get("requestId");
        if ("shutdown_request".equals(type)) {
            BUS.send(agent, "lead", "Shutting down.", "shutdown_response",
                     Map.of("requestId", reqId, "approve", "true"));
            return DispatchOutcome.stopLoop();    // 停止循环
        }
        if ("plan_approval_response".equals(type)) {
            boolean approve = Boolean.parseBoolean(msg.getMetadata().get("approve"));
            messages.add(new MessageParam("user",
                approve ? "[Plan approved]" : "[Plan rejected]"));
        }
        return DispatchOutcome.continueLoop();
    }
}
```

新增协议类型只需注册新 handler。

### 4. ProtocolRegistry — 类型校验

`match` 不只按 `requestId` 找状态，还会校验响应类型是否匹配请求类型：

```java
public void match(String responseType, String requestId, boolean approve) {
    ProtocolState s = pending.get(requestId);
    if (s == null) return;
    if ("shutdown".equals(s.getType()) && !"shutdown_response".equals(responseType)) return;
    if ("plan_approval".equals(s.getType()) && !"plan_approval_response".equals(responseType)) return;
    if (!"pending".equals(s.getStatus())) return;     // 已解决，跳过重复
    s.setStatus(approve ? "approved" : "rejected");
}
```

一个 shutdown_response 不会意外 approve 一个 plan_approval 请求。

### 5. 统一 inbox 消费

`check_inbox` 工具和主循环末尾都调用同一个 `consumeLeadInbox()`，先路由协议消息再返回剩余内容：

```java
public List<MailboxMessage> consumeLeadInbox(boolean routeProtocol) {
    List<MailboxMessage> msgs = BUS.readInbox("lead");
    if (routeProtocol) {
        for (MailboxMessage msg : msgs) {
            String reqId = msg.getMetadata().get("requestId");
            String type = msg.getType();
            if (reqId != null && type.endsWith("_response")) {
                boolean approve = Boolean.parseBoolean(msg.getMetadata().get("approve"));
                registry.match(type, reqId, approve);
            }
        }
    }
    return msgs;
}
```

### 6. teammate idle loop — 等待而不是退出

s17 的 teammate 跑完 N 轮就退出。s18 的 teammate 在 LLM 返回非 tool_use 后进入 idle 等待：每秒轮询 inbox，收到 shutdown_request 就响应退出，收到新消息就继续工作：

```
LLM 返回非 tool_use
  → idle: 每秒轮询 inbox
  → 收到 shutdown_request → 回复 shutdown_response → 退出
  → 收到新消息 → 注入 messages → 继续 LLM turn
```

### 7. 三个新工具

```java
request_shutdown  → Lead 发 shutdown_request
request_plan      → teammate 发 plan_approval_request
review_plan       → Lead 回 plan_approval_response
```

## 工具数量

| 工具 | 说明 |
|------|------|
| 上一版（s17）全部工具 | 不变 |
| **request_shutdown, request_plan, review_plan** | 新增 3 个协议工具 |

## 相对 s17 的变更

| 组件 | s17 | s18 |
|------|-----|-----|
| teammate 退出 | 跑完 N 轮直接退 | idle loop，等 shutdown_request |
| 协调方式 | 松散消息 | request-response + 状态机 |
| 新增类 | — | ProtocolState、ProtocolDispatcher、ProtocolRegistry、DispatchOutcome |
| 新工具 | — | request_shutdown, request_plan, review_plan |

## 试一试

```bash
mvn -pl hoppinzq-module-agent-protocols -am compile
mvn -pl hoppinzq-module-agent-protocols exec:java -Dexec.mainClass=com.hoppinzq.agent.AgentProtocols
```

试试这些 prompt：

1. `Spawn alice 让她创建 config.py，然后 request_shutdown(alice)` — 期望：alice 收尾后回 shutdown_response，状态 approved
2. `Spawn bob 让他先提交 plan，等他 plan_approval_request 进 inbox 后 review approve` — 期望：bob 收到 `[Plan approved]` 继续干活
3. `Spawn alice 做事 → request_shutdown → alice 拒绝（仍在写文件）` — 期望：alice 回 shutdown_response approve=false，继续工作
4. `同时 spawn 两个 teammate，分别走 shutdown 和 plan_approval 协议` — 期望：requestId 互不混淆

观察重点：`requestId` 是否贯穿全链路？`pending_requests` 状态是否正确从 pending → approved/rejected？teammate 在 idle loop 时是否每秒轮询？
